## QA verification of the cart total fix

**Verdict: pass.** The fix removes the causes of all four reported symptoms and the coupon-lookup bug. One low-severity edge case remains, and it was not in the report.

### Root causes (traced against the original `f3df4d2:src/cart.js`)
1. **Quantity ignored:** `sum += item.price` never reads `qty`. This gives 19.9 for 3 × 19.90.
2. **Percent coupon inverted:** `sum * value / 100` returns the discount amount, not the discounted total. This gives 20 for OFF20 on 100.
3. **Negative totals:** `sum - coupon.value` has no floor. This gives -5 for TENOFF on 5.00.
4. **Float drift:** the sum is never rounded. This gives 0.30000000000000004 for 0.1 + 0.2.
5. **Inherited coupon match:** `COUPONS[couponCode]` resolves `'constructor'` to `Object`. That makes `sum - undefined` = NaN.

### Fix applied (committed in `0c15ba7`, and the working tree is clean)
The handoff said the changes were uncommitted, but `git diff` is empty and `git show --stat HEAD` shows them in `0c15ba7`. The contents match the handoff.
- Each line is summed as `Math.round(price * 100) * qty` in integer cents.
- The percent coupon is applied as `cents * (100 - value) / 100`, rounded to integer cents.
- The fixed coupon subtracts `value * 100` cents.
- The result is clamped with `Math.max(0, cents) / 100`.
- Coupons are looked up with `hasOwnProperty.call`, so inherited names are ignored.
- The public API `module.exports = { total }` is unchanged.

### Validation evidence
- **Executed:** `npm test` passes 8/8. This includes the 6 new regression tests: quantity, fixed coupon floor, fixed coupon subtraction, percent coupon, cent rounding, and unknown coupons including `'constructor'`.
- **Read:** I checked that each new test fails on the original code. Quantity gives 19.9 instead of 59.7. TENOFF gives -5 instead of 0. OFF20 gives 20 instead of 80. The 0.1 + 0.2 case gives 0.30000000000000004. `'constructor'` gives NaN. The `'fixed coupon is subtracted'` test already passed before the fix, which is expected.
- **Read:** integer-cent division by 100 yields the nearest double to the 2-decimal value, so output such as `0.3` prints cleanly.
- **Read:** `hasOwnProperty` rejects `undefined`, `null`, `'__proto__'`, `'toString'` and `'constructor'`.
- **Read:** the only caller of `total` in the repo is `test/cart.test.js`. There are no other dependents, so there is no wider regression surface.

### Findings
- **Low, edge case (pass):** a fractional quantity is not rounded to cents. `total([{ price: 9.99, qty: 1.5 }])` gives `999 × 1.5 = 1498.5` cents and returns `14.985`. The fix does not round the final value when `qty` is non-integer, and the `qty: number` type allows it. The reported bug does not cover this. A fix would be to round the final cents with `Math.round` before dividing. Whether to do that is for the team to decide.
- **Low, validation (not a finding for this step):** missing or NaN `price` or `qty` returns NaN, and negative prices are not rejected. The previous step already flagged this as a residual risk.
- **Coverage gap:** no test covers `HALF`, percent rounding on odd cent amounts (e.g. 0.99 with OFF20), multi-item carts with a coupon, or prototype names other than `'constructor'`. These are worth adding but are not blockers.

### Limits
- I could not run ad-hoc scenarios. The sandbox allows only the project test commands and Git reads, so every edge-case result above comes from reading the code, not from execution.
- I did not run the fractional-quantity case or the original-code regression check. Both are read-based.
- I did not modify any files.
