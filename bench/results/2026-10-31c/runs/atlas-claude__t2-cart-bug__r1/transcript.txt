## Residual risks

- **Half-cent rounding:** `Math.round(x * 100) / 100` can round some binary-float values such as 1.005 the wrong way, because `1.005 * 100` is slightly below 1.005 × 100 in exact arithmetic. Integer-cent arithmetic would avoid this, but it would be a larger change than the report asks for.
- **Missing `qty`:** an item with no `qty` now produces NaN. The JSDoc says `qty` is required, and the existing tests always pass it, so I did not add a default.
- **Runtime requirement:** `Object.hasOwn` needs Node 16.9 or later. `node --test` already requires a recent Node, so I expect this is fine, but I did not check the project's pinned Node version.
- **Rounding order:** rounding is applied only to the final total, not per line. Customers who expect per-line rounding would see different cents on multi-line carts.

## Final report

**Cause.** The original `total()` had several defects in `src/cart.js`:
- `qty` was never multiplied in, so 3 × 19.90 came out as 19.9.
- A fixed coupon could push the sum below zero (TENOFF on 5.00 gave -5).
- A percent coupon subtracted the discount amount, so OFF20 on 100 returned 20 instead of 80.
- Nothing rounded the result, so float sums such as 0.1 + 0.2 leaked long decimals.
- Coupon lookup used a plain property read, so inherited names such as `constructor` resolved to a truthy function and produced NaN.

**Fix applied (current file, `src/cart.js:13-27`).**
- Line 16 multiplies `item.price * item.qty`.
- Line 18 uses `Object.hasOwn(COUPONS, couponCode)`, so only the table's own keys count.
- Lines 20-24 apply percent coupons as `sum - sum * value / 100` and fixed coupons as `sum - value`.
- Line 26 returns `Math.max(0, Math.round(sum * 100) / 100)`, which clamps at zero and rounds to cents.
- `module.exports = { total }` is unchanged (line 29), and the signature is the same.

**Evidence.**
- *Read:* `src/cart.js` and `test/cart.test.js` as they are now. The test file has 7 tests, covering single item, empty cart, quantity, fixed coupon floor, percent coupons (OFF20 and HALF), cent rounding, and unknown or inherited coupons.
- *Read:* `package.json` has `"test": "node --test"` and no `engines` field. `Object.hasOwn` needs Node 16.9+, and `node:test` needs a recent Node, so the code is compatible with the test runner.
- *Read (grep):* `total` has no callers outside `test/cart.test.js`, so no other code depends on the changed behaviour.
- *Derived by hand, not executed:* each customer example gives the expected result.
  - 19.9 × 3 = 59.7 (the product rounds to 5970 cents).
  - TENOFF on 5 gives 5 − 10 = −5, clamped to 0.
  - OFF20 on 100 gives 80.
  - 0.1 + 0.2 gives 0.30000000000000004 and rounds to 0.3.
  - An inherited name like `constructor` is skipped by `Object.hasOwn`, so the total stays 10.
- *Derived by hand:* the regression tests would fail on the original code. Without the quantity fix, the 19.9 test returns 19.9. Without the clamp, the TENOFF test returns -5. Without the percent fix, OFF20 returns 20. Without rounding, 0.1 + 0.2 keeps the long decimal. Without `hasOwn`, `constructor` gives NaN. The previous step reported that all 5 new tests failed before the fix, and I have no reason to doubt that.

**Side effects checked.** Nothing else in the repo calls `total`. The output is always a finite number unless the input itself is NaN, and the clamp keeps it non-negative. The one behaviour change beyond the reported bugs is that percent coupons now take a percentage of the subtotal, which is the intended meaning of "20% off".

**Findings (ordered by severity).**
1. **Low / correctness (pre-existing, not a regression).** `Math.round(sum * 100) / 100` rounds binary-float halves the wrong way. For example, 1.005 × 100 = 100.49999999999999, so `total([{price:1.005,qty:1}])` returns 1 instead of 1.01. The report flagged this at medium. I rate it low because no customer example depends on it, and the fix belongs in a separate change using integer-cent arithmetic. Reproduce with `total([{ price: 1.005, qty: 1 }])`. Note that the expected value needs a business decision first.
2. **Low / test coverage.** The regression tests do not cover these cases:
   - a fixed coupon on a cart larger than its value (for example TENOFF on 15 should give 5);
   - a percent coupon on a non-round subtotal (for example OFF20 on 19.99 should give 15.99);
   - multi-item carts with a coupon;
   - `qty: 0`, negative price or quantity, and NaN inputs (these currently return NaN, which is not a clamp case).
3. **Low / hardening (beyond the report).** The coupon code is case-sensitive, so `tenoff` is silently ignored. This matches the original behaviour and the "unknown coupons are ignored" rule, so it is only worth noting.

**What remains unverified.**
- I did not run `npm test` or the regression tests, so the "7 pass" claim in the handoff is unconfirmed by me.
- I did not confirm the original-code failure counts by running the old file.
- I did not check the Node version installed in the environment.
