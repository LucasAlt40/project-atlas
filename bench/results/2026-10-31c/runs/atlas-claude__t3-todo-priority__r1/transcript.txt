## Architecture analysis and plan: todo priorities

**Scope.** Add a `priority` (`low` | `normal` | `high`) to todos. Changes: `store.add`, `store.list`, `formatList`, and tests. Out of scope: `complete`, the todo id scheme, the README (optional one-line note), and any CLI, since the repo has none.

### What the project looks like today
- `src/store.js`: `createStore()` closes over a private `todos` array and `nextId`. `add(title)` validates and pushes `{id, title, done}`. `list()` returns shallow copies in insertion order. There are no dependencies.
- `src/format.js`: `formatList(todos)` renders `[x] title` / `[ ] title`, one per line, in the order it receives.
- `test/store.test.js`: four tests using `node:test` and `assert`. The `format` test passes plain objects with no `priority` field, so a missing priority must render as normal.
- Baseline: `npm test` passes 4 of 4.

### Architectural impact
- The module boundary stays the same. The store owns data and ordering; the formatter only renders. Priority rules belong in the store, and the formatter reads only the `priority` field.
- The public contract grows in a backward-compatible way: `add` gets an optional second argument, and every todo gets one new field. Nothing existing breaks, provided no caller compares whole todo objects with deep equality (none in this repo).

### Decisions the Developer must follow
1. **Priority set in one place.** In `store.js`, define a single constant of the valid priorities and a rank map (`high` 0, `normal` 1, `low` 2). Use it for validation and sorting. Do not export it, and do not add a new module, because the task doesn't need one.
2. **`add(title, options = {})`.** Keep the title check first (`TypeError`). Then, if `options.priority` is `undefined`, use `'normal'`. Any other value that is not in the set throws `RangeError`. That includes `null`, `'HIGH'` and `'urgent'`. Stored todo: `{id, title, done, priority}`.
3. **`list(filter = {})`.**
   - With `filter.priority` set: return the todos with that priority, in insertion order. If the filter value is not a valid priority, throw `RangeError` (this is my choice; the spec is silent, and throwing avoids a silently empty list).
   - Without the filter: return a stable sort by rank, high first, then normal, then low. Insertion order is kept within each rank.
   - Sort a copy, never the internal `todos` array. The internal order is the insertion order and must stay that way.
   - Keep the copy-on-return behaviour (`{ ...t }`).
4. **`formatList`.** Render `high` todos as `[ ] !title` (and `[x] !title` when done). Render `normal`, `low`, and todos with no priority field exactly as before. Do not sort inside `formatList`; it renders in the order it is given.
5. **`complete` is unchanged.**

### Files and contracts to change
- `src/store.js`: `add` signature and validation, `list` filter and sort, and the `priority` field on each todo.
- `src/format.js`: the `!` prefix for `high`.
- `test/store.test.js`: keep the four existing tests unchanged, and add new tests (below).
- `README.md`: optional. One line noting that todos have priorities is enough.

### Tests to add (in `test/store.test.js`)
- `add` without options gives `priority: 'normal'`.
- Each valid priority is stored as given.
- Invalid priorities (`'urgent'`, `'HIGH'`, `null`, `42`) throw `RangeError`.
- `list({ priority: 'high' })` returns only high todos, in insertion order.
- An invalid filter priority throws `RangeError`.
- `list()` sorts high, normal, low. Within a rank the order is insertion order. Use a mixed insertion sequence such as low, high, normal, high, low to show stability.
- `list()` does not reorder the store: a later `list()` after an add still matches insertion order within each rank.
- `formatList` renders `'[ ] !Pay rent'` for high, plain `[ ] title` for normal and low, and `[x] !title` for a done high todo.
- `formatList` on todos without a priority field renders as before (the existing `format` test covers this; add an explicit assertion too).

### Risks
- A consumer that deep-equals whole todo objects will now see the extra `priority` field. None exist in this repo.
- Stability of `Array.prototype.sort` is guaranteed by ES2019, so the sort is safe on the Node version this repo uses. The stability test guards it.
- Sorting the internal array by accident would silently change insertion order for later calls. The copy-then-sort rule and the store-order test guard against this.

### Verification
- Run `npm test`. All four existing tests must still pass unchanged, plus the new ones.
- Read the diff against the list above to confirm that `complete`, ids and the copy-on-return behaviour are untouched.
