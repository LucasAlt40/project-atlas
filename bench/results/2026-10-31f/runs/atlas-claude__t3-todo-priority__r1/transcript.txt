## Plan: priorities for the todo store

**Goals.** Todos carry a `priority` of `low`, `normal` or `high`. `list` can filter by priority and sorts by priority when unfiltered. `formatList` marks high-priority todos with `!`. Existing behaviour and the four current tests stay unchanged.

**In scope.** `src/store.js`, `src/format.js`, `test/store.test.js`.
**Out of scope.** `complete`, the README (a one-line file, not part of the contract), and any new modules, exports or dependencies.

**Current architecture.** A zero-dependency CommonJS module. `createStore()` closes over a `todos` array and `nextId`. `format.js` is a pure function that only reads `done` and `title`. The two modules do not import each other, and `format.js` never sees the store. The change keeps it that way.

### Files and contracts

1. **`src/store.js`**
   - `add(title, options)`: keep the title check first. Then resolve priority: `undefined` becomes `'normal'`; any other value must be one of `'low' | 'normal' | 'high'`, otherwise throw `RangeError`. Validate *before* `nextId++` and before the push, so a rejected call leaves no partial state. The stored todo becomes `{ id, title, done, priority }`.
   - `list(filter)`: if `filter && filter.priority !== undefined`, keep only todos with that priority. Then sort a copy by rank `high=0, normal=1, low=2`. `Array.prototype.sort` is stable in Node, so ties keep insertion order. Still return copies.
   - Keep the valid-priority list as a local constant in `store.js`. Do not export it; nothing outside needs it.

2. **`src/format.js`**
   - Prefix `!` directly before the title when `t.priority === 'high'`. Todos with no `priority` field (such as the existing format test's objects) render exactly as before.

3. **`test/store.test.js`** (same style: `node:test` plus `node:assert`, one `test()` per behaviour)
   - Default priority is `'normal'`; an explicit priority is stored.
   - Invalid priority (`'urgent'`, `null`, `''`) throws `RangeError`, and the next id is not consumed.
   - `list({ priority: 'low' })` returns only low todos.
   - Unfiltered `list()` orders high, normal, low, with ties in insertion order.
   - `formatList` gives `[ ] !Pay rent` for high, and unchanged output for normal and low.

### Decisions for the Developer

- `undefined` means default; `null` is an invalid value and throws. This matches "any other value throws".
- Validate before any mutation.
- Filtering uses strict equality and no sorting beyond the rank above. Within a single priority, filtered and unfiltered results come out in the same order, so the spec is consistent there.
- Unknown `filter.priority` values: **assumed** to throw `RangeError`, to match `add`. The spec does not cover this. If the user prefers an empty result, only that branch changes.
- No new abstractions, no changes to `complete`, and no change to returned object shapes beyond the added field.

### Risks

- The implicit `filter` contract: passing a filter with other keys is ignored. Acceptable for now.
- Ordering depends on stable sort, which Node guarantees since v12. The test for ties guards it.
- `null` vs `undefined` for the default is the one easy place to get the behaviour wrong; the test covers it.
