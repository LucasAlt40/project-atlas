## Architecture & Code Validator: `src/users.js`

Read-only review. Nothing was modified. I could not execute the functions directly, because only the project's test commands are permitted here. Every finding below rests on reading the code. The one command I ran was `npm test`.

### Findings (most severe first)

**1. High, Security: `escapeHtml` does not escape all occurrences.** `src/users.js:18-20`
`String.prototype.replace` with a string pattern replaces only the first match. Only the first `<`, the first `>` and the first `&` are escaped. Input with a second `<` passes through as live markup. Example: `x<y<img src=x onerror=alert(1)>` becomes `x&lt;y<img src=x onerror=alert(1)>`, and the `<img>` tag is injected. `userRow` (line 25) passes user-controlled `user.name` through this function, so this is a stored or reflected XSS path into the users page. The doc comment at line 15 promises the output is "safe to put inside HTML", which it is not.
*Recommendation:* use a global regex with a character map, for example `String(text).replace(/[&<>"']/g, c => MAP[c])`, where `MAP` covers `& < > " '`. Escaping `&` first is not needed when a single pass with a map is used. Add `"` and `'` so the function is also safe in attribute contexts, since its doc promises general HTML safety.

**2. Medium, Conventions (contract mismatch): `paginate` treats pages as 0-based but its doc says 1-based.** `src/users.js:3-5`
The doc comment says "1 is the first page", but `start = page * size` makes page 1 start at index `size`. Calling `paginate(items, 1, 10)` returns items 10–19, silently skipping the first ten users. Page 0, which the code treats as the first page, is never documented. Page values below 1 are also not validated. Negative page numbers produce a negative `start`, and `slice` then counts from the end of the array, returning wrong rows without an error.
*Recommendation:* use `const start = (page - 1) * size;`. Validate that `page` and `size` are integers of at least 1 and throw a `RangeError` otherwise. Alternatively, if 0-based paging is intended, change the doc comment and validate `page >= 0`.

**3. Medium, Conventions (correctness): `isAdult` ignores month and day.** `src/users.js:11-12`
The function subtracts only the birth year from the current year. Someone who has not yet had their birthday this year is counted as already having reached that age. Example: `isAdult(new Date(2008, 11, 31), new Date(2026, 0, 1))` returns `true` (2026 − 2008 = 18), but the person is 17. The doc comment at line 9 says "18 or older on `today`", which the code does not implement. If this is used to gate age-restricted content, it lets underage users through for up to a year.
*Recommendation:* compute the age accounting for the birthday, for example: `let age = today.getFullYear() - birthDate.getFullYear(); const m = today.getMonth() - birthDate.getMonth(); if (m < 0 || (m === 0 && today.getDate() < birthDate.getDate())) age--; return age >= 18;`. Compare in local time consistently with how `birthDate` is built.

**4. Medium, Testing: no tests for any exported function.** Whole project (`npm test` run)
`npm test` runs `node --test` and reports `tests 0`. The three defects above are all in functions with no coverage, so nothing catches them. The package declares a test script but has no test files.
*Recommendation:* add `test/users.test.js` using `node:test`. Include cases for page 1 returning the first slice, page 0 and negative pages being rejected, `escapeHtml` on input with several `<`, `>` and `&` characters, `isAdult` on the day before and the day of the 18th birthday, and `userRow` for an admin and a non-admin user.

**5. Low, Maintainability: `userRow` renders `undefined` for a missing name.** `src/users.js:25`
If `user.name` is missing, `escapeHtml(undefined)` returns the string `"undefined"`, which is rendered in the table. There is no validation of the input shape.
*Recommendation:* validate the input or default the name to an empty string in the caller's contract.

### Verdict: **fail**

Findings 1 and 2 are defects that must be fixed before this module is accepted. Finding 1 is an XSS vulnerability and finding 2 is a silent data error. Finding 3 is a correctness error that should be fixed before the function is used for any access decision.
