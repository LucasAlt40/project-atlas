## Plan: priorities for the todo store

**What:** Each todo gets a `priority` of `'low' | 'normal' | 'high'`. `store.add` sets it, `store.list` filters and sorts by it, and `formatList` marks high-priority items with `!`.

**Baseline:** `npm test` passes 4 of 4 tests (`node --test`, CommonJS, no dependencies).

### Scope
- **In:** `src/store.js`, `src/format.js`, a new test file or additions to `test/store.test.js`.
- **Out:** Persistence, `complete()` semantics, the README, and any CLI. No such code exists in the repo.

### Current code the change touches
- `src/store.js:8-15`: `add(title)` validates the title, builds `{ id, title, done }` and pushes it to the `todos` array, which is kept in insertion order.
- `src/store.js:26-28`: `list()` maps over `todos` and returns shallow copies, in insertion order.
- `src/format.js:3`: `formatList` renders `[x] title` or `[ ] title`.
- `test/store.test.js:27`: the existing format test passes plain objects with no `priority` field, so the formatter must accept those.

### Decisions for the Developer
1. **Validation in `add`.** Change the signature to `add(title, options = {})`. Use `const priority = options.priority ?? 'normal'`, so `undefined` defaults to `'normal'`. Any other value that is not one of the three strings throws `RangeError`, including `null`, `''` and `'HIGH'`. Keep the existing `TypeError` for the title check and do it first.
2. **Stored shape.** Add `priority` to the object: `{ id, title, done, priority }`. Do not add other fields.
3. **Rank table.** Define one constant in `store.js`, e.g. `const PRIORITY_RANK = { high: 0, normal: 1, low: 2 }`. Use it both to validate (`Object.hasOwn(PRIORITY_RANK, p)`) and to sort. Do not duplicate the list of names.
4. **`list(filter)` behaviour.**
   - With `filter?.priority`, return only the todos with that priority. Keep insertion order.
   - Without a filter, return everything sorted by rank.
   - Sorting must be stable within a priority. `Array.prototype.sort` is stable in Node 12 and later, and the input is already in insertion order, so `[...todos].sort((a, b) => rank(a) - rank(b))` gives the required order. Do not sort the internal `todos` array in place.
   - An unknown `filter.priority` throws `RangeError`, the same as `add`. This is my choice; the task does not specify it. Returning an empty list would hide typos.
5. **Keep copies.** `list()` must keep returning copies, so callers cannot mutate store state.
6. **Formatter.** In `formatList`, a todo with `priority === 'high'` renders as `[ ] !Pay rent`. A missing or other priority renders as before. Keep the existing one-line-per-todo format and the `[x]`/`[ ]` marker.
7. **Behaviour change to note.** A no-filter `list()` now returns high before normal before low. The existing tests use only default priorities, so they are unaffected.

### Files and contracts
- `src/store.js`: `add(title, options)` gains `priority` validation and storage. `list(filter)` gains filtering and sorting. The return shape gains `priority`.
- `src/format.js`: `formatList` gains the `!` prefix for high priority.
- `test/store.test.js` or a new `test/priority.test.js` (the runner picks up both under `node --test`): add tests for the new behaviour.

### Tests to add
- `add` without options gives `priority: 'normal'`.
- `add` with each of `low`, `normal`, `high` stores that value.
- `add` with `'urgent'`, `null` or `'HIGH'` throws `RangeError`, and the store is left unchanged.
- `add` with an empty title still throws `TypeError`.
- `list()` sorts high, then normal, then low, and keeps insertion order within each priority.
- `list({ priority: 'low' })` returns only low todos, in insertion order.
- `list({ priority: 'bogus' })` throws `RangeError`.
- `list()` returns copies: mutating a returned item does not change the store.
- `formatList` gives `[ ] !Pay rent` for high and unchanged output for normal and low, and still works on objects without `priority`.
- Existing tests keep passing unchanged.

### Risks
- Changing the order of no-filter `list()` is a visible change. It is required by the task, but any caller relying on insertion order will see a difference.
- A non-stable sort would break the within-priority order. Node's sort is stable, so this is low risk, but the test above covers it.
- `formatList` receives plain objects, not store objects. It must not assume `priority` exists.
