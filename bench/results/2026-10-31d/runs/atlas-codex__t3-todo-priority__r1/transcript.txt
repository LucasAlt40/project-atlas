## Goal

Add priority-aware behavior while preserving the existing CommonJS API, title validation, completion behavior, insertion semantics, and tests.

## Scope

In scope:

- `store.add(title, options)` with `low`, `normal`, and `high` priorities.
- Default priority of `normal`.
- `RangeError` for invalid priorities.
- Priority filtering and default priority ordering in `store.list`.
- High-priority rendering in `formatList`.
- Tests covering all new behavior and existing compatibility.

Out of scope:

- New modules, dependencies, persistence, CLI changes, or README changes.
- Changes to completion semantics or todo IDs.
- Formatting changes for non-high priorities.

## Architecture and dependencies

The project has two small boundaries:

- `src/store.js`: owns mutable in-memory todo state, IDs, validation, filtering, and ordering.
- `src/format.js`: pure presentation logic; it receives todo-shaped objects and returns text.

`test/store.test.js` is the current integration-level contract for both modules. There are no runtime dependencies; tests use Node’s built-in runner.

The architectural impact is limited to the todo data contract: every todo returned by the store will gain a `priority` field. The formatter should remain independent of the store and only inspect `priority === 'high'`.

## Developer decisions to follow

- Preserve `store.add('title')` by treating omitted options as an empty options object.
- Store the normalized title and a priority on every todo; omitted priority becomes `'normal'`.
- Validate priority before inserting the todo. Invalid values must throw `RangeError` and must not mutate the store.
- Keep the internal insertion array unchanged. `list()` should return copies and apply filtering/sorting to the returned view.
- Use explicit priority ranking `high > normal > low`.
- Preserve insertion order among equal-priority todos. Do not rely on mutating the stored array or on incidental ordering.
- `list(filter)` should filter only when `filter.priority` is supplied; no filter preserves the new default priority ordering.
- `formatList` should add `!` only for high-priority todos. Missing or non-high priority remains rendered in the existing format, preserving the current formatter test.

## Files and contracts to change

- `src/store.js`
  - Extend `add` to accept `options`.
  - Add the `priority` field to created todos.
  - Extend `list` to accept an optional filter and return priority-filtered or priority-sorted copies.
  - Keep `complete` unchanged.

- `src/format.js`
  - Change title rendering so high-priority todos render as `[ ] !Title` or `[x] !Title`.
  - Keep all other output unchanged.

- `test/store.test.js`
  - Add tests for default priority and explicit valid priorities.
  - Add tests that invalid priorities throw `RangeError` without adding a todo.
  - Add tests for filtering.
  - Add tests for high-first ordering and insertion order within a priority.
  - Add formatter coverage for high and non-high priorities.
