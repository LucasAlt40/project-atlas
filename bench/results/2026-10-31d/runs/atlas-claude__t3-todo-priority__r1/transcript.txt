## Plan: todo priorities in `src/store.js` and `src/format.js`

**Baseline:** `npm test` (`node --test`) passes all 4 existing tests.

### Goals
- `store.add(title, options)` accepts `options.priority` ∈ {`low`, `normal`, `high`}, defaults to `normal`, and throws `RangeError` for any other value. The priority is stored on the todo as `priority`.
- `store.list(filter)` filters by `filter.priority` when given. Without a filter it sorts high → normal → low, and keeps insertion order within each priority.
- `formatList` prefixes high-priority titles with `!` (`[ ] !Pay rent`). Other priorities render exactly as today.
- Existing behaviour and the four existing tests stay unchanged.

### In scope / out of scope
- In: `src/store.js` (`add`, `list`), `src/format.js` (`formatList`), `test/store.test.js` (new cases).
- Out: `complete`, persistence, ids, the `done` flag, any new module, any change to `README.md` beyond what is needed (none is needed; the README documents no API).

### Architecture and dependencies
- The store is a closure over a private `todos` array, and every read returns copies (`list()` maps with `{ ...t }`). Keep both properties: the sort must run on a copy, never on the internal array, so callers cannot reorder the store and the array stays in insertion order.
- Sorting belongs in the store's `list()`, not in `formatList`. `formatList` renders the order it is given; it should not re-sort. This keeps presentation separate from the data contract.
- `format.js` has no dependencies and will not import from `store.js`. It checks `t.priority === 'high'` as a literal. The existing `format` test passes objects with no `priority` field, so the check must treat `undefined` as non-high. Do not add a shared constants module for three strings; that is an abstraction the task does not need.
- The only caller of `list()` in the repo is the test file, so the new default sort order has no other consumers to break.

### Decisions the Developer must follow
1. **Validation** lives in `add`, after the existing title check. Only `options.priority === undefined` means "default to `normal`". `null`, `''`, `'HIGH'`, numbers and other non-matching values throw `RangeError`. Title validation still throws `TypeError` first.
2. **`options` defaults:** signature `add(title, options = {})`, so `add('a')` still works.
3. **Rank table** in `store.js`, e.g. `const PRIORITY_RANK = { high: 0, normal: 1, low: 2 };`. Use it for both validation (`in` check) and sorting.
4. **Sorting** is stable: copy the array with `map`, then `sort((a, b) => PRIORITY_RANK[a.priority] - PRIORITY_RANK[b.priority])`. `Array.prototype.sort` is stable in Node ≥ 12, so insertion order within a priority is kept. Do not add an insertion index field.
5. **Filter** signature `list(filter = {})`. If `filter.priority` is present and not one of the three values, throw `RangeError`, to match `add` and avoid silently returning an empty list for a typo. Filtered results are returned in insertion order (filtering before sorting is fine; a single priority sorts to insertion order anyway).
6. **`formatList`** keeps its one-line `map`. Add the marker only for `high`:
   `` `[${t.done ? 'x' : ' '}] ${t.priority === 'high' ? '!' : ''}${t.title}` ``
7. **Tests** go into `test/store.test.js`, next to the existing ones, so they follow the file's current layout (the format test lives there too).

### Files to change
- `src/store.js`: `add(title, options = {})` with priority validation and `priority` on the todo; `list(filter = {})` with filter, validation and stable sort; a `PRIORITY_RANK` constant.
- `src/format.js`: the `!` marker for high-priority todos.
- `test/store.test.js`: new tests (below). Existing tests are not edited.

### Test plan (`node --test`, via `npm test`)
- Default priority is `normal` when `add('a')` or `add('a', {})` is called.
- Each valid priority is stored on the todo (`priority` field matches).
- Invalid priorities (`'urgent'`, `null`, `'HIGH'`, `1`) throw `RangeError`. Title still throws `TypeError` for empty input.
- `list()` without a filter sorts high, normal, low, with insertion order kept within each group. Use mixed adds such as low-a, high-b, normal-c, high-d, low-e → [high-b, high-d, normal-c, low-a, low-e].
- `list({ priority: 'high' })` returns only high todos, in insertion order. Unknown filter priority throws `RangeError`.
- `list()` still returns copies: mutating a returned todo does not change the store.
- `formatList` shows `[ ] !Pay rent` for high, and `[ ] a` / `[x] a` for normal and low, with the existing `format` test still passing.

### Risks
- **Changed order of `list()`:** intentional, but any caller relying on insertion order for mixed priorities will see a different order. Only the test file calls it today.
- **Strict validation of `filter.priority`:** throwing is a choice; if the Developer or user prefers an empty result for unknown filters, change decision 5 and its test together.
- **`formatList` depends on the literal `'high'`:** a rename in `store.js` would have to be mirrored in `format.js`. Acceptable for a three-value field; covered by the format test.
