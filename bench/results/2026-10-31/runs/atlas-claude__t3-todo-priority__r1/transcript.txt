## Plan: priorities for the todo store (`src/store.js`, `src/format.js`)

**Goal:** add a `priority` field (`'low' | 'normal' | 'high'`, default `'normal'`) to todos, filter and sort `list()` by it, and mark high-priority rows with `!` in `formatList`. Existing behaviour and the four current tests must keep passing.

**Baseline:** `npm test` (`node --test`) passes 4/4 on the untouched code.

### What is in and out of scope

- **In:** `store.add` option handling and validation, `store.list(filter)` filtering and ordering, `formatList` rendering, and new tests in `test/`.
- **Out:** `complete()`, persistence (the store is in-memory), changing the `list()` return shape beyond adding `priority`, and changing the README. The README is three lines and does not document the API, so I would leave it alone unless you ask.

### Modules and dependencies

- `src/store.js` is self-contained: a closure over `todos` and `nextId`, no imports. All the new logic lives here.
- `src/format.js` depends only on the todo shape (`title`, `done`). It needs one comparison, `t.priority === 'high'`. It should not import from `store.js`, so the two modules stay decoupled.
- There are no other consumers in the repo. The only callers are the tests.
- Architectural impact is low. The change adds an optional parameter and a field, and nothing existing is removed.

### Decisions the Developer must follow

1. **Validation in `add`.** Accept `options` as an optional object. If `options.priority` is `undefined`, use `'normal'`. Otherwise it must be one of the three strings, or throw `RangeError`. Non-strings such as `null`, `1` or `'HIGH'` also throw. Validate the title and the priority before pushing, so a failed call leaves no partial state. Keep the existing `TypeError` for titles.
2. **Ordering in `list()`.** Keep `todos` in insertion order. Build the returned copies and stable-sort them by rank (`high`=0, `normal`=1, `low`=2). Since `Array.prototype.sort` is stable in Node, ties keep insertion order without an extra sequence number. Keep the `{ ...t }` copies.
3. **`list(filter)` signature.** `filter` is optional, so `list()` and `list(undefined)` both work. When `filter.priority` is set, return only todos with that priority, in insertion order. An invalid `filter.priority` throws `RangeError`, matching `add`. This is my recommendation; the spec does not cover it, so say if you want an empty array instead.
4. **`formatList` output.** For `priority === 'high'`, the line is `[ ] !Title` or `[x] !Title`. Every other case, including a missing `priority` field, renders exactly as before. Treating missing as non-high keeps the existing `format` test valid without changes.
5. **Style.** Match the file's current style: plain `function`s, no new dependencies, no separate constants module. A `const PRIORITY_RANK = { high: 0, normal: 1, low: 2 }` object inside `store.js` is enough, and `Object.hasOwn` or a `has`-style check is fine for validation.

### Files to change

- `src/store.js`: `add(title, options = {})` validates and stores `priority`. `list(filter = {})` filters and sorts.
- `src/format.js`: the `!` prefix for high-priority todos.
- `test/store.test.js`: add new `test(...)` blocks. The file covers both modules, so I would extend it rather than create a new file. The existing tests stay unchanged.

### Tests to add

- `add` defaults `priority` to `'normal'`. Explicit `'low'`, `'normal'` and `'high'` are stored.
- `add` with an invalid priority (`'urgent'`, `'HIGH'`, `null`, `1`) throws `RangeError`, and the list is unchanged afterwards.
- `list()` orders high, then normal, then low, and keeps insertion order within each priority.
- `list({ priority: 'low' })` returns only low todos, in insertion order. A filter with an invalid priority throws `RangeError`.
- `list()` and `list(undefined)` still return all todos (covered by the existing `add and list` test, plus one explicit case).
- `formatList`: a high todo renders as `[ ] !Pay rent`, and a done high todo renders as `[x] !Pay rent`. Normal and low todos render as before, and a todo without a `priority` field renders as before.

### Risks

- **Mutating the wrong array:** sorting `todos` in place would reorder insertion history. The sort must run on the copied array.
- **Lenient validation:** accepting `null` or other values as "default" would violate "any other value throws". The `undefined`-only default avoids that.
- **Filter validation is a judgement call.** Throwing and returning an empty array are both defensible. I recommend throwing so typos are caught.

### How the result will be verified

- `npm test` must pass all existing tests unchanged, plus the new ones.
- Read the diff against the decisions above. Confirm `complete()` and the `TypeError` path are untouched.
