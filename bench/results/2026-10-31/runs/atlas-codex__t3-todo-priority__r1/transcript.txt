## Goal

Add priority semantics to the todo store and formatter while preserving all existing behavior and tests.

## Scope

In scope:

- `store.add(title, options)` with `low`, `normal`, and `high` priorities.
- Default priority of `normal`.
- `RangeError` for invalid priority values.
- Persisting `priority` on every todo.
- `store.list(filter)` priority filtering and default priority ordering.
- High-priority formatting with `!` before the title.
- Tests covering defaults, validation, filtering, ordering, stability, and formatting.

Out of scope:

- Persistence, new modules, API redesign, CLI changes, README changes, or changes to completion/title behavior.
- Validation of `filter.priority`, since the task only requires validation for `add`.

## Architecture and dependencies

- `src/store.js` owns todo state, ID allocation, mutation through `complete`, and defensive copies returned by `list`.
- `src/format.js` is a pure presentation function and should remain independent of store internals.
- `test/store.test.js` is the existing test boundary and already covers both modules.
- There are no runtime dependencies; tests use Node’s built-in runner.

The change is localized to the existing store model and presentation format. No new abstraction is needed.

## Developer decisions

1. Extend `add` to accept an optional options object, defaulting to `{}`.
2. Use `normal` when `options.priority` is omitted.
3. Validate supplied priorities against the exact set `low`, `normal`, `high`; throw `RangeError` otherwise.
4. Store `priority` directly on each todo, including todos created with the default.
5. Keep the internal insertion array in insertion order. Implement default listing by sorting a copied result using priority rank `high > normal > low`, with insertion order as the tie-breaker.
6. When `filter.priority` is present, return only matching todos and preserve their insertion order; do not apply default priority sorting to filtered results unless the existing contract requires it.
7. Keep `list` defensive: callers receive copied todo objects and sorting/filtering must not reorder internal state.
8. In `formatList`, prepend `!` only when `t.priority === 'high'`; missing priority remains visually unchanged for backward compatibility with existing callers/tests.

## Files and contracts

- `src/store.js`
  - Change `add(title)` to `add(title, options)`.
  - Add priority validation/defaulting.
  - Add `priority` to todo objects.
  - Change `list()` to `list(filter)` with filtering and default ordering.
  - Preserve title validation, IDs, completion, and copied results.

- `src/format.js`
  - Update the rendered title prefix to produce `[ ] !Pay rent` for high-priority todos.
  - Preserve existing output for normal, low, and priority-less todo objects.

- `test/store.test.js`
  - Extend/add tests for:
    - default `normal` priority;
    - explicit valid priorities;
    - invalid priority throwing `RangeError`;
    - high-first ordering;
    - insertion order within equal priorities;
    - `filter.priority`;
    - priority field preservation through `complete`/`list`;
    - high-priority formatting and unchanged formatting for other priorities.

## Verification

Run the existing test suite with `npm test` and confirm all original and new tests pass. The tests should also verify that filtering and sorting do not mutate the store’s insertion order or alter existing title/completion behavior.

Architectural impact is low: one domain-field extension, one query-ordering rule, and one presentation rule within existing module boundaries.

## Architectural impact and decisions

The change remains within the existing in-memory store boundary. No new abstraction is justified.

The Developer must:

1. Preserve the internal insertion-order `todos` array.
2. Add `options = {}` handling so omitted options default cleanly.
3. Validate priority before creating or inserting a todo. Invalid values must throw `RangeError`; failed additions must not consume an ID or mutate the store.
4. Store `priority` on every todo, including legacy-style calls without options.
5. Keep `list()` defensive by returning copied todo objects.
6. Implement filtering before or alongside ordering so `list({ priority })` returns only matching todos.
7. Order unfiltered results by `high`, `normal`, `low`, while preserving insertion order within each priority. Use an explicitly stable approach rather than relying on incidental sort behavior.
8. Preserve existing behavior for `complete(id)`, title trimming, invalid titles, and empty lists.
9. Keep formatting backward-compatible for objects without a priority field: only an explicit `high` priority adds `!`.

The main architectural risk is accidentally mutating the store’s insertion order during listing or sorting. Listing must operate on a copied array/result so subsequent calls and completion behavior remain predictable. A second risk is inconsistent priority handling between creation, filtering, ordering, and formatting; the same three literal values should be used consistently.

## Files and contracts

- `src/store.js`
  - Change `add(title)` to accept `options`.
  - Add `priority` to the todo object.
  - Change `list()` to accept an optional filter and apply priority ordering/filtering.
- `src/format.js`
  - Change the rendered title expression so high-priority todos render as `[ ] !Title` or `[x] !Title`.
- `test/store.test.js`
  - Add tests for:
    - default priority;
    - each accepted priority;
    - invalid priority throwing `RangeError`;
    - high/normal/low ordering;
    - insertion-order preservation within a priority;
    - priority filtering;
    - high-priority formatting;
    - unchanged formatting for normal/low and existing objects.
