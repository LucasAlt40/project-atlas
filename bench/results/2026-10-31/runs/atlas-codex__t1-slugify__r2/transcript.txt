# Slugify Module and Tests

## Goals

Add a dependency-free CommonJS `slugify(text, options)` utility with:

- Lowercasing and diacritic removal.
- Non-alphanumeric runs normalized to one `-`.
- No leading or trailing separators.
- Optional word-aware `maxLength` truncation.
- `TypeError` for non-string input.
- Node built-in tests covering normal, Unicode, boundary, truncation, and validation cases.

## Scope

In scope:

- `src/slugify.js`
- `test/slugify.test.js`

Out of scope:

- Changes to `package.json`, `README.md`, or test configuration.
- New dependencies, shared abstractions, browser integration, or unrelated utilities.

## Architecture and dependencies

This is a deliberately small package with one module boundary:

- `src/slugify.js`: standalone pure transformation function; no project dependencies.
- `test/slugify.test.js`: black-box tests using `node:test` and `node:assert`.

The package already declares `"type": "commonjs"` and uses `node --test`, so the implementation must use:

```js
module.exports = { slugify };
```

No additional abstraction is justified for this scope.

## Implementation decisions

The Developer must:

1. Validate `typeof text === 'string'` before processing and throw `TypeError` otherwise.
2. Normalize Unicode using canonical decomposition, then remove combining marks.
3. Lowercase before applying the allowed-character rule.
4. Replace each run outside `[a-z0-9]` with one hyphen, then trim boundary hyphens.
5. Treat `options.maxLength` as optional; when present it must be a positive integer.
6. For truncation:
   - Return the full slug when it fits.
   - Prefer the longest complete hyphen-delimited prefix that fits.
   - If the first word itself exceeds the limit, hard-cut that first word.
   - Never return a trailing hyphen.
7. Preserve the exact export contract and avoid mutating inputs.

The task does not specify behavior for invalid `options.maxLength` values such as zero, negatives, non-integers, or `NaN`. This is a minor contract ambiguity. The implementation should reject them with `TypeError` or `RangeError` consistently, and tests should document that choice; no architectural change is required.

## Files and contracts

- `src/slugify.js`
  - New CommonJS module.
  - Public contract: `{ slugify }`.
  - Function contract: `slugify(text, options?) -> string`.

- `test/slugify.test.js`
  - New built-in Node test suite.
  - Must cover the supplied examples and the edge cases above.

## Architectural impact and risks

Impact is isolated to a new leaf module; there are no existing consumers or dependency edges to update.

Primary risks:

- Unicode normalization may leave combining marks unless explicitly removed.
- Truncation can accidentally split a later word or leave `-`.
- A naive regex may mishandle repeated punctuation or whitespace.
- Ambiguous invalid `maxLength` behavior could become an undocumented edge-case contract.


Tests should verify all supplied examples, Unicode conversion, punctuation runs, empty/ separator-only input, first-word hard truncation, word-boundary truncation, exact-length results, and non-string input errors. Only the two requested files should appear in `git status`.
