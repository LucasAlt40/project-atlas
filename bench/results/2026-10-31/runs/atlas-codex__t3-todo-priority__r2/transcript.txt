## Plan: Add todo priorities

### Goals

- Add validated `low`, `normal`, and `high` priorities to stored todos.
- Preserve existing title validation, completion behavior, IDs, and API compatibility.
- Sort unfiltered results by priority while preserving insertion order within each priority.
- Support priority filtering.
- Render high-priority todos with `!`.
- Extend existing tests without adding dependencies or abstractions.

### Scope

In scope:

- `src/store.js`: `add(title, options)` and `list(filter)`.
- `src/format.js`: high-priority rendering.
- `test/store.test.js`: tests for defaults, validation, sorting, filtering, and formatting.

Out of scope:

- Persistence, new modules, CLI changes, README changes, or changes to completion semantics.
- Validation of option shapes beyond the specified priority values.
- Reordering internal storage; ordering should be applied to list results.

### Modules and dependencies

- `src/store.js` owns todo state, IDs, mutation, and list projection.
- `src/format.js` is a pure presentation function and should remain independent of the store.
- `test/store.test.js` uses Node’s built-in `node:test` and `node:assert`.
- There are no runtime or development dependencies.

### Architectural impact and risks

The store’s todo contract gains a required `priority` field, defaulting to `normal`. `list()` must return copied todo objects as it does today, so sorting and filtering must operate on a copied/result array without mutating internal insertion order.

The main risks are:

- Invalid priorities accidentally being accepted or silently normalized.
- A sort implementation that changes insertion order for equal priorities.
- Existing formatter callers passing objects without `priority`; those must continue rendering unchanged.
- Adding unnecessary option validation that expands the API beyond the requested contract.

### Decisions the Developer must follow

1. Treat omitted or priority-less options as `normal`.
2. Throw `RangeError` for any explicitly supplied priority other than `low`, `normal`, or `high`.
3. Store `priority` on every todo returned by `add` and `list`.
4. For unfiltered `list()`, return all todos in `high`, `normal`, `low` order, preserving original insertion order within each group.
5. For `list({ priority })`, return only todos matching that priority; use the same priority validation rules if filter validation is needed by the implementation.
6. Do not mutate the internal `todos` array while sorting or filtering.
7. Keep `formatList` backward-compatible: prepend `!` only when `t.priority === 'high'`; missing or non-high priorities retain the current output.
8. Reuse the existing object shape and test style; do not introduce a priority enum, separate module, or sorting abstraction.

### Files and contracts to change

  - Extend `add` to accept options and assign `priority`.
  - Extend `list` to accept an optional filter and produce the specified ordering/filtering.
  - Update the list comment to describe priority ordering.

## Architecture and dependencies

The project has two small boundaries:

- `src/store.js`: in-memory domain state and todo lifecycle. It owns IDs, title validation, mutation via `complete`, priority validation, filtering, and ordering.
- `src/format.js`: pure presentation logic. It should inspect todo data but not alter or sort it.
- `test/store.test.js`: integration-level contract tests using Node’s built-in test runner.

There are no runtime dependencies. The implementation should reuse the current CommonJS style and avoid introducing a priority class, separate repository, or shared abstraction.

## Architectural impact

Priority becomes part of the todo domain model. The store’s internal insertion order remains authoritative for ties, while `list()` produces a sorted copy for callers. Filtering and sorting should not mutate the internal `todos` array.

The formatter remains backward-compatible: only `priority === 'high'` changes output, so existing callers or fixtures that omit `priority` continue to render as before.

## Decisions for the Developer

- Keep `add('title')` valid and default omitted `options` and omitted `options.priority` to `'normal'`.
- Accept only `'low'`, `'normal'`, and `'high'` for an explicitly supplied priority; throw `RangeError` for anything else.
- Store `priority` on every newly created todo, including the default `'normal'`.
- Implement `list(filter)` as a non-mutating operation returning shallow copies.
- With `filter.priority`, return only exact matches. Without a filter, order by `high`, then `normal`, then `low`.
- Preserve insertion order among equal-priority todos.
- Format high-priority todos as `[ ] !Title` or `[x] !Title`; leave other priorities unchanged.
- Retain the current title trimming and validation behavior.
- Do not alter `complete()` semantics.
