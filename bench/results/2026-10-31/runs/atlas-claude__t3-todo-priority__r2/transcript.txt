## Plan: priorities for the todo store

**Goal:** Each todo gets a `priority` of `'low' | 'normal' | 'high'` (default `'normal'`). `store.list()` returns todos sorted high, normal, low, with insertion order kept within each level. `store.list({ priority })` filters. `formatList` prefixes high-priority titles with `!`.

**In scope:** `src/store.js`, `src/format.js`, `test/store.test.js`. The README is a one-line description with nothing to update.

**Out of scope:** `complete()`, changing a todo's priority after creation, persistence (the store is in-memory), a CLI, and a new file or module for priorities.

### Current state (what I read)
- `src/store.js` (`createStore`): `add(title)` validates the title, pushes `{ id, title, done }` into a closure-local `todos` array, and returns the object. `complete(id)` mutates in place. `list()` returns shallow copies in insertion order.
- `src/format.js`: `formatList(todos)` maps each todo to `[x]` / `[ ]` plus the title. It has no dependency on the store.
- `test/store.test.js`: four `node:test` tests (add/list, complete, empty title, format). They use `require('../src/...')` and `assert`. `package.json` has no dependencies and `"test": "node --test"`.

### Steps
1. **`src/store.js`**
   - Define one constant in the module: a rank map `{ high: 0, normal: 1, low: 2 }`. Its keys are also the valid priorities.
   - `add(title, options)`: take the priority with destructuring, `const { priority = 'normal' } = options ?? {};`. The default applies only to `undefined`, so `null` or `'urgent'` reaches the check and throws `RangeError`. Store `priority` on the todo object next to `id`, `title` and `done`.
   - `list(filter)`: if `filter?.priority` is set, validate it with the same `RangeError` check, then keep the todos with that priority. Otherwise sort a copy of the array by rank. `Array.prototype.sort` is stable, so equal ranks keep insertion order. Sort a mapped copy so the internal `todos` array is never reordered.
2. **`src/format.js`**: prefix the title with `!` when `t.priority === 'high'`. Todos without a `priority` field, as in the existing format test, render exactly as before.
3. **`test/store.test.js`**: keep the four existing tests unchanged and add:
   - default priority is `'normal'`;
   - explicit `'low'` and `'high'` are stored;
   - invalid values (`'urgent'`, `'High'`, `null`, `3`) throw `RangeError`;
   - `list()` orders high, normal, low, and within a level keeps insertion order;
   - `list({ priority: 'low' })` returns only low todos;
   - `list()` still returns copies, and the internal order is unchanged after a sorted `list()`;
   - `formatList` gives `[ ] !Pay rent` for high and unchanged output for the other priorities.

### Decisions for the Developer
- **Validation lives in the store.** `formatList` does not validate priority and does not import from the store. It only checks `=== 'high'`.
- **Invalid filter priority throws `RangeError`** instead of returning an empty list. This matches `add` and makes typos visible. The spec does not say this, so it is my choice; I'd flag it for review.
- **Sort copies, never the internal array.** Sorting in place would change `list()` order for everyone and is the easiest way to break the insertion-order rule.
- **Keep `filter` optional.** `list()` and `list({})` both return the sorted full list.
- **No new abstractions.** One rank constant inside `store.js`, no classes, no new modules, no new dependencies.

### Files and contracts
- `add(title, options?)` → todo `{ id, title, done, priority }`. `options` may be omitted.
- `list(filter?)` → copies, sorted by priority unless `filter.priority` is given.
- `formatList(todos)` → unchanged signature. Output changes only for `priority === 'high'`.

### Risks
- **Sort stability:** this relies on Node's stable `Array.prototype.sort` (Node 12+). `node --test` needs Node 18+, so that holds.
- **Null options:** `add('x', null)` will go through the `??` fallback and default to `'normal'`. If the project wants that to be a `TypeError`, say so.
- **Mutable output:** `list()` returns copies, so a caller who modifies `priority` on the returned objects does not change the store. This is the existing behaviour and stays as it is.

- Run `npm test` (`node --test`) from the worktree. All four existing tests must still pass, and the new tests must pass.
- Review the diff to confirm `src/store.js` does not call `sort` on `todos` directly.
