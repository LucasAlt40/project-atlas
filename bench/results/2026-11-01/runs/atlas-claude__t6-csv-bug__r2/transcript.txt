## Verification report: parseCsv fix (pass 1)

**Verdict: pass.** The fix removes the cause. The regression tests cover the reported bugs. The only issues I found are low-severity edge cases for the person to decide on.

**Root cause.** The original `parseCsv` (`bcabb3b:src/csv.js`) split the text on `\n` and then on `,` before looking at quotes. It only stripped quotes when a field both started and ended with `"`. So quoted commas, doubled quotes, quoted line breaks, CRLF and the trailing newline all failed, and an unclosed quote never raised an error. The reported symptoms come from this one design flaw.

**Fix applied (`eeb0556`, the committed tree is clean).** `src/csv.js` is now a single-pass scanner with `inQuotes` and `fieldStart` state. A quote opens a quoted field only at field start. Inside quotes, `""` becomes `"`, a lone `"` closes the field, and commas and line breaks are literal. Outside quotes, `\n` and `\r\n` end a row. At the end, a row is emitted only if it has content, so a trailing newline adds nothing, and an unclosed quote throws `SyntaxError`. The export is still `module.exports = { parseCsv }`.

**Validation evidence**
- *Executed:* `npm test` (`node --test`) gives 10 pass, 0 fail.
- *Read:* each reported bug traced through the scanner.
  - `"Lisbon, Portugal",2`: the comma is inside quotes, so it is kept.
  - `"say ""hi"""`: `""` inside quotes becomes one `"`.
  - `a,b\nc,d\n`: the final branch is skipped because `fieldStart` is true and the row is empty.
  - `a,b\r\n`: `\r` followed by `\n` is one break, so no `\r` is left in the field.
  - `"line1\nline2"`: the newline is inside quotes, so the field continues.
  - `"abc` and `a,"b\nc`: the end check throws.
- *Read, regression tests:* against the original code, seven new tests should fail, matching the handoff's "7 failing". I worked this out from the old code, not by running it. The "empty fields" and "quoted field without specials" tests pass on both versions, so they guard against regression rather than prove the fix.
- *Read, side effects:* the only caller of `parseCsv` in the repo is `test/csv.test.js`. The return shape is unchanged for well-formed input, which is what the existing tests check.
- *Read, edge cases traced:* `""` gives `[['']]`; `,` gives `[['', '']]`; `"a"""` gives `a"`; `"a""` throws; `""` followed by a comma gives an empty first field; a quote inside an unquoted field (`a"b`) is kept literally.

**Low-severity findings (for the person to decide)**
1. A lone `\r` (old Mac line endings) is kept as a literal character. RFC 4180 does not require handling it.
2. A UTF-8 BOM at the start of the file stays in the first field. Windows-saved files often have one.
3. Text after a closing quote is appended without a separator (`"a"b` gives `ab`). This follows the stated decision, but nothing tests it.
4. Whitespace before an opening quote (` "a,b"`) makes the quotes literal and splits the field at the comma. This is RFC-consistent, but many real files have it.
5. Blank lines inside the file give a row with one empty field (`a\n\nb` gives `[['a'],[''],['b']]`). The old code did the same. The spec does not say what to do.
6. Test gaps: no tests for `""""`, `"a""`, CRLF at end of file without a trailing newline, a stray quote in an unquoted field, text after a closing quote, blank lines, a lone `\r`, or a bare `,` or `\n`.

**Could not verify**
- I could not run ad hoc inputs against the code. Read-only mode allows only the project's test commands, so the edge-case results above come from reading the code.
- I could not run the regression tests against the original code to confirm the seven failures. That would mean changing the working tree.
- Behaviour on the BOM, lone `\r` and blank lines is only traced by reading, not run.
