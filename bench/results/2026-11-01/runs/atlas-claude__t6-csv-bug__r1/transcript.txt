## QA verdict: pass

The fix removes the cause. The original parser split on `\n` and then on `,`, so it could not see quotes spanning those characters. The new code in `src/csv.js` scans characters once and tracks quote state, so it handles all five reported bugs and the unclosed-quote error. `npm test` passes 11/11. I found no high or medium issues. The remaining items are low severity and listed below for you to decide.

**Root cause.** `parseCsv` was line-based and not quote-aware. The original code (`git show 0f02d75:src/csv.js`) did `text.split('\n')`, then `line.split(',')`, then stripped quotes only when a field both started and ended with `"`. That produced the comma split, the doubled-quote bug, the extra row from a trailing newline, the leftover `\r` from CRLF, the cut at embedded line breaks, and the silent acceptance of an unclosed quote.

**Fix applied (commit b78f9a7, `Atlas: step exec-2`).** `src/csv.js` is now a single-pass state machine.
- Quotes open a field only at its start (`:20`). Inside quotes, `""` becomes `"` (`:12`).
- Commas and LF end a field and a row (`:23`, `:27`). CRLF is treated as a row end, and a bare `\r` before a non-LF is kept as data (`:33`).
- An input that ends inside quotes throws `SyntaxError` (`:41`).
- A final row is kept only if it has content, a field, or a quoted marker (`:45`). This avoids a phantom row after a trailing newline and keeps `""` as one empty field.
- `module.exports = { parseCsv }` is unchanged.

The working tree is clean, so the diff is in the commit, not the index.

**Validation evidence**
- *Executed:* `npm test` gives 11 pass, 0 fail. This includes the 8 new regression tests and the 2 original ones.
- *Read:* I traced the 8 regression tests against the original code at `0f02d75`. Tests 3–8 (comma, doubled quote, trailing newline, CRLF, embedded LF, embedded CRLF), 10 (empty input) and 11 (unclosed quote) each fail there. Tests 1, 2 and 9 pass on both versions; test 9 is a guard.
- *Read:* I traced edge inputs by hand against the new code. `""` gives `[['']]`. `a,"b"""` gives `a,b"`. `"a""` throws. `\n` gives `[['']]`, the same as before. `a,b\n` gives no extra row.
- *Read:* `parseCsv` has no other callers in the repo (grep). The README only describes `node --test`.

**Not verified**
- I could not run the new tests against the original code. That would need a checkout or file edits, which read-only mode does not allow. The "fails on original" result is from reading the code.
- I could not run ad-hoc Node scripts for edge cases, so those results come from reading the code, not execution.
- I could not run a regression test in isolation. `npm test` runs the whole suite, which is fine for this project.

**Low-severity findings (outcome stays pass)**
- *Coverage:* No test for `""` as the whole input, which should give `[['']]` and depends on the `quoted` flag at `:45`. Removing that flag would not fail any current test.
- *Behaviour:* A quote after other text is literal (`ab"c"` gives `ab"c"`). Text after a closing quote is appended (`"a"b` gives `ab`). Both are lenient, not RFC-strict. This matches the handoff's note.
- *Behaviour:* Blank lines give `['']` rows, as the original did. RFC 4180 does not define them. You may want them skipped.
- *Hardening:* A UTF-8 BOM at the start of a Windows-saved file makes a leading quoted header field keep its quotes (`\uFEFF"Name"`). This is outside the reported bugs.
- *Behaviour:* A trailing lone `\r` at end of input stays in the last field. This follows the documented decision that only CRLF is a line break, and no test covers it.
