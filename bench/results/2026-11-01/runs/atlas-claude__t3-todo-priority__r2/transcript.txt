## Plan: priorities for the todo store

**Goals**
- `store.add(title, options)` accepts `options.priority` of `'low' | 'normal' | 'high'`, defaulting to `'normal'`. Any other value throws `RangeError`.
- `store.list(filter)` supports `filter.priority`. With no filter, todos are sorted high, normal, low, and keep insertion order within each priority.
- `formatList` prefixes high-priority titles with `!`, so `[ ] !Pay rent`.
- Existing behaviour and the four existing tests in `test/store.test.js` stay unchanged.

**Out of scope**
- Changing `complete`, title validation, or the README. The README is two lines and documents no API.
- Persistence. The store is in memory, so there is no migration.
- New modules, classes, or abstractions.

**Current state (verified by reading)**
- `src/store.js`: `createStore()` holds a `todos` array in insertion order. `add(title)` validates the title and builds `{ id, title, done }`. `list()` returns shallow copies in insertion order.
- `src/format.js`: `formatList(todos)` maps each todo to `[x] title` or `[ ] title`.
- `test/store.test.js` uses `node:test`. Its `format` test passes plain `{ title, done }` objects with no `priority` field.
- `package.json` has `"test": "node --test"`.

**Design decisions for the Developer**
1. **Priority table in `src/store.js`.** Define one table, for example `const PRIORITY_RANK = { high: 0, normal: 1, low: 2 }`. Use it for validation, the default, and sort order. Don't scatter string literals.
2. **Validate with an own-property check.** Use `Object.prototype.hasOwnProperty.call(PRIORITY_RANK, value)`, not `value in PRIORITY_RANK`. The `in` form accepts `'toString'` and `'constructor'`. Values are case-sensitive, so `'High'` throws.
3. **Default applies only to `undefined`.** `options` may be omitted, so default it to `{}`. `options.priority === undefined` becomes `'normal'`. `null` and every other non-allowed value throw `RangeError`. This is a judgement call the spec does not settle; flagging it in the final report.
4. **Sort is explicit and stable.** Sort a copy with `(a, b) => PRIORITY_RANK[a.priority] - PRIORITY_RANK[b.priority]`. `Array.prototype.sort` is stable in Node, so ties keep insertion order. Sort a copy, never the internal `todos` array, so the stored order is untouched.
5. **Filter behaviour.** `list({ priority })` validates the value with the same check and throws `RangeError` on an invalid one. This is also a judgement call, for consistency with `add`. It then returns the matching todos in insertion order. Without a filter, `list()` returns the full sorted copy. A filter with no `priority` key behaves like no filter.
6. **Each todo stores `priority`.** `add` creates `{ id, title, done, priority }`. Shallow copies from `list` keep the field.
7. **Format tolerates a missing priority.** In `src/format.js`, test `t.priority === 'high'`, not the store's constants. Keep `format.js` free of imports from `store.js`, so the two modules stay decoupled. Todos without a `priority` field render as before, which keeps the existing `format` test passing. The `!` goes after the checkbox and space: `[ ] !title`, and `[x] !title` for a done high-priority todo.

**Files to change**
- `src/store.js`: the priority table, the `add` signature and validation, the `priority` field, and the `list(filter)` sort and filter.
- `src/format.js`: the `!` prefix for high priority.
- `test/store.test.js`: new tests. Keep the existing four unchanged.

**Tests to add**
- `add` defaults to `'normal'`. Each of `'low'`, `'normal'`, `'high'` is stored.
- `add` throws `RangeError` for `'urgent'`, `'High'`, `null`, `'toString'`.
- `list()` sorts high, normal, low, and keeps insertion order within each group, using mixed insertions.
- `list({ priority: 'high' })` returns only high todos in insertion order. An invalid filter value throws `RangeError`.
- `list()` returns copies, so mutating a result does not change the store.
- `formatList` prefixes `!` for high, both open and done. It leaves normal and low unchanged. Todos without `priority` render as before.

**Risks**
- Existing `list()` callers now get sorted output. The only current test that checks order (`add and list`) uses two `normal` todos, so it is unaffected. Callers that relied on insertion order now see a different order when priorities are mixed. This is what the spec asks for.
- Hidden coupling from the literal `'high'` in `format.js`. Accepted to keep modules decoupled; a shared constant would add an import for one string.
