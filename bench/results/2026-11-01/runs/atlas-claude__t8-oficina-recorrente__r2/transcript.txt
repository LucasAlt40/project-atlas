## Root cause: confirmed

`PaymentGatewayService.updatePaymentStatus` (`src/main/java/.../pagbank/service/PaymentGatewayService.java:166-200`) never creates a payment for a recurring charge. Every webhook takes `payments.getLast()` and overwrites that row's date and status. So September's charge rewrites August's row: the date moves to September, which is why August disappears from the listing, and a declined September charge also changes August's status.

Evidence:
- The only `paymentService.insert` call is at checkout (`application/DonationApplication.java:88`), so no code path ever adds a row for a later charge.
- `SELECT_PAYMENTS_BY_DONATION` (`infra/payment/repository/PaymentQueryBuilder.java:16-20`) has no `ORDER BY`, so "last" is not well defined either.
- Running the new regression test against the unmodified code reproduced it: 2 of 6 tests fail. The September DECLINED charge calls `updatePaymentDate` and `updateStatus` on August's row (`07ebe317…`) and never inserts. A repeated PAID notification in the same month also rewrites the existing row's date.

## Fix

In `updatePaymentStatus`, the payment row is now chosen by rule instead of "last row":
- **Recurring:** if a PAID payment already exists for the current calendar month, the notification is ignored for payment rows. Otherwise it updates the current month's payment, or the WAITING checkout payment if there is no current-month row. If neither exists, it inserts a new payment.
- **One-time:** the WAITING payment is updated, or the last one as before. Nothing new is ever inserted.
- Method, card brand, fee and sponsorship activation run as before.

I chose "same calendar month, server time" as the cycle boundary. That is my interpretation; the request didn't define it.

## Residual risks

- **Subsequent-charge payload not confirmed.** The only fixture (`webhook.json`) contains `recurring.type = INITIAL`. The fix assumes PagBank sends a non-null `recurring` on later charges. If it sends null, those charges are treated as one-time and the bug persists.
- **Existing data is not repaired.** Rows already overwritten by the bug (August rows with September dates) stay as they are; there's no migration.
- **`cancelCheckout` still runs on each PAID webhook** (`PaymentGatewayService.java` `notifyPayment`). It is outside this fix, but a PagBank error on an already-inactive checkout would fail the webhook after the payment update.
- **Cycle boundary is server local time.** A charge notified on the 1st of the next month is attributed to that month.

Please run `mvn test -Dtest=PaymentGatewayServiceTest` on a normal machine and confirm 6 passing.

## Verification report: per-month payment fix (commit `0ed6528`)

**Verdict: pass with conditions.** The fix removes the cause by reading the code, but I could not run the regression test in this sandbox. The fix's effect also depends on a PagBank payload I could not confirm from the repo.

I changed no files. The working tree is clean, and the fix is committed in `0ed6528` rather than left in the worktree.

### Root cause
`updatePaymentStatus` always wrote to `payments.getLast()`, updating its date and status. It never inserted a row for later charges, so each recurring charge overwrote the previous month's row. The original code is at `0ed6528^`, `PaymentGatewayService.java` lines 169–206.

### Fix applied
- **Recurring charges** (`recurring` non-null): the service looks for a row whose date falls in the current calendar month, then falls back to the `WAITING` checkout row. If neither exists, it inserts a new row (`PaymentGatewayService.java:215–243`).
- **Duplicate guard:** if the current month already has a `PAID` row, the notification is logged and ignored (`:181`, `:245–248`).
- **One-time donations:** prefer the `WAITING` row, otherwise `getLast()`. This never inserts (`:234–236`).
- **Unchanged:** method, card brand, fee, and sponsorship activation.

### Traced by reading (not executed)
- **Each of the 6 tests against the code.** Tests 1 and 3 fail on the original code, as the handoff said. The other four pass on both versions. Tests 2, 4, and 6 are one-time or first-charge guards that also pass on the original code. Constructor arguments for `SponsorshipDto`, `UserDto`, `PaymentDto`, and `ResponseWebhookCustomer` match, and `PaymentStatusEnum` contains `IN_ANALYSIS`. `updatePaymentDate` is not overloaded, so `any()` is unambiguous. I did not compile the file.
- **Repository and service calls.** `PaymentService.insert` returns the id that the service uses. The checkout creates a single `WAITING` row with a null date (`DonationApplication.java:87–88`). Only the checkout and the gateway service write payment rows.
- **`updateMethod`.** It is called twice in `updatePaymentStatus`. The original code did this too, so it is not a regression.

### Not verified
- **The recurring flag on later charges.** The fix only runs for later charges if PagBank's subsequent-charge webhook has a non-null `recurring`. The repo's `webhook.json` has 35 samples, all `"recurring":{"type":"INITIAL"}` and none for a later charge. If later charges omit the field, they take the one-time path and the bug remains.
- **The regression test run.** `mvn test -Dtest=PaymentGatewayServiceTest` failed before any test ran. Maven could not write `target/classes` (`Operation not permitted` in the sandbox).
- **Concurrency and time-zone handling** of `payment_date`. No schema file was in `src/main/resources`, so I could not check the column type.

## Final report

**Root cause:** `updatePaymentStatus` always updated the last row in the payment list, and never inserted a row for a new recurring charge. Each new charge therefore overwrote the previous month's date and status.

**Fix (commit `0ed6528`):** recurring charges now match the current calendar month, fall back to the `WAITING` checkout row, and otherwise insert a new row. A `PAID` row in the current month blocks duplicates. One-time donations keep the update path and never insert.

**Evidence:**
- Read: the diff, the original file, the six tests traced against the code, DTO constructors, the SQL in `PaymentQueryBuilder`, and the `webhook.json` samples.
- Executed: `mvn test -Dtest=PaymentGatewayServiceTest` was blocked by the sandbox before any test ran. This is not a test result.

**Findings, by severity:**
1. **High, unverified:** the fix depends on subsequent-charge webhooks carrying a non-null `recurring` (`PaymentGatewayService.java:365`). The 35 samples in `webhook.json` are all `INITIAL`. Confirm with a real PagBank subsequent-charge notification, and add a `notifyPayment` test that sets `recurring` on the charge.
2. **Medium, verification:** the regression test has not been run in this step. Run `mvn test -Dtest=PaymentGatewayServiceTest` on a machine where Maven can write `target/`.
3. **Medium, leftover:** `target/test-classes/mockito-extensions/org.mockito.plugins.MockMaker` contains `mock-maker-subclass`, forcing a workaround mock maker for every test run. I did not delete it because the mode is read-only. It is not tracked by git. Delete it and re-run the test.
4. **Medium, concurrency:** `updatePaymentStatus` (`:169`) is not transactional, and its check-then-insert is not locked. Two webhooks for the same month handled at the same time could both insert a row. No test covers this.
5. **Medium, ordering:** `SELECT_PAYMENTS_BY_DONATION` has no `ORDER BY` (`PaymentQueryBuilder.java:16–20`). `getLast()` at `:235` therefore has no defined order. The original bug may have been partly caused by this too.
6. **Medium, same bug pattern:** `updateCheckoutStatus` still writes to `payments.getLast()` (`:259`, `:285`). After a September row exists, a checkout notification can change September's row. This is outside the fix's scope.
7. **Low, flow:** `notifyPayment` calls `cancelCheckout` on every `PAID` charge (`:378–381`). If PagBank rejects inactivating an inactive checkout, the webhook fails after the row is written, and PagBank may retry. The original code had the same path.
8. **Low, behaviour change:** the one-time path now prefers the `WAITING` row over `getLast()` (`:235`). Normal data gives the same result. A repeated one-time `PAID` notification still rewrites that row's date, which the tests do not check.
9. **Low, data:** existing rows already overwritten by the bug are not repaired. A data fix is still needed for affected donations.
10. **Low, coverage:** no test covers a cross-month first charge left as `IN_ANALYSIS`, or a September `DECLINED` row later updated to `PAID`. The tests use `LocalDateTime.now()` separately from the service, so a test run at a month boundary could flake.

**Decisions for the person:**
- Whether PagBank's subsequent-charge payload carries `recurring`. This decides whether the fix works in production.
- Whether to repair the rows already overwritten.
