# Plan: todo priorities

**Goal.** Todos carry a `priority` of `'low'`, `'normal'` (default) or `'high'`. `store.list()` returns high, then normal, then low, with insertion order kept within each level. `store.list({ priority })` filters. `formatList` prefixes high-priority titles with `!`.

**In scope**
- `src/store.js`: `add` accepts and validates priority. `list` accepts a filter and sorts.
- `src/format.js`: `!` marker for high-priority todos.
- `test/store.test.js`: new cases for the behaviour above.

**Out of scope**
- `complete()`, which needs no change.
- Persistence and any CLI. The repo has neither.
- Sorting inside `formatList`. It renders in the order it receives, so ordering stays in the store.
- `add` returning the internal object reference. This is existing behaviour and is kept.

**Modules, dependencies and architectural impact**
- `store.js` and `format.js` have no dependencies. The test imports both.
- The only contract change is that a todo gains a `priority` field. `formatList` reads only `title` and `done`, so existing callers are unaffected.
- Keep the rules where they belong. Validation, ordering and filtering live in the store. The `!` marker is presentation and lives in `format.js`.

**Decisions the Developer must follow**
1. **Constants (store.js, module-level, not exported):** `const PRIORITIES = ['low', 'normal', 'high']` for validation, and a rank map `{ high: 0, normal: 1, low: 2 }` for sorting.
2. **`add(title, options = {})`:** validate `title` first, keeping the existing `TypeError`. Then resolve priority with `options.priority === undefined ? 'normal' : options.priority`. Do not use `??`: it would turn `null` into `'normal'`, but the spec says any value other than the three must throw. If the value is not in `PRIORITIES`, throw `new RangeError(...)`. Store it as `priority` on the todo object.
3. **`list(filter = {})`:**
   - Build a copy first, `todos.map((t) => ({ ...t }))`, as now.
   - If `filter.priority !== undefined`, validate it against `PRIORITIES` and throw `RangeError` if invalid (my choice, see below). Then filter to that priority.
   - Sort with `sort((a, b) => RANK[a.priority] - RANK[b.priority])`. `Array.prototype.sort` is stable in every supported Node version, so insertion order holds within a level.
   - Never sort the internal `todos` array in place. That would destroy the insertion order that later ties depend on.
4. **`format.js`:** `const bang = t.priority === 'high' ? '!' : '';`, rendered as `` `[${t.done ? 'x' : ' '}] ${bang}${t.title}` ``. Todos without a `priority` field, like those in the existing format test, render exactly as before.
5. **Tests:** add cases to the existing `test/store.test.js`. Do not create a new file.

**Files and contracts**
- `src/store.js`: `add(title, options?)` gains an optional `options`. `list(filter?)` gains an optional `filter`. Both return the same shapes as before, plus `priority` on each todo.
- `src/format.js`: `formatList(todos)` signature unchanged.
- `test/store.test.js`: new test cases, the existing four unchanged.

**Test cases to add**
- `add` without options gives `priority: 'normal'`. `add` with `'low'` and `'high'` stores them.
- `add` with `'urgent'`, `'HIGH'`, `null`, `1` throws `RangeError`.
- Order: add low a, normal b, high c, normal d, high e. `list()` titles are `[c, e, b, d, a]`.
- `list({ priority: 'normal' })` returns only normal todos, in insertion order.
- `list({ priority: 'urgent' })` throws `RangeError`.
- Calling `list()` twice after a filtered call still returns insertion order. This guards against the in-place sort.
- `formatList`: a high todo renders `[ ] !Pay rent`, and `[x] !a` when done. Normal and low render as before.

**Risks and how they are handled**
- In-place sort corrupting insertion order: handled by copying before sorting, and covered by a test.
- `null` silently defaulting: handled by the `=== undefined` check, and covered by a test.
- Invalid filter value: my choice is to throw `RangeError`, to match `add`. The alternative is an empty result. The spec does not say; this is easy to change if you prefer it.
- Stability of `sort`: guaranteed since ES2019 and Node 12, so no workaround is needed.

**Verification.** Run `npm test` (`node --test`). All four existing tests and the new cases must pass. Nothing else in the repo needs checking.
