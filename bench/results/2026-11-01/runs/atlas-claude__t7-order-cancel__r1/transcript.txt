The task spans three modules (`orders`, `inventory`, `reports`) plus the event contract and the test suite. The design has real ordering and consistency decisions, though the codebase is small. I did not implement anything; this is the analysis and plan.

## Plan: order cancellation

**Baseline:** `npm test` passes 3/3 (`place takes stock and announces`, `not enough stock takes nothing`, `reports`).

### Goals
- `orders.cancel(orderId, reason)` cancels a placed order, returns stock, sets `status: 'cancelled'`, keeps `reason`, and emits `order.cancelled` once with `{ orderId, reason }`.
- Error contract: invalid `reason` → `TypeError`; unknown id → `Error` containing "not found"; already cancelled → `Error` containing "already cancelled". Each failure changes nothing (no stock move, no event).
- `reports.revenue()` and `reports.unitsSold(sku)` exclude cancelled orders.
- Existing behaviour and the three existing tests stay unchanged.

### Out of scope
- Partial cancellation, cancelling by any other route, refunds or payment handling (there is no payment module).
- Changes to `events.js`. The bus is synchronous and has no API changes needed.
- Changes to `place`, `get`, `all` semantics. `all()` keeps returning cancelled orders; reports is what filters them.
- A `README` update beyond what the tests document (optional, see decisions).

### Current structure and dependencies
- `src/shop.js` wires `createBus`, `createInventory`, `createOrders({ inventory, bus, prices })` and `createReports({ orders })`. Nothing else must change in wiring: `createOrders` already receives `inventory` and `bus`.
- `src/orders.js` holds orders in a `Map` keyed by numeric id. `get` and `all` return copies. `place` takes stock, records the order, emits `order.placed`.
- `src/inventory.js` exposes `quantity` and `take` only. There is **no way to return stock**, so cancellation needs a new method.
- `src/reports.js` reads only through `orders.all()`. It has no notion of status today.
- Dependency direction is clean (`orders → inventory, bus`; `reports → orders`). The change keeps it that way.

### Decisions the Developer must follow
1. **Inventory gets a `restore(sku, qty)` method** next to `take`, adding `qty` back to the stock map. It mirrors `take` and does not validate beyond that (the order was already valid when placed). No other inventory behaviour changes.
2. **Check order in `cancel`:** (a) validate `reason` (`typeof reason === 'string' && reason.trim() !== ''`, else `TypeError`); (b) look up the order (missing → "not found"); (c) if `status === 'cancelled'` → "already cancelled". Only after all checks pass: restore each item's stock, set `status = 'cancelled'` and `reason` on the stored record, then emit. Validation before any mutation is what makes "changes nothing" hold.
3. **Mutate the stored record in place** (the `Map` value), with `reason` as a new field on the order. Return a deep copy in the same shape as `get` (`{ ...order, items: items.map(copy) }`), so callers cannot mutate internal state.
4. **Event emitted exactly once, after state changes**, with payload exactly `{ orderId, reason }` (no `total`), so the existing `order.placed` payload is not reused.
5. **Filtering lives in `reports.js`**, not in `orders.all()`. Both `revenue` and `unitsSold` skip orders with `status === 'cancelled'`. Keeping `all()` unfiltered means the orders module stays a faithful record.
6. **Tests go into `test/shop.test.js`**, reusing the `setup()` helper and the `node:test`/`assert` style. No new test file or framework.

### Files to change
- `src/inventory.js`: add `restore(sku, qty)`.
- `src/orders.js`: add `cancel(orderId, reason)` to the object returned by `createOrders`.
- `src/reports.js`: add a `status !== 'cancelled'` filter in `revenue` and `unitsSold`.
- `test/shop.test.js`: add tests (below).
- Not touched: `src/events.js`, `src/shop.js`, `package.json`.

### Test plan (added to `test/shop.test.js`)
- Cancel returns stock: place then cancel → `inventory.quantity` restored, returned order has `status: 'cancelled'` and the reason.
- Event: `order.cancelled` fires exactly once with `{ orderId, reason }`.
- Unknown id throws `Error` matching `/not found/`; no event, no stock change.
- Double cancel throws `Error` matching `/already cancelled/`; stock is not restored twice; no second event.
- Empty / whitespace / non-string reason throws `TypeError`; the order stays `placed` and stock is unchanged.
- Reports: after cancelling one of two orders, `revenue()` and `unitsSold(sku)` count only the remaining order.
- Existing three tests pass unchanged.

### Verification
- `npm test` must show the 3 existing tests plus the new ones passing, with 0 failures.
- Read-through check: every failing path must occur before any call to `inventory.restore`, `bus.emit`, or any write to the stored order.

### Risks and trade-offs
- **Partial state on listener failure:** `bus.emit` is synchronous. If an `order.cancelled` listener throws, the cancellation has already happened and the error propagates to the caller. `place` has the same property. Accepted for consistency; the Developer should not add rollback.
- **Two places must agree on "cancelled"** (the filter in reports and the status string in orders). Acceptable at this size; a shared constant or helper is unnecessary abstraction for two lines.
- **Numeric ids:** `orders.get` uses the `Map` with numeric keys, so `cancel('1')` returns "not found". This matches existing `get` behaviour; the Developer should not coerce types.
- **Not verified here:** no existing test or doc describes cancelled orders, so the exact `reason` field name on the order is my choice (`reason`). Revisit if the user wants a different shape.
