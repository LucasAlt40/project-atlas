## Plan: todo priorities in `src/store.js` and `src/format.js`

**Baseline:** `npm test` passes all 4 existing tests.

### Goals
- `store.add(title, options)` accepts `options.priority` of `'low'`, `'normal'` or `'high'`. It defaults to `'normal'` and throws `RangeError` for anything else.
- Each todo stores `priority`.
- `store.list(filter)` filters by `filter.priority` when given. Without a filter it sorts high, normal, low, and keeps insertion order within a priority.
- `formatList` renders high-priority todos as `[ ] !Title`. Other priorities render as before.
- Existing tests keep passing, and new tests cover the new behaviour.

### Out of scope
- Changing `complete`, the title validation, or the `add` return value (it still returns the internal object, as today).
- Persistence, CLI, or README changes. The README is three lines and nothing in the task asks for it to change.
- Sorting or filtering by anything other than priority.

### Modules and dependencies
- `src/store.js` is the only module with state. `list()` already returns copies, so the sort and filter operate on copies and cannot leak internal state.
- `src/format.js` is a pure function of its input. It needs no new dependency. It reads `t.priority` and treats a missing field as "not high", so the existing `format` test (todos without `priority`) keeps its output.
- No dependencies are added. Node's built-in `Array.prototype.sort` is stable (ES2019+), so a rank-based sort keeps insertion order within a priority.

### Decisions for the Developer
1. **Ranking constant in `store.js`:** `const PRIORITY_RANK = { high: 0, normal: 1, low: 2 };`. Use it both for validation (`Object.hasOwn(PRIORITY_RANK, p)`, not `in`, so `'toString'` is rejected) and for sorting. Do not add a separate array of names.
2. **Defaults:** `add(title, options = {})`, then `const priority = options.priority === undefined ? 'normal' : options.priority`. Only `undefined` means "use the default". `null` and other values go to validation and throw `RangeError`. This follows the spec literally, which says "any other value throws".
3. **Filter validation:** `list(filter = {})`. When `filter.priority !== undefined`, validate it with the same `RangeError` rule. The spec does not state this, but an invalid filter silently returning `[]` would hide typos. This is a judgement call the user can redirect.
4. **Order of operations in `list`:** copy the todos, filter if a priority was given, then stable-sort by `PRIORITY_RANK[t.priority]`. The sort also runs on filtered results, which is harmless and keeps one code path.
5. **Case sensitivity:** `'High'` is invalid. The spec lists exact values.
6. **Todo shape:** `{ id, title, done, priority }`. Key order matches the existing object literal.

### Files and contracts
- `src/store.js`
  - `add(title, options = {})` now stores `priority` and throws `RangeError` for invalid values. The `TypeError` for titles is unchanged.
  - `list(filter = {})` returns copies, filtered and sorted as above.
- `src/format.js`
  - `formatList` produces `[x] !Title` or `[ ] !Title` when `t.priority === 'high'`, and the existing `[x] Title` / `[ ] Title` otherwise.
- `test/store.test.js`
  - Add tests for: default `normal`; explicit `low` and `high`; `RangeError` for `'urgent'`, `'High'` and `null`; `list({ priority: 'low' })` returns only low todos; no-filter order is high, normal, low; insertion order is kept within a priority; `list({ priority: 'urgent' })` throws; `formatList` shows `!` for high, shows no marker for normal or low, and formats a `done` high todo as `[x] !Title`.

### Risks
- **Behaviour change in `list()` order:** callers that relied on insertion order will now see high-priority items first. This is the requested change, so it is intentional. The existing `add and list` test uses only normal todos and stays valid.
- **`add` returns the internal object:** a caller can mutate `priority` on the returned object and bypass validation. This is pre-existing for `done` too, and fixing it is out of scope.
- **`null` priority:** `options.priority === undefined` is deliberately strict. Using `??` would silently turn `null` into `'normal'`, and that is the one design choice here that could go against what the user wants.

### Verification
- `npm test` (runs `node --test`). Expect the 4 existing tests plus the new ones to pass.
- Read the diff against this plan to confirm that `format.js` output for todos without `priority` is unchanged.
- No implementation was done in this step, so nothing was run beyond the baseline.
