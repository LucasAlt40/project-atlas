## Plan: todo priorities

### Goals
- `store.add(title, options)` accepts `options.priority` of `'low' | 'normal' | 'high'`, defaulting to `'normal'`. Any other value throws `RangeError`.
- `store.list(filter)` filters by `filter.priority` when given. Without a filter it returns todos sorted high, normal, low, with insertion order kept inside each priority.
- `formatList` prefixes high-priority titles with `!`, e.g. `[ ] !Pay rent`. Other priorities render as before.
- Existing behaviour and the existing tests in `test/store.test.js` stay unchanged.

### Out of scope
- Changing a todo's priority after creation (there is no setter or update API today).
- Changing `complete`, ids, or the `README.md` description. I'm not proposing a README change because the README describes the project, not its API.
- New modules, a new priority class, or a shared constants file. The task is small enough that these would be unnecessary abstractions.

### Modules and dependencies
- `src/store.js` is the only owner of priority validation and ordering. It has no dependencies.
- `src/format.js` is standalone and receives plain objects. It needs only the literal string `'high'`, so it does not need to import anything from the store.
- The architectural impact is confined to these two files and the test file. The store's public shape gains one field (`priority`) and one optional parameter on each of `add` and `list`.

### Decisions the Developer must follow
1. **One constant in `store.js`.** Define `const PRIORITIES = ['high', 'normal', 'low'];` at module level. Validate with `PRIORITIES.includes(p)` and rank for sorting with `PRIORITIES.indexOf(p)`. Do not create a separate map.
2. **Validation order in `add`.** Keep the existing title check first (it throws `TypeError`). Then resolve priority: `const priority = options.priority ?? 'normal'`, where `options` defaults to `{}`. Throw `RangeError` if `priority` is not in `PRIORITIES`. `null` and `undefined` should be handled deliberately: `undefined` means the default, and `null` is invalid and throws.
3. **Stored shape.** Each todo becomes `{ id, title, done, priority }`. `list()` still returns copies.
4. **`list(filter = {})`.**
   - If `filter.priority` is set, return only todos with that priority. For an invalid filter value I recommend throwing `RangeError`, matching `add`. This is a choice I'm making; the task did not specify it.
   - Always sort the returned copies by `PRIORITIES.indexOf`. The sort is stable on Node 12 and later, so the insertion order within a priority is preserved. A filtered result has a single priority, so sorting it changes nothing. Sorting unconditionally avoids a special case for "filter present vs. absent".
   - Sort the copies, not the internal `todos` array, so that insertion order is never lost.
5. **`formatList` in `src/format.js`.** Use `t.priority === 'high' ? '!' : ''` inserted before the title. Todos with no `priority` field (as in the existing `format` test) must still render without `!`, so do not require the field to exist.
6. **Tests go in `test/store.test.js`**, following the existing style (`node:test`, `assert`, one `test(...)` per behaviour). Leave the four existing tests untouched.

### Files to change
- `src/store.js`: `PRIORITIES` constant; `add(title, options)` with priority validation and default; `list(filter)` with filtering and stable sort.
- `src/format.js`: `!` prefix for `priority === 'high'`.
- `test/store.test.js`: new tests appended.

### Test cases to add
- `add` without options gives `priority === 'normal'`.
- `add` with each of `'low'`, `'normal'`, `'high'` stores that value.
- `add` with `'urgent'`, `''`, `null`, `'HIGH'` throws `RangeError`. Also check that `add('  ', {priority:'high'})` still throws `TypeError`, to confirm the order.
- `list()` without a filter sorts high, normal, low, and keeps insertion order within each group. Use mixed inserts, e.g. normal a, low b, high c, high d, normal e, and expect c, d, a, e, b.
- `list({ priority: 'low' })` returns only the low todos, in insertion order.
- `list({ priority: 'bogus' })` throws `RangeError` (if the recommended decision above is accepted).
- `formatList` with a high todo, done and not done, gives `[ ] !Pay rent` and `[x] !Pay rent`. A normal and a low todo show no `!`. A todo with no `priority` field shows no `!`.
- The existing `add and list`, `complete`, `empty title rejected` and `format` tests must still pass unchanged.

### Risks
- **Silent order change for existing callers.** Only todos created with the default `normal` exist today, so the sorted output equals the current insertion order. The change is visible only when a caller mixes priorities, which is the intended new behaviour.
- **Invalid `filter.priority` behaviour.** Throwing and returning an empty list are both defensible. The decision is above; the Developer should follow it or flag it.
- **`null` options.** `add(title, null)` would throw a `TypeError` on property access if handled carelessly. Default `options` with a `?? {}` guard, or treat `null` the same as missing, and keep it consistent in the tests.
