## Architecture plan: todo priorities

**Goal:** Add a `priority` (`low` | `normal` | `high`) to todos in `src/store.js`, use it for filtering and ordering in `store.list`, and show high-priority items with `!` in `src/format.js`. Existing behaviour and the current tests in `test/store.test.js` must keep passing.

**Current state (what I read):**
- `src/store.js` is a single closure (`createStore`) with an in-memory `todos` array and a monotonic `nextId`. `add(title)` validates the title and throws `TypeError`. `list()` returns shallow copies in insertion order. There are no dependencies.
- `src/format.js` exports `formatList`, which renders `[x]`/`[ ]` plus the title. It has no knowledge of the store.
- `test/store.test.js` uses `node:test` and covers add/list, complete, empty-title rejection and format. `npm test` runs `node --test`.

**In scope:** priority validation and storage, filtered and sorted `list`, the `!` marker in `formatList`, and tests for all of it.

**Out of scope:** changing `complete`, persisting todos, changing the `TypeError` for titles, a priority-setting API after creation, and any new module or abstraction. `README.md` is not part of this change.

**Modules and dependencies:** Both files stay independent. `format.js` keeps its single-argument, dependency-free design and checks the plain string `'high'`. It does not import from `store.js`, so the two modules stay decoupled. The valid priorities live in one constant inside `store.js`.

### Decisions for the Developer

1. **Valid priorities and rank.** In `store.js`, define `const PRIORITIES = ['high', 'normal', 'low'];`. The array index is the sort rank, so high sorts first. Validation is `PRIORITIES.includes(value)`.
2. **`add(title, options = {})`.** If `options.priority === undefined`, the priority is `'normal'`. Any other value that is not in `PRIORITIES` throws `RangeError`, including `null`, `''`, and non-strings. Only `undefined` means "use the default". Title validation runs first and is unchanged. The todo object becomes `{ id, title, done, priority }`.
3. **`list(filter = {})`.**
   - If `filter.priority` is `undefined`, there is no filter.
   - If it is set, validate it with the same rule and throw `RangeError` for an unknown value. This is my choice, since the spec is silent and throwing matches `add`. Returning an empty array would hide typos.
   - When filtering, return only todos with that priority.
   - Sort a copy with `[...todos].sort((a, b) => PRIORITIES.indexOf(a.priority) - PRIORITIES.indexOf(b.priority))`. `Array.prototype.sort` is stable in Node 12+, so todos with the same priority keep insertion order. Sorting a copy keeps the internal array untouched.
   - Keep returning shallow copies (`{ ...t }`) as today.
4. **`formatList`.** Render `[${mark}] ${bang}${t.title}`, where `bang` is `'!'` only when `t.priority === 'high'` and `''` otherwise. Todos without a `priority` field (like the existing format test input) render exactly as before.

### Files and contracts

- `src/store.js`: add the `PRIORITIES` constant, change `add` and `list`, and keep the existing signatures compatible (`add(title)` still works, `list()` still works).
- `src/format.js`: change one line in `formatList`.
- `test/store.test.js`: add tests. No existing test changes.
- `README.md`: no change.

### Tests to add (in `test/store.test.js`)

- Default priority is `'normal'` when `add('a')` or `add('a', {})` is used.
- An explicit `'low'`, `'normal'` or `'high'` is stored on the todo.
- `add('a', { priority: 'urgent' })`, `null` and `''` throw `RangeError`. Title validation still throws `TypeError`.
- `list()` sorts high, then normal, then low, and keeps insertion order within each group (use interleaved adds).
- `list({ priority: 'high' })` returns only high todos, in insertion order. Repeat for the other two priorities.
- `list({ priority: 'bogus' })` throws `RangeError`.
- `formatList([{ title: 'Pay rent', done: false, priority: 'high' }, { title: 'b', done: true, priority: 'low' }])` gives `'[ ] !Pay rent\n[x] b'`.
- The existing `add and list`, `complete`, `empty title rejected` and `format` tests still pass unchanged.

### Risks

- **Sort stability:** this relies on the stable `Array.prototype.sort` guarantee, which all supported Node versions provide. The within-priority order test covers it.
- **Invalid filter:** throwing for an unknown filter priority is a stricter contract than the spec states. If the user prefers an empty result, that is a one-line change.
- **Coupling:** `format.js` hardcodes `'high'`. That is acceptable for a single marker. Sharing the constant would couple the modules for little gain.
