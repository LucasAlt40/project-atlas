## Decisions for the Developer

1. **Slug pipeline.** Apply in this order: `toLowerCase()` → `normalize('NFD')` → strip `/[\u0300-\u036f]/g` (combining marks) → replace `/[^a-z0-9]+/g` with `-` → strip leading and trailing `-`. Use `options = {}` as the default parameter. Export exactly `module.exports = { slugify };`.
2. **`maxLength` validation (my choice, since the spec is silent).** Only validate when `options.maxLength !== undefined`. If the value is not a positive integer, throw `RangeError`. `TypeError` stays reserved for a non-string `text`, as the spec says.
3. **Truncation (`slug` already normalized, with no `--` runs):**
   - If `slug.length <= max`, return `slug`.
   - Otherwise let `head = slug.slice(0, max)`. If `slug[max] === '-'`, the cut is already on a word boundary, so return `head`.
   - Else let `i = head.lastIndexOf('-')`. If `i !== -1`, return `head.slice(0, i)`. Otherwise return `head` (hard cut).
   - Checked by hand against the examples: `'hello-big-world'` with max 9 → `'hello-big'`; with max 8 → `'hello'`; `'supercalifragilistic'` with max 5 → `'super'`. The `i !== -1` branch cannot produce a leading `-`, because the slug never starts with `-`.
4. **Known limitation, not a change.** Letters with no Unicode decomposition (`ß`, `ø`, `æ`, `ł`) are not in `a-z0-9`, so rule 3 turns them into `-` (for example `'straße'` → `'stra-e'`). This follows the spec literally; the Developer should not add transliteration tables.

## Files and contracts

  - a result never ends with `-` after truncation.
