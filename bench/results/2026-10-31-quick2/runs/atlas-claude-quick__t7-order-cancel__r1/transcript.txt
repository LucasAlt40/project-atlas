**Plan: order cancellation**

**Goal.** Add `orders.cancel(orderId, reason)` so that a placed order is cancelled, its stock is returned, the reason is kept, and `order.cancelled` is emitted. Reports must exclude cancelled orders. Existing behaviour and the three tests in `test/shop.test.js` must stay unchanged.

**Current state (what I read).**
- `src/orders.js`: `createOrders({ inventory, bus, prices })` keeps records in a `Map` and creates them with `status: 'placed'`. `place` emits `order.placed`. `get` and `all` return copies.
- `src/inventory.js`: only `quantity` and `take`. There is no way to put stock back.
- `src/reports.js`: `revenue()` and `unitsSold(sku)` both sum over `orders.all()` with no status filter.
- `src/events.js`: a synchronous bus. A handler that throws propagates to the emitter.
- `src/shop.js`: wires the modules together. It needs no change.
- `npm test` (`node --test`) runs 3 tests and all pass. This is the baseline.

**In scope.** `src/inventory.js`, `src/orders.js`, `src/reports.js`, `test/shop.test.js`.
**Out of scope.** `src/events.js`, `src/shop.js`, the `order.placed` payload, partial cancellation, cancellation of any status other than `placed`, persistence.

**Decisions for the Developer.**
1. **Inventory restock.** Add `inventory.put(sku, qty)`, the counterpart of `take`: it does `stock.set(sku, (stock.get(sku) ?? 0) + qty)`. Do not reuse `take` with negative quantities. `take` would accept them and bypass its check.
2. **Validation order in `cancel`.** Validate arguments first, then look up the order, then check state:
   - a `reason` that is not a string, or is empty after `trim()`, throws `TypeError`;
   - an unknown id throws `Error('order not found')`;
   - status `cancelled` throws `Error('order already cancelled')`.
   Validating `reason` first means a bad call never reports "not found". Whitespace-only is treated as empty. The reason is stored exactly as given, not trimmed.
3. **Mutate the stored record.** `cancel` finds the record in the `Map`, sets `status = 'cancelled'` and `reason`, restocks each item with `inventory.put`, emits `order.cancelled` with `{ orderId, reason }`, and returns a copy in the same shape `get` returns. Set the status only after all checks pass, so a rejected call changes nothing.
4. **Order of effects.** Restock, then set status, then emit. The emit comes last, as in `place`. Like `place`, an error thrown by a subscriber propagates after the state change; the bus has no rollback and I am not adding one.
5. **Reports.** Filter in `reports.js` (`o.status !== 'cancelled'`) in both `revenue` and `unitsSold`. Keep `orders.all()` returning every order, because it is the raw record. Do not add a second accessor, since nothing else needs one.
6. **Test location.** Append the new tests to `test/shop.test.js`, reusing its `setup()` helper. Use the same `node:test` and `assert` style.

**Files and contracts.**
- `src/inventory.js`: new `put(sku, qty)`.
- `src/orders.js`: new `cancel(orderId, reason)`. An order record gains a `reason` field only once cancelled. Event `order.cancelled` payload `{ orderId, reason }`.
- `src/reports.js`: both functions skip cancelled orders.
- `test/shop.test.js`: new tests.

**Tests to add.**
- Cancel a placed order: returns the order with `status: 'cancelled'` and the `reason`; stock for every item is restored; `order.cancelled` fires exactly once with `{ orderId, reason }`.
- Cancelling an unknown id throws an `Error` whose message contains "not found".
- Cancelling twice throws "already cancelled", and the second call leaves stock and the event count unchanged.
- An empty, whitespace-only, or non-string reason throws `TypeError`, and nothing changes (stock, status, no event).
- After cancelling, `revenue()` and `unitsSold(sku)` no longer count that order. Other orders still count.
- Regression: the three existing tests still pass unchanged.

**Risks.**
- Ids are numeric. `cancel('1')` will report "not found". This matches `get` and I am keeping it.
- A subscriber that throws after the state change leaves the order cancelled. This is the same as `place` today. It is a known limitation of the bus, not a new one.
- `put` has no upper-bound check. That is fine, since restocking can only add stock for an item that was previously taken.

**Verification.** Run `npm test`. The 3 existing tests and the new ones should pass. Read the diff to confirm the stored record is mutated only after all checks pass.

**Ambiguity.** The request does not say which error wins when the id is unknown and the reason is invalid. I chose `TypeError` first, and I list it under decision 2 so you can redirect it.
