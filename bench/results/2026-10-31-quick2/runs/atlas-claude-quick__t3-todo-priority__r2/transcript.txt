## Plan: todo priorities in `src/store.js` and `src/format.js`

**Goals**
- `store.add(title, options)` stores a `priority` of `'low' | 'normal' | 'high'`, defaulting to `'normal'`, and throws `RangeError` for anything else.
- `store.list(filter)` filters by `filter.priority` when given, and otherwise returns todos sorted high, normal, low, with ties kept in insertion order.
- `formatList` prefixes high-priority titles with `!` (`[ ] !Pay rent`). Other priorities render exactly as today.
- Existing behaviour and tests stay unchanged.

**Scope**
- In: `src/store.js`, `src/format.js`, `test/store.test.js`.
- Out: `complete`, persistence, a CLI, the README, and any new modules or dependencies.

**Current structure and dependencies**
- `createStore()` keeps `todos` as an in-memory array in insertion order, with `id` from a monotonic `nextId`. `list()` returns shallow copies, so callers cannot mutate the store.
- `format.js` has no imports and depends only on the `title` and `done` fields. The tests import both modules directly.
- Architectural impact is local. Public signatures gain optional parameters only, so no caller breaks.

**Decisions for the Developer**
1. **Priority set and rank live in `store.js`.** Define `const PRIORITIES = ['high', 'normal', 'low']` once. Validation is `PRIORITIES.includes(p)`, and the sort rank is `PRIORITIES.indexOf(p)`. Do not duplicate the list.
2. **`add` validation.** Keep the title check first and unchanged. Then read `const priority = options?.priority ?? 'normal'` (so `undefined` and missing options mean normal). Anything not in `PRIORITIES` throws `RangeError`. This includes `null`, `''`, and `'High'` (case-sensitive). Store `priority` on the todo object, after `done`.
3. **`list(filter)` semantics.**
   - With `filter?.priority` set, return only matching todos, as copies.
   - Also validate `filter.priority` and throw `RangeError` if it is not a valid priority. This is a judgement call: it matches `add` and avoids a silent empty result from a typo. The Developer should use this behaviour.
   - Sort with an explicit comparator `(rank(a) - rank(b)) || (a.id - b.id)`. Ids are monotonic, so this gives insertion order within a priority and does not rely on sort stability.
   - Filtered and unfiltered results share the same ordering code path. Within one priority the order is insertion order either way, so there is no output difference to decide.
4. **`formatList`.** Use `${t.priority === 'high' ? '!' : ''}${t.title}` in the template, so todos without a `priority` field (like the existing test fixture) render as before. The `!` goes after the checkbox and space and before the title, including for done high todos (`[x] !a`). `format.js` does not import the priority constant.
5. **Copies.** `list()` keeps returning copies via the spread, which already includes `priority`.

**Files to change**
- `src/store.js`: add `PRIORITIES`, extend `add` and `list`. Update the JSDoc comments to match.
- `src/format.js`: add the `!` prefix logic.
- `test/store.test.js`: add tests. Leave the four existing tests as they are.

**Tests to add (in `test/store.test.js`, same style)**
- Default priority is `'normal'`, and an explicit `{ priority: 'low' }` / `'high'` is stored.
- Invalid priority values (`'urgent'`, `'High'`, `null`, `''`) throw `RangeError`. Confirm that an invalid title still throws `TypeError`.
- `list()` without a filter sorts high, normal, low. Use mixed insertion order and check that ties keep insertion order.
- `list({ priority: 'low' })` returns only low todos, in insertion order. An invalid filter priority throws `RangeError`.
- `formatList` with a high todo gives `[ ] !Pay rent`. A done high todo gives `[x] !…`. Normal and low lines are unchanged. Keep the existing `format` test passing with a todo that has no `priority`.

**Risks**
- Low: `list()` now sorts on every call. The store is in-memory and small, so this does not matter for now.
- Low: the `list(filter)` argument is new. Making it optional keeps existing calls valid. The chosen `RangeError` for a bad filter is a new contract. Mention it in the README only if the Developer or reviewer wants it documented, which is out of scope here.
- Low: `options?.priority` needs optional chaining. This is fine on the Node version in use, but the Developer should confirm the Node version supports it.
