- Nothing tracked quote state, so an unclosed quote never raised an error.

All six share one cause: the parser split on lines and commas before handling quotes. I replaced that with a character scanner that tracks whether it is inside quotes. The existing `module.exports = { parseCsv }` is unchanged.

## Verification report

**Verdict: pass.** The fix removes the root cause, and the project suite passes. The remaining issues are edge-case behavior the bug reports don't cover.

**Root cause.** The original `parseCsv` (`git show a4764b0:src/csv.js`) split the text on `\n`, then on `,`, and only stripped quotes when a field both started and ended with `"`. It never tracked quote state, so quoted commas, doubled quotes, quoted line breaks and unclosed quotes were all handled wrongly. A trailing newline produced an extra row, and a `\r` before `\n` stayed in the last field. Those are the five reported symptoms, plus the empty-input and unclosed-quote cases.

**Fix applied (commit `0acac5d`).** `src/csv.js` is now a character-level scanner. It tracks whether it is inside quotes and handles `""` as an escaped quote. It treats CRLF as one row break, adds no row for a trailing newline, and throws `SyntaxError` on an unclosed quote. `module.exports = { parseCsv }` is unchanged. The working tree is clean, so the fix is already committed rather than pending as the handoff's "M" status suggested.

**Evidence**
- **Executed:** `npm test` gives 10 pass, 0 fail. This covers all the regression tests added in `test/csv.test.js:17-43`.
- **Read:** I traced each regression test against the pre-fix algorithm. Seven of them fail on the old code: Lisbon (3 fields), doubled quote (`say ""hi""`), trailing newline (extra `['']` row), CRLF (`b\r`), quoted line break (split into two rows), empty input (`[['']]` instead of `[]`), and unclosed quote (no throw). The empty-fields test already passed on the old code, so it guards against regression rather than covering a bug.
- **Read, side effects:** the only importer of `parseCsv` in the repo is `test/csv.test.js`. No other code depends on the old split behavior. The export shape is unchanged.
- **Read, edge cases:** `""` gives an empty field, `""""` gives `"`, `"""` throws, `a,` gives `['a','']`, and `""` alone gives `[['']]`. All match RFC 4180 as the scanner implements it.

**What I could not verify**
- I could not run ad-hoc inputs, because only the project test commands are allowed. The edge-case results above are from reading the code, not from execution.
- The fail-on-old-code claims are from tracing the old algorithm, not from running the old code.
- The lone-CR and `"a"b` behavior and the blank-line result are read from the code only.

**Decisions for the person**
- Whether classic Mac CR-only line endings must be supported (finding 1). This is outside the RFC 4180 scope in the bug reports.
- Whether malformed text after a closing quote should be rejected or accepted leniently (finding 2).
- Whether blank lines should produce `[]` rows instead of `['']` (finding 3).
