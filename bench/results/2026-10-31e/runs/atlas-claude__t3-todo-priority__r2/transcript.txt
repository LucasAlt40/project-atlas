## Plan: add priorities to the todo store

**Goal:** add `priority` (`low` | `normal` | `high`, default `normal`) to `store.add`, sort and filter in `store.list`, and show `!` before high-priority titles in `formatList`. Existing behaviour and tests must stay as they are.

**Current state (verified by reading):**
- `src/store.js`: `createStore()` returns `add(title)`, `complete(id)` and `list()`. `add` returns `{ id, title, done }`. `list()` returns shallow copies in insertion order. There is no options or filter parameter yet.
- `src/format.js`: `formatList` maps each todo to `[x] title` or `[ ] title`, joined with `\n`. It is only passed plain objects, including `{ title, done }` in the existing test, so a missing `priority` must render exactly as before.
- `test/store.test.js`: four tests using `node:test` and `assert`. `npm test` runs `node --test`. The package has no dependencies.

**In scope:** `src/store.js`, `src/format.js`, and new tests in `test/`.
**Out of scope:** `complete`, persistence, a CLI, changing the README beyond an optional note, and any new modules or shared constants files.

**Modules and architecture impact:** both modules are standalone with no shared dependencies. The store owns the priority rules. The formatter only needs to know the string `'high'`. Adding a constants module would be an abstraction the task does not need, so I recommend against it.

**Decisions the Developer must follow:**
1. **Validation in `add(title, options)`:** `options` defaults to `{}`. If `options.priority` is `undefined`, use `'normal'`. Any other value that is not one of the three strings throws `RangeError`. This includes `null`, so the check is a strict membership test, not a truthy test. Keep the existing `TypeError` for the title unchanged.
2. **Stored shape:** `{ id, title, done: false, priority }`. Existing `list()` copies carry the field through automatically.
3. **Ordering in `list(filter)`:** rank map `{ high: 0, normal: 1, low: 2 }`. Sort a copy of the array by rank. `Array.prototype.sort` is stable (ES2019), so ties keep insertion order. Do not mutate the internal `todos` array.
4. **Filtering:** if `filter` is absent or `filter.priority` is `undefined`, return all todos, sorted. If `filter.priority` is set, return only todos of that priority in insertion order. Recommendation: throw `RangeError` for an invalid filter priority, the same as `add`. The task does not specify this, so I am flagging it as a choice the Developer should make and state in the final message.
5. **Formatting:** render `!` only when `t.priority === 'high'`, giving `[ ] !Pay rent`. Do not default missing priority to anything, so `[x] a` and `[ ] b` from the existing test stay the same. `low` and `normal` render as before.
6. **Tests:** add them to `test/store.test.js` (or a sibling `test/priority.test.js`, the Developer's choice) and keep the existing four tests untouched.

**Files to change:**
- `src/store.js`: `add` signature and validation, `list(filter)` sort and filter.
- `src/format.js`: one-line change in the map callback.
- `test/store.test.js`, or a new `test/priority.test.js`: new cases.

**Test cases to add:**
- `add` without options gives `priority: 'normal'`.
- Each valid priority is stored.
- Invalid values (`'urgent'`, `null`, `''`, `'High'`) throw `RangeError`.
- `list()` sorts high, normal, low, with insertion order kept within each group.
- `list({ priority: 'low' })` returns only low todos in insertion order.
- Invalid filter priority behaves as decided in item 4.
- `formatList` renders `[ ] !Pay rent` for high and unchanged output for other priorities and for plain objects without `priority`.

**Risks:**
- Relying on sort stability. It is guaranteed by ES2019, and the Node version here supports it, so the risk is low.
- The `null` options edge case. Guarding with `options ?? {}` is cheap, and the Developer should choose it deliberately.
- Changing the return shape of `add` could break callers that compare whole objects. The existing tests do not do this.

**Verification:** run `npm test` (`node --test`). All four existing tests and the new ones must pass. I did not run tests in this step because the step is analysis only and must not implement.
