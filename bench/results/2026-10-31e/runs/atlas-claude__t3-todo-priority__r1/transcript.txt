## Plan: todo priorities in `src/store.js` and `src/format.js`

**Baseline:** `npm test` passes 4/4 on the untouched code.

### Goals
- `store.add(title, options)` accepts `options.priority` of `'low' | 'normal' | 'high'`, defaulting to `'normal'`. Anything else throws `RangeError`.
- `store.list(filter)` returns only todos matching `filter.priority` when given. Without a filter, it returns high, then normal, then low, with insertion order kept within each priority.
- `formatList` renders high-priority todos as `[ ] !Title`. Other priorities render as before.
- All existing tests keep passing, and new tests cover the new behaviour.

### Out of scope
- No changes to `complete`, the id scheme, or the `title` validation.
- No change to `README.md` beyond an optional one-line mention.
- No new modules, classes, or config.

### Architectural impact
The change stays inside one closed module, `createStore`, plus the pure function `formatList`. Neither has external dependencies, and `format.js` does not import `store.js`, so the dependency direction stays the same. The `list()` return shape changes only by one new field (`priority`) and by ordering. The `list()` ordering change is the only behaviour change visible to existing callers.

### Decisions for the Developer
1. **One rank table in `store.js`.** Define `const PRIORITY_RANK = { high: 0, normal: 1, low: 2 };` at module level. Use `Object.hasOwn(PRIORITY_RANK, p)` (or `in`) to validate, and use the same table to sort. Do not duplicate the list in `format.js`; `formatList` only compares against `'high'`.
2. **Defaulting.** `options` defaults to `{}`. Only `undefined` means "not given" and falls back to `'normal'`. Any other value, including `null`, `'High'`, or `'urgent'`, throws `RangeError`. This matches the spec's "any other value throws".
3. **Validate the filter too.** `list(filter = {})` throws `RangeError` when `filter.priority` is set to an unknown value. The spec is silent here. Silently returning `[]` would hide typos, so I recommend throwing. This is a judgement call; flag it if the user prefers an empty result.
4. **Sorting.** Sort a copy of the array, not the stored `todos`. Use `Array.prototype.sort` with the comparator `PRIORITY_RANK[a.priority] - PRIORITY_RANK[b.priority]`. The sort is stable (ES2019), so insertion order survives within each priority. Apply the filter first, then the sort.
5. **Storage.** Store `priority` as a plain string field on the todo object, next to `id`, `title`, and `done`. `list()` keeps returning shallow copies, so the new field flows through with no extra code.
6. **Formatting.** `formatList` prefixes `!` only when `t.priority === 'high'`. Todos without a `priority` field (as in the existing format test) render exactly as before.

### Files and contracts
- **`src/store.js`**: add the rank table, extend `add(title, options = {})` with validation and the `priority` field, and extend `list(filter = {})` with filtering and sorting.
- **`src/format.js`**: change the line prefix to `${t.priority === 'high' ? '!' : ''}${t.title}`.
- **`test/store.test.js`**: add tests (below). Keep the existing file and style; do not create new test files.
- **Contract**: `add` returns `{ id, title, done, priority }`. `list` returns copies sorted by priority, optionally filtered. `formatList` output is unchanged for non-high todos.

### Verification
Add these tests to `test/store.test.js`:
- `add` without options gives `priority: 'normal'`.
- `add` with each of `low`, `normal`, `high` stores that value.
- `add` with `'urgent'`, `'High'`, `null` throws `RangeError`.
- `list({ priority: 'low' })` returns only low todos, in insertion order.
- `list({ priority: 'urgent' })` throws `RangeError`.
- `list()` with mixed priorities added in the order low, high, normal, high returns high, high, normal, low. The two highs keep their insertion order.
- `list()` does not reorder the underlying store: a second call returns the same order.
- `formatList` on `[{title:'Pay rent', done:false, priority:'high'}, {title:'b', done:true, priority:'low'}]` gives `'[ ] !Pay rent\n[x] b'`.

Run `npm test`; expect the 4 existing tests plus the new ones to pass.

### Risks
- **Silent ordering change.** Existing callers of `list()` that relied on insertion order will now see high-priority items first. It is the spec's requirement, but the Developer should mention it in the final summary.
- **Shared-reference bug.** If the sort were applied in place to `todos`, `list()` would reorder the store. The copy in decision 4 prevents this.
- **Validation gaps.** The `filter` argument might be given as `null`. `list(null)` would fail on `filter.priority`. Handle with `filter = {}` plus a `filter ?? {}` guard, or document that `null` is not accepted.

### Not verified
I did not implement the change, as the step requires. The test commands above have not been run against the new code.
