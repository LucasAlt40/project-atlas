All 7 tests pass: the 2 existing tests and the 5 regression tests that failed before the fix.

**Root causes (confirmed by reading `src/cart.js` and by the failing tests):**
- **Quantity ignored:** the sum added `item.price` and never used `item.qty`, so 3 × 19.90 gave 19.9.
- **Percent coupon inverted:** `sum * value / 100` computes the discount amount, not the payable amount, so OFF20 on 100 gave 20.
- **Negative totals:** the fixed coupon subtracts with no floor, so TENOFF on 5.00 gave -5.
- **Long decimals:** nothing rounds the result, so 0.1 + 0.2 gave 0.30000000000000004.
- **Extra bug, same rule:** `COUPONS[couponCode]` also matches inherited object properties, so `toString` or `__proto__` produced `NaN`. The spec says unknown coupons are ignored, so I fixed it too.

**Fix:** multiply by quantity, apply the percent as `100 - value`, look up coupons with `Object.hasOwn`, and return `Math.max(0, Math.round(sum * 100) / 100)`. The export is still `module.exports = { total }`.

**Files changed:**
- `src/cart.js`: the fix above.
- `test/cart.test.js`: five `regression:` tests covering quantity, the negative clamp, percent coupons (OFF20 and HALF), cent rounding, and unknown coupons.

**Commands run:** `npm test`, before the change, passed 2 of 2. With the new tests added and the fix not yet applied, it failed 5 of 7, with the failures listed above. After the fix it passed 7 of 7.

**Residual risk:**
- `Math.round(x * 100)` rounds exact binary half-cent values unpredictably (for example 1.005 becomes 1.00). Integer-cent arithmetic would remove this, but it is a larger change than this bug needs.
- The code does not validate `price` or `qty` (negative or non-numeric values are not rejected). That was not in the report.
- `git log` was refused by the sandbox, so the recent-history check relies on the commit list in the session context.

## QA verification: cart total fix

**Verdict: pass.** The fix removes each of the four reported causes, and the regression tests cover them. I found no regressions in the code paths I traced. Remaining items are low-severity hardening notes.

### Root cause (from the investigation, confirmed against the code)
1. **Quantity ignored:** the subtotal added `item.price` without `item.qty`. (read: `src/cart.js:16`)
2. **OFF20 returned the discount:** percent coupons returned `sum * value / 100`, which is the discount amount, not the payable amount. (read: `src/cart.js:21`)
3. **Negative totals:** fixed coupons subtracted with no floor. (read: `src/cart.js:23`, `:26`)
4. **Long decimals:** the final sum was never rounded to cents. (read: `src/cart.js:26`)
5. **Inherited keys as coupons:** `COUPONS[couponCode]` matched `toString` and `__proto__`, so the coupon's `type` was undefined and the result was `NaN`. (read: `src/cart.js:18`)

### Fix applied (as present in the worktree)
- `src/cart.js:16` multiplies by `qty`.
- `src/cart.js:18` uses `Object.hasOwn(COUPONS, couponCode)`.
- `src/cart.js:21` computes `sum * (100 - value) / 100`.
- `src/cart.js:23` subtracts the fixed value.
- `src/cart.js:26` returns `Math.max(0, Math.round(sum * 100) / 100)`.
- `module.exports = { total }` is unchanged (`src/cart.js:29`).

### Validation evidence
- **Read:** traced each reported scenario through the code:
  - 19.9 × 3 gives 59.7.
  - TENOFF on 5.00 gives 0 (clamped).
  - OFF20 on 100 gives 80.
  - 0.1 + 0.2 gives 0.3 (rounded).
  - `toString` and `__proto__` are not own keys, so they are ignored and give 5.
  - `undefined` as a coupon code converts to the key `"undefined"`, which is not an own key, so no coupon applies.
- **Read:** `test/cart.test.js:13-41` has a regression test for each reported bug. Each one would fail against the pre-fix code, which matches the investigation's recorded before-fix evidence (19.9 vs 59.7, 20 vs 80, -5 vs 0, 0.30000000000000004 vs 0.3, NaN vs 5). I traced these by hand; I did not re-run them against the old code, because I cannot modify files in this read-only mode.
- **Executed:** `npm test` (`node --test`) ran 7 of 7 tests, all passing, 0 failing.
- **Read:** `package.json` declares no `engines` field. `Object.hasOwn` needs Node 16.9 or later, and `node --test` already needs Node 18 or later, so this is not a new requirement.
- **Read:** the only callers in the repo are the test file. I found no other consumers of `total` in the files I read.

### Side effects and regression risk
- Rounding happens only once, after the coupon and the clamp, so intermediate values are not rounded.
- The `Math.max(0, …)` clamp applies to every coupon type. A percent coupon cannot produce a negative value, since `100 - value` is positive for these coupons.
- The unknown-coupon path (`null`) keeps the old behavior of returning the plain subtotal.
- Both `Object.hasOwn` and `Math.round` have no effect on the normal coupon paths above.

### Findings (low severity, pass outcome)
- **Half-cent rounding:** `Math.round(x * 100) / 100` rounds binary half-cent values down. For example, `1.005 * 100` is `100.49999999999999`, so the result is `1` rather than `1.01`. This is an edge case the spec does not mention. Decide whether a decimal-safe rounding is needed.
- **No input validation:** negative `qty` or a non-numeric `price` gives a negative or `NaN` total. `Math.max(0, NaN)` returns `NaN`, so a `NaN` input still produces a `NaN` total. This is beyond the reported bugs.
- **Coupon codes are case-sensitive:** `tenoff` is silently ignored. The spec does not say whether codes should be case-insensitive.
- **Test gaps:** there is no test for a percent coupon on a half-cent result, for combined quantity and coupon edge cases beyond the one case, or for `NaN`/negative inputs. These are worth adding if the team wants them covered.

### What I could not verify
- I could not run `git diff` because the sandbox refused it, so the change was reviewed from the file contents and the handoff's diff summary, not from a diff.
- I could not run the regression tests against the pre-fix code to watch them fail, because the sandbox is read-only. The failure claim rests on my trace and on the earlier step's recorded evidence.
