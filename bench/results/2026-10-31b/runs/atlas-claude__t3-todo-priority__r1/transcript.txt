## Plan: priorities for the todo store

**Goal:** Each todo has a `priority` of `'low'`, `'normal'` (default) or `'high'`. `store.list()` sorts by priority, and `store.list({ priority })` filters. `formatList` marks high-priority todos with `!`.

**Scope.** In: `src/store.js`, `src/format.js`, `test/store.test.js`. Out: `complete()`, `README.md`, and any persistence (the store is in-memory only). No new modules or dependencies.

**Current state (verified by reading the files):**
- `src/store.js`: `createStore()` keeps a private `todos` array in insertion order. `add(title)` validates the title and builds `{ id, title, done }`. `list()` returns shallow copies in insertion order. `complete(id)` mutates the internal todo.
- `src/format.js`: `formatList` maps each todo to `[x]`/`[ ]` plus the title.
- `test/store.test.js`: uses `node:test` and `node:assert`. Two existing tests depend on current behaviour. `add and list` expects `['a', 'b']` in insertion order, which still holds once all todos are `normal`. `format` passes plain `{ title, done }` objects with no `priority` field, so the `!` check must treat a missing priority as not high.

**Architectural impact.** The change stays inside the single `createStore` closure. Ordering and filtering are pure functions of the internal array, so `complete()` and the `id` sequence are unaffected. The only behaviour change for existing callers is the sort order of `list()`, and that is identical for all-`normal` data.

**Decisions the Developer must follow:**
1. **Validation in `store.js`.** Define one private rank map, `{ high: 0, normal: 1, low: 2 }`, and use its keys both to validate and to sort. Do not export it and do not add a separate module.
2. **`add(title, options = {})`.** If `options.priority` is `undefined`, use `'normal'`. Any other value that is not one of the three keys throws `RangeError`. This includes `null`, `'High'` (case-sensitive) and `'urgent'`. Keep the existing `TypeError` for titles unchanged, and validate the title first so the error order does not change.
3. **Store the field.** `add` returns `{ id, title, done: false, priority }`.
4. **`list(filter = {})`.**
   - If `filter.priority` is `undefined`, return all todos sorted by rank.
   - If it is set, validate it the same way as in `add` (throw `RangeError` if invalid), then return only todos of that priority.
   - Build the result by copying the array with `map` and then sorting the copies with `sort` by rank. `Array.prototype.sort` is stable in Node, so ties keep insertion order. Do not sort the internal `todos` array.
5. **`formatList` in `format.js`.** For `priority === 'high'`, output `[ ] !title` or `[x] !title` (the `!` appears whether or not the todo is done). Every other case, including a missing `priority`, produces exactly today's output.
6. **No extra API.** Do not add `setPriority`, a `PRIORITIES` export or any other surface the task does not ask for.

**Tests to add in `test/store.test.js`:**
- The default priority is `'normal'`, and an explicit `'low'` or `'high'` is stored on the todo.
- `add` throws `RangeError` for `'urgent'`, `'High'`, `null` and `''`.
- `list()` orders high, then normal, then low. Within one priority the insertion order is kept, e.g. two highs added in the order `h1, h2` come back as `h1, h2`.
- `list({ priority: 'low' })` returns only low todos, in insertion order.
- `list({ priority: 'bogus' })` throws `RangeError`.
- `formatList` gives `'[ ] !Pay rent'` for a high todo and `'[x] !Pay rent'` for a done high todo, and normal and low todos are unchanged.

**Risks and how to handle them:**
- *Sort stability.* Node's `sort` is stable, so the tie-order test is what guards this.
- *Mutation.* `list()` must sort copies. Sorting the internal array would break insertion order for later calls.
- *Invalid filter.* I decided to throw rather than return an empty list, so a typo such as `'hgih'` is not silent. This is a design choice; say so if you want the other behaviour.
