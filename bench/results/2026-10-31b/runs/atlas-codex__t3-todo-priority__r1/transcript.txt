## Goals

Add priority behavior while preserving current todo storage, completion, formatting, and existing tests.

## Scope

In scope:

- `store.add(title, options)` with `low`, `normal`, and `high` priorities.
- Default priority of `normal`.
- `RangeError` for invalid priorities.
- Priority-aware filtering and default ordering.
- High-priority formatting with `!`.
- New tests in `test/`.

Out of scope:

- Persistence, UI changes, CLI changes, or new dependencies.
- Changes to todo IDs, completion behavior, title validation, or public module structure.

## Modules and architectural impact

- `src/store.js` remains the domain/data boundary. It owns priority validation, todo creation, filtering, copying, and ordering.
- `src/format.js` remains a pure presentation function. It only needs to inspect `priority` when deciding whether to prefix a title.
- `test/store.test.js` remains the single integration-style test module.
- No external dependencies are involved; the project uses CommonJS and Node’s built-in test runner.

The change is additive to the todo object shape. Existing callers that omit `options` remain valid, and formatting objects without a `priority` field continues to produce the existing output.

## Developer decisions to follow

- Treat omitted `options` as an empty options object.
- Accept only the exact strings `low`, `normal`, and `high`.
- Throw `RangeError` before adding a todo for any other priority.
- Store the resolved priority on every newly created todo.
- Preserve insertion order for `list({ priority })`; all matching todos have the same priority, so this also preserves their relative order.
- For unfiltered `list()`, order by explicit priority rank `high`, `normal`, `low`, while preserving insertion order within each rank. Do not mutate the internal `todos` array.
- Continue returning shallow copies from `list()`.
- In `formatList`, prefix only todos whose priority is exactly `high`; all other values, including an omitted priority on legacy input objects, retain the existing rendering.

## Files and contracts to change

- `src/store.js`
  - Change `add(title)` to accept optional `options`.
  - Add priority validation/defaulting.
  - Add `priority` to created todo objects.
  - Change `list()` to accept an optional filter and apply priority filtering/sorting.
  - Preserve existing title validation, completion behavior, IDs, and copy semantics.

- `src/format.js`
  - Render high-priority todos as `[ ] !Title` or `[x] !Title`.
  - Preserve rendering for normal, low, and legacy objects without `priority`.

- `test/store.test.js`
  - Test default and explicit priorities.
  - Test invalid priority rejection and that invalid additions are not stored.
  - Test priority filtering.
  - Test high-first ordering and insertion-order stability within a priority.
  - Test high-priority formatting and unchanged formatting for other priorities.
  - Keep all existing tests unchanged or compatible.

## Risks and trade-offs

- Sorting directly with an unstable comparator could reorder equal-priority todos; the implementation must explicitly preserve insertion order.
- Adding the field changes the complete shape of newly returned todos, which is required by the task but could affect consumers doing exact object equality.
- Legacy objects passed directly to `formatList` may not have `priority`; checking specifically for `'high'` avoids a compatibility regression.
- Options such as `null` are not defined by the contract; the implementation should support omitted options without introducing broader validation behavior that the task does not require.
