## Plan: token bucket limiter (`src/limiter.js` + `test/limiter.test.js`)

**Goal:** a dependency-free, injectable-clock token bucket exported as `module.exports = { createLimiter }`, with node:test tests.

**In scope**
- `src/limiter.js` (new): `createLimiter(options)` returning `{ tryRemove, available, msUntil, reset }`.
- `test/limiter.test.js` (new): node:test + `node:assert` tests.

**Out of scope**
- No edits to `package.json` or any other file. `node --test` already discovers `test/*.test.js`.
- No async API, persistence, keyed/multi-bucket limiting, or integration with other code. Node is single-threaded, so no locking is needed.

**Architectural impact:** none. The module is a leaf with no dependencies and no existing callers. Time enters only through the injected `now` function, which keeps it deterministic to test.

**Decisions the Developer must follow**
1. **Validation in `createLimiter`:** `options = {}` default, so a missing argument fails on capacity as a `RangeError`. `capacity` must pass `Number.isInteger(c) && c > 0`. `refillPerSecond` must pass `typeof === 'number' && Number.isFinite(r) && r > 0`. Both failures throw `RangeError`. `now` defaults to `Date.now`; do not add extra validation to it, since the spec does not require any.
2. **State:** `tokens` (float, starts at `capacity`) and `last` (ms, set to `now()` at creation).
3. **Refill(t):** if `t < last`, set `last = t` and add nothing. Otherwise `tokens = min(capacity, tokens + (t - last) * refillPerSecond / 1000)` and `last = t`. Every method calls refill first.
4. **`n` validation** (shared by `tryRemove` and `msUntil`): `Number.isInteger(n) && n > 0`, else `RangeError`. Then `n > capacity` also throws `RangeError`. `available()` takes no argument.
5. **`tryRemove(n = 1)`:** after refill, if `tokens >= n`, subtract and return `true`; otherwise return `false` and change nothing.
6. **`available()`:** return `Math.floor(tokens)` after refill.
7. **`msUntil(n = 1)`:** after refill, `deficit = n - tokens`. If `deficit <= 0`, return `0`. Otherwise `Math.ceil(deficit * 1000 / refillPerSecond)`.
8. **`reset()`:** `tokens = capacity` and `last = now()`.
9. **Floating-point risk:** fractional refill can leave `tokens` a hair under an integer (e.g. `2.9999999999`), which would make `tryRemove` fail or `msUntil` report one extra millisecond. The Developer should not add an epsilon in the implementation unless a test shows the problem. Tests should use rates and timestamps that are exact in binary (`1`, `2`, `0.5`, `0.25`, and millisecond steps that divide evenly), so the expected values are exact.

**Files and contracts**
- `src/limiter.js`: exports exactly `{ createLimiter }`. Public surface: `createLimiter(options) → { tryRemove(n?), available(), msUntil(n?), reset() }`.
- `test/limiter.test.js`: requires `node:test` and `node:assert`.

**Test coverage the Developer should write**
- Starts full; `tryRemove` succeeds until empty, then returns `false` without changing the count.
- Refill is continuous and capped at `capacity` (a long idle period does not exceed it).
- Fractional rate (`0.5`/s): `msUntil(1)` after draining is `2000`; `available()` floors partial tokens.
- `msUntil` returns `0` when already available; the round-up behaviour is covered.
- `tryRemove(n)` with `n > capacity` throws `RangeError`; `n` of `0`, `-1`, `1.5`, `NaN` throws `RangeError` for both `tryRemove` and `msUntil`.
- `createLimiter` throws `RangeError` for missing/non-number/zero/negative/NaN/Infinity `refillPerSecond`, and for missing/non-integer/zero/negative `capacity`.
- Clock going backwards: no tokens added or lost, and the next refill counts from the earlier time.
- `reset()` refills to `capacity`.

**Verification:** run `npm test` (the project's own command) and confirm all tests pass. Read `src/limiter.js` against each numbered decision above.

**Risks:** the floating-point edge in decision 9. Also, `now()` returning a non-number would produce `NaN` state; the spec does not cover this, so I am not adding a guard.

## QA verdict: fail

**Executed:** `npm test` ran 18 of 18 tests, all passing.

**Read only, not executed:** the 0.1 drift trace below. The sandbox only allows the project's test commands, so I could not run a probe. The trace relies on IEEE-754 double arithmetic, which is well established, but treat it as unverified until someone runs the repro.

### Main finding (medium): fractional refill loses a whole token

`src/limiter.js:37` accumulates `tokens += ((t - last) * refillPerSecond) / 1000` on every refill. With `refillPerSecond: 0.1`, each 1000 ms step adds exactly the double nearest 0.1. Ten such additions sum to `0.9999999999999999`, not `1`.

Repro (read-traced, not executed):
- `createLimiter({ capacity: 1, refillPerSecond: 0.1, now })` at t=0, then `tryRemove()` returns true.
- Call `available()` at t=1000, 2000, …, 10000.
- At t=10000 the spec requires `available() === 1`. The code returns `0`.
- `tryRemove()` at t=10000 returns `false`, and `msUntil()` returns `1` instead of `0`.

The spec says refill is continuous and that `available()` rounds down the true token count. After exactly 10 s at 0.1/s there is one whole token. The implementation drops it. The existing tests do not catch this: they use binary-exact rates (0.5, 1, 3 only at a single ceil check), so the drift never shows. The Developer and Architect both flagged this as a possible issue and deferred it; the trace above shows it is a real off-by-one for an in-contract input.

Suggested fix: add a test with the repro above (it should fail today), then either compare with a small epsilon (e.g. `1e-9`) in `available`, `tryRemove` and `msUntil`, or track elapsed time in integer ms and compute tokens from total elapsed rather than accumulating per step.

### Low-severity findings (do not change the outcome)

1. **`now()` returning a non-number freezes refill** (`src/limiter.js:34-39`, read). If `now()` returns `NaN`, `t > last` is always false and `last` becomes `NaN`, so the bucket never refills again. This is outside the stated contract, but a guard or a throw would make it visible.
2. **Denormal `refillPerSecond` gives `Infinity` from `msUntil`** (`src/limiter.js:63`, read). For a value such as `5e-324`, `(n - tokens) * 1000 / refillPerSecond` overflows to `Infinity`, and `Math.ceil` returns `Infinity`, not a whole number of ms. In contract, but an edge case no test covers.
3. **`createLimiter(null)` throws `TypeError`** (`src/limiter.js:25`, read). The default `= {}` only covers `undefined`. The spec only covers a missing capacity, so this is a robustness nit.
4. **Default clock is not tested** (`test/limiter.test.js`, read). Every test injects `now`, so the `Date.now` default is never exercised.
5. **Backwards-clock tests do kill the mutants** (read). Removing the `t > last` guard breaks test 'a clock going backwards adds no tokens and loses none'. Removing `last = t` breaks 'after a backwards clock, refill is measured from the earlier time'. Removing `Math.min` breaks 'refill never exceeds capacity'. Removing `Math.ceil` breaks 'msUntil rounds up to the next millisecond'.

### What I could not check
- Real-time behaviour with `Date.now`.
- Any non-binary fractional rate (the core of the finding above), since I could not execute a probe.
- Concurrency is not applicable: the module is synchronous.
