# Plan: order cancellation

## Goals
- `orders.cancel(orderId, reason)` cancels a placed order, restores its stock, records the reason and status, emits `order.cancelled`, and returns the cancelled order.
- Invalid calls fail with the specified errors and change nothing.
- `reports.revenue()` and `reports.unitsSold(sku)` exclude cancelled orders.
- Existing behaviour and the existing tests in `test/shop.test.js` stay unchanged.

## Out of scope
- Cancelling an order that was partly fulfilled, refunds, or any payment concept (none exists in the code).
- Changes to `events.js` (the bus already supports `on`/`emit`).
- Changes to `shop.js` wiring. `createOrders` already receives `inventory` and `bus`, so no new dependency is needed.
- Changes to `README.md`, unless the Developer wants a one-line note about the new method.

## Current architecture and impact
- `shop.js` is the only composition root. `orders.js` depends on `inventory` and `bus` (injected). `reports.js` depends on `orders` only, through `orders.all()`.
- Impact is contained: one new inventory method, one new orders method, one filter change in reports, and new tests. Nothing else depends on order internals.
- `orders.get`/`all` return copies. The Developer must keep that pattern so callers cannot mutate stored orders.

## Decisions the Developer must follow
1. **Validation order in `cancel`:** check `reason` first (TypeError, no state read), then look up the order (`not found`), then check status (`already cancelled`). Checking the argument first keeps the rule independent of state and makes the "nothing changes" guarantee easy to see.
2. **Reason validation:** reject non-strings and strings that are empty after `trim()`. Whitespace-only is treated as empty. This is my reading of "non-empty"; the user can redirect it to a plain `length === 0` check.
3. **Stored fields:** on cancel, set `status = 'cancelled'` and add `reason` to the stored order. `place` does not write `reason`, so an uncancelled order has no `reason` key.
4. **Restocking:** add `inventory.restock(sku, qty)` next to `take`. It adds to stock and does not check availability. Restocking the items in an order is the mirror of `place`'s `take` loop.
5. **Mutation order:** restock all items, set status and reason, then emit `order.cancelled` with `{ orderId, reason }`. This follows `place`'s pattern of mutating before emitting. The event fires exactly once, and only on success.
6. **Return value:** return a copy shaped like `place`'s return (`{ ...order, items: copied }`), including `reason` and `status: 'cancelled'`.
7. **Reports:** filter out `o.status === 'cancelled'` inside `reports.js` for both `revenue` and `unitsSold`. Leave `orders.all()` unchanged, so listing still shows cancelled orders.

## Files and contracts
- `src/inventory.js`: add `restock(sku, qty)`. Contract: `quantity(sku)` increases by `qty`.
- `src/orders.js`: add `cancel(orderId, reason)`. Contract: errors as specified (`Error` with "not found" or "already cancelled", `TypeError` for reason); event `order.cancelled` with `{ orderId, reason }`, emitted once.
- `src/reports.js`: filter cancelled orders in `revenue` and `unitsSold`.
- `test/shop.test.js`: append new tests. Reuse the existing `setup()` helper and style. Do not edit the existing tests.

## Test plan
- Cancel restores stock; the returned order has `status: 'cancelled'` and `reason`; `get` reflects the same.
- Exactly one `order.cancelled` event with `{ orderId, reason }` is emitted (collect into an array, as the existing `order.placed` test does).
- Unknown id throws `Error` matching `/not found/`; no stock change, no event.
- Cancelling twice throws `Error` matching `/already cancelled/`; the second call changes no stock and emits no event.
- Empty string, whitespace-only and non-string reasons throw `TypeError`; stock, status and events are unchanged.
- Reports: after cancelling one of two orders, `revenue()` and `unitsSold(sku)` reflect only the remaining order.
- Run `npm test`. All existing tests must still pass.

## Risks
- **Handler failure after mutation:** if an `order.cancelled` handler throws, the cancellation has already happened. This matches the existing `place` behaviour, so I accept it and do not design around it.
- **Status string coupling:** reports depend on the literal `'cancelled'`. A small module-level constant would avoid typos, but the codebase uses plain string literals for `'placed'`, so I recommend following that pattern.
- **Whitespace reason:** if the user wants any non-empty string accepted, decision 2 changes. Nothing else depends on it.
