## Plan: priorities for the todo store

**Goal:** add `priority` (`low` | `normal` | `high`, default `normal`) to `createStore().add`, filtering and priority-first ordering to `list`, and a `!` marker for high-priority items in `formatList`. Existing behaviour and the four current tests must keep passing.

**Current state (read, not changed):**
- `src/store.js`: `createStore()` holds a private `todos` array. `add(title)` validates the title (`TypeError`), pushes `{ id, title, done }`. `complete(id)` is unchanged. `list()` returns copies in insertion order. There is no filter.
- `src/format.js`: `formatList` maps each todo to `[x]`/`[ ]` plus title. It does not import anything.
- `test/store.test.js`: one file using `node:test` and `node:assert`, covering add/list, complete, empty title, and format. `npm test` (`node --test`) passes 4/4 on the current tree.

**In scope**
- `src/store.js`: `add(title, options)`, `list(filter)`.
- `src/format.js`: `formatList`.
- `test/store.test.js`: new cases appended to the existing file.

**Out of scope**
- `complete()`, persistence, any new module, CLI, or changes to `package.json`.

### Design decisions for the Developer

1. **Priority list lives in `store.js`.** Use one constant, ordered by sort rank: `const PRIORITIES = ['high', 'normal', 'low'];`. Validation is `PRIORITIES.includes(p)`. The sort rank is the array index. Do not add a separate module, since three values do not justify one.
2. **`add(title, options)`:**
   - `options` defaults to `{}`.
   - Title validation runs first, unchanged, so the existing `TypeError` still applies.
   - If `options.priority === undefined`, use `'normal'`.
   - Any other value that is not in `PRIORITIES` throws `RangeError`. This includes `null`, `'High'` (case-sensitive), and `''`.
   - The stored todo becomes `{ id, title, done: false, priority }`.
3. **`list(filter)`:**
   - `filter` defaults to `{}`.
   - Start from a copy (`todos.filter(...)` or `todos.map(...)`), so the internal array is never sorted in place.
   - If `filter.priority` is given, keep only todos with that priority. **Decision:** an unknown filter value throws `RangeError`, matching `add`. The spec does not say this. Returning `[]` is the alternative, and if the user prefers it, change the one check.
   - Sort by `PRIORITIES.indexOf(t.priority)`. `Array.prototype.sort` is stable (ES2019+), so insertion order holds within a priority. Do not add an explicit sequence number.
   - Return copies as today (`{ ...t }`).
4. **`formatList`:** a todo with `priority === 'high'` renders as `[ ] !Pay rent` (or `[x] !Pay rent` when done). Everything else renders exactly as before. The check is a literal `'high'`, so format does not depend on store. Todos without a `priority` field, such as the raw objects in the existing format test, render as before.

### Files and contracts
- `src/store.js`: `add` signature gains an optional second argument. `list` gains an optional filter. Todo shape gains `priority`. Existing callers passing only a title are unaffected.
- `src/format.js`: output format unchanged except for the `!` prefix on high-priority titles.
- `test/store.test.js`: add these cases:
  - default priority is `normal`;
  - explicit `low` and `high` are stored;
  - invalid values (`'urgent'`, `'High'`, `null`, `''`) throw `RangeError`;
  - the filter returns only the matching priority;
  - an unknown filter throws `RangeError`;
  - an unfiltered list sorts high, normal, low, with insertion order kept within each group;
  - `formatList` prints `!` for high (open and done), and no `!` for normal or low.

### Risks
- **Mutation of internal state:** sorting the internal array in place would reorder insertion order for later calls. Sorting a copy avoids this. The new order test should check it by calling `list()` twice.
- **Non-object `options`:** `add('x', 'high')` silently gets `normal` because a string has no `priority` property. This is acceptable for a plain JS API. Tightening it is optional and is not in the spec.
- **Stable sort:** relies on Node's stable `Array.prototype.sort`, which is guaranteed for all supported modern Node versions.

### Verification
- `npm test` must show all existing tests passing plus the new ones.
- Reading the diff confirms the internal array is not sorted in place and that `formatList` output is unchanged for non-high todos.
