## Plan: todo priorities

**Goal:** Add `low` / `normal` / `high` priorities to the in-memory store, make `list` filter and sort by them, and mark high-priority rows in `formatList`. Existing behaviour and `node --test` must stay green.

**Current state (verified by reading):**
- `src/store.js`: `createStore()` returns `add(title)`, `complete(id)` and `list()`. Todos are `{ id, title, done }`. `list()` returns shallow copies in insertion order and takes no arguments.
- `src/format.js`: `formatList(todos)` renders `[x] title` / `[ ] title`, one per line.
- `test/store.test.js`: four tests (add/list, complete, empty title, format) using `node:test` and `assert`. Run with `npm test`, which is `node --test`.

**In scope**
- `add(title, options)` accepts `options.priority`, default `'normal'`. Any other value throws `RangeError`.
- Each todo gets a `priority` field.
- `list(filter)`: with `filter.priority`, return only todos of that priority. Without it, sort high → normal → low. Ties keep insertion order.
- `formatList`: a high-priority todo renders as `[ ] !Title` (and `[x] !Title` when done). Other priorities render as today.
- New tests in `test/store.test.js`.

**Out of scope**
- `complete`, id generation, title validation, and the README (no API docs exist there today; I'd leave it alone unless you want a line added).
- Persistence, and any priority-changing API beyond `add`.

**Files and contracts**
1. `src/store.js`
   - Add one module-level constant, `const PRIORITIES = ['high', 'normal', 'low'];`. It serves both validation (`includes`) and the sort rank (`indexOf`). No new abstraction.
   - `add(title, options = {})`: resolve `priority = options.priority === undefined ? 'normal' : options.priority`. If it isn't in `PRIORITIES`, throw `new RangeError(...)`. Store `{ id, title, done: false, priority }`. Title validation stays first and unchanged.
   - `list(filter = {})`: start from `todos`. If `filter.priority !== undefined`, validate it the same way and keep only matches. Then sort by `PRIORITIES.indexOf(t.priority)`. `Array.prototype.sort` is stable in Node, so ties keep insertion order. Return copies with `map`, as now.
2. `src/format.js`
   - Prefix the title with `'!'` when `t.priority === 'high'`. Todos without a `priority` field (for example, objects built by hand in the format test) are not high, so the existing output is unchanged.
3. `test/store.test.js`: add tests, keep the existing four unchanged.

**Decisions for the Developer to follow**
- Priority comes from `options.priority`. `undefined` means default `'normal'`. Any other value, including `null`, `'HIGH'` or `'urgent'`, throws `RangeError`. Matching the spec literally is the reason.
- An invalid `filter.priority` in `list` also throws `RangeError`, to match `add`. The spec doesn't cover it. This is my choice; the alternative is returning an empty array.
- Sorting happens in `list` on a copy, never on the internal `todos` array, so insertion order is preserved for later calls.
- The filter path and the sort path share the same code. When filtering by one priority, the sort is a no-op, so no special case is needed.
- `formatList` checks `priority === 'high'` only. It does not change for `normal` or `low`.

**Verification**
- `npm test` must pass, including the four existing tests.
- New tests in `test/store.test.js`:
  - Default priority is `'normal'` when no options are passed, and when `options` is `{}`.
  - `add('x', { priority: 'high' })` stores `priority: 'high'`.
  - Invalid values (`'urgent'`, `'HIGH'`, `null`, `1`) throw `RangeError`.
  - `list()` order: add low, normal and high todos in mixed order; expect high, normal, low, with ties in insertion order.
  - `list({ priority: 'low' })` returns only low todos, in insertion order.
  - `list({ priority: 'urgent' })` throws `RangeError`.
  - `formatList([{ title: 'Pay rent', done: false, priority: 'high' }, { title: 'b', done: true, priority: 'low' }])` gives `'[ ] !Pay rent\n[x] b'`.
- Read-through check that `complete` still works, since it reads `todos` directly.

**Risks**
- Callers that deep-equal whole todo objects will now see a `priority` key. Nothing in the repo does this today; the only consumers are the tests.
- `list` now takes an argument. Calls with no arguments are unaffected.
- The `RangeError` choice for `null` could surprise a caller that passes `priority: null` to mean "unset". The spec says any other value throws, so I'm following it.
