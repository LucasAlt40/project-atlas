# Plan: priorities for the todo store

**Goal:** Todos carry a `priority` ('low' | 'normal' | 'high'). `store.list()` returns them high → normal → low with insertion order kept within a priority. `store.list({ priority })` filters. `formatList` marks high-priority todos with `!` before the title. Existing behaviour and tests stay unchanged.

**Out of scope:** no new modules or classes, no README change, no change to `complete()`, no persistence, no change to `formatList`'s input-order behaviour (it still renders in the order it is given).

**Current state (verified by reading):**
- `src/store.js`: `createStore()` closes over `todos` and `nextId`. `add(title)` validates the title with `TypeError`, pushes `{id, title, done}`, and returns it. `list()` returns shallow copies in insertion order. `complete(id)` mutates in place.
- `src/format.js`: `formatList(todos)` maps to `[x]`/`[ ]` plus title, joined with `\n`. It does no sorting.
- `test/store.test.js`: four `node:test` cases. `format` uses todo objects with no `priority` field, so the formatter must treat a missing priority as normal.
- `package.json`: `"test": "node --test"`, CommonJS, no dependencies.

**Architectural impact:** Ordering and validation belong in the store, which owns the data. Rendering stays in the formatter, which only reads `priority`. The formatter does not need the store, and the store does not know about display. The dependency direction stays as it is.

**Decisions the Developer must follow:**
1. Keep one constant in `store.js`, e.g. `const PRIORITY_RANK = { high: 0, normal: 1, low: 2 }`. Validate with `Object.hasOwn(PRIORITY_RANK, value)` or an equivalent check. Do not add a class or enum module.
2. `add(title, options = {})`: default only when `options.priority === undefined`, not with `??`, so `null` throws. Any value outside the three strings throws `RangeError`. The check is case-sensitive, so `'High'` throws.
3. Validate in this order: title (`TypeError`), then priority (`RangeError`). Both run before `todos.push` and before `nextId++`, so a rejected add consumes no id and stores nothing.
4. The stored object is `{ id, title, done, priority }`. Keep `list()` returning copies.
5. `list(filter = {})`: if `filter.priority` is set, validate it with the same `RangeError` rule, then keep only matching todos. An invalid filter value throws rather than returning `[]`. This is my choice, since the brief is silent on it, and I flag it below.
6. Sorting uses an explicit comparator, not reliance on sort stability: `PRIORITY_RANK[a.priority] - PRIORITY_RANK[b.priority] || a.id - b.id`. Ids increase with insertion, so the tie-break is insertion order. Sort after filtering or before; the result is the same.
7. `formatList`: `const bang = t.priority === 'high' ? '!' : '';` and the line becomes `` `[${mark}] ${bang}${t.title}` ``. A missing or other priority renders exactly as before.

**Files and contracts:**
- `src/store.js`: `add(title, options)`, `list(filter)` signatures and the `priority` field on todos. These are the new contracts.
- `src/format.js`: output for high-priority todos only. Other output is unchanged.
- `test/store.test.js`: add new cases; leave existing ones untouched.

**Tests to add (`test/store.test.js`):**
- Default priority is `'normal'`; explicit `'low'` and `'high'` are stored.
- `add('x', { priority: 'urgent' })`, `'High'`, `null` and `''` each throw `RangeError`. A rejected add leaves `list()` unchanged and does not consume an id (the next valid add gets the expected id).
- `list()` order: add a normal, a low, a high, another high, another normal → high, high, normal, normal, low in insertion order within each group.
- `list({ priority: 'normal' })` returns only normal todos in insertion order; an invalid filter throws `RangeError`.
- `list()` copies still don't leak references.
- `formatList` with a high todo renders `[ ] !Pay rent`; with normal and low todos renders as before; a todo with no `priority` field renders as before.

**Verification:** Run `npm test` (`node --test`). All four existing tests must pass unchanged, plus the new ones. I did not run tests in this step, since nothing has been implemented.

**Risks:**
- `list()` with no argument now returns a different order than before. This is required by the brief, but any caller relying on insertion order will see a change. No other code in the repo calls `list()`, so the impact is limited to the tests.
- Sorting on every `list()` call is O(n log n). That is irrelevant at this size, and I'm not adding caching.

**Open point (not blocking):** The brief does not say what `list({ priority: 'urgent' })` should do. I chose to throw `RangeError` to match `add`. If you would rather it return `[]`, change decision 5 and its test.

Decisions (1–7) above are the design; no files have been changed in this step.
