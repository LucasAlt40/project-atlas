## Plan: order cancellation

**Goal.** Add `orders.cancel(orderId, reason)` so that a placed order returns its items to stock, becomes `cancelled` with its reason kept, emits one `order.cancelled` event, and drops out of `reports.revenue()` and `reports.unitsSold(sku)`. The existing 3 tests must keep passing (baseline: `npm test` gives 3/3).

**Out of scope.** No change to `place`'s behaviour, no refunds or payments, no `order.cancelled` consumers, no change to `events.js`, no new modules or classes.

**Architectural impact.** Cancellation touches three existing modules that the composition root (`src/shop.js`) already wires together: `orders` (owns status and the event), `inventory` (owns stock), and `reports` (derives figures from orders). Each keeps its current owner. `shop.js` needs no change because `createOrders` already receives `inventory` and `bus`.

**Decisions the Developer must follow.**

1. **`src/inventory.js`:** add `give(sku, qty)` as the mirror of `take`: `stock.set(sku, (stock.get(sku) ?? 0) + qty)`. No validation is needed because `qty` comes from a stored, already-validated order.
2. **`src/orders.js` `cancel(orderId, reason)`**, with checks in this order so that nothing changes on any error:
   - a. If `typeof reason !== 'string' || reason.trim() === ''`, throw `TypeError`. This is checked first because it is argument validation and does not depend on the order's state.
   - b. Look up the order. If missing, throw `Error('order ${orderId} not found')`.
   - c. If `status === 'cancelled'`, throw `Error('order ${orderId} already cancelled')`.
   - d. Only then mutate: `inventory.give` for each item, set `order.status = 'cancelled'` and `order.reason = reason`, then `bus.emit('order.cancelled', { orderId, reason })` once.
   - e. Return a copy in the same shape as `get`, with items copied.
   - Store the reason on the order as `reason`. Placed orders have no `reason` property.
3. **Keep cancelled orders in `orders.all()` and `orders.get()`.** They are still records. The filter belongs in reports.
4. **`src/reports.js`:** exclude orders with `status === 'cancelled'` from both `revenue()` and `unitsSold(sku)`. Use one shared filter, e.g. `const counted = () => orders.all().filter((o) => o.status !== 'cancelled')`.
5. **Tests go in `test/shop.test.js`**, reusing its `setup()` helper and `node:test` style, rather than a new file. Cases:
   - Cancel restores stock, sets status and reason, emits exactly one `order.cancelled` with `{ orderId, reason }`, and returns the cancelled order.
   - Unknown id throws an `Error` matching `/not found/`, with no event and no stock change.
   - Cancelling twice throws an `Error` matching `/already cancelled/`, with no stock change and no second event.
   - Reason `''`, `'   '`, `undefined` and `42` each throw `TypeError`, with no stock, status or event change.
   - After a cancel, `revenue()` and `unitsSold('pen')` drop the cancelled order's contribution.
   - The existing three tests stay unchanged.

**Files to change.** `src/inventory.js` (add `give`), `src/orders.js` (add `cancel`), `src/reports.js` (filter), `test/shop.test.js` (new cases). `src/events.js` and `src/shop.js` are not changed.

**Risks.**
- `orderId` is matched strictly against the numeric `Map` key, so `cancel('1')` reports "not found". This matches `get` today and is acceptable; the Developer should not coerce types.
- The spec does not say which error wins when the reason is invalid and the order is missing. This plan picks the `TypeError` (check a). This is the one ambiguity that changes behaviour; it is noted here rather than asked, since either order satisfies the spec as written.
- Atomicity relies on the synchronous code path: all checks run before any mutation, and `give` cannot throw. If `give` ever gained validation, the ordering would need to be revisited.

**Verification.** Run `npm test`. Expect the 3 existing tests plus the new cases to pass, and check the new tests fail if `give` or the reports filter is removed.

Analysis only, nothing implemented. The design is ready for the Developer.
