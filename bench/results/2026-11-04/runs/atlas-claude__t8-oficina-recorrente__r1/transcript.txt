**Verdict: pass, with limits.** I checked the fix by reading. I could not run the regression test, because Maven cannot write to `target/` inside the read-only sandbox.

**Root cause.** `updatePaymentStatus` always updated `payments.getLast()` and never inserted a row. For a subscription, the September charge therefore overwrote August's row, changing its date and status. Nothing in the code path inserts a new payment for a recurring charge. The only insert is at checkout (`DonationApplication.java:88`).

**Fix applied (already in HEAD `0e1af67`).** In `PaymentGatewayService.java`:
- A donation is a subscription when `recurring || donation.sponsorshipId() != null` (line 180). The project's own `DonationQueryBuilder` also defines RECURRING as `sponsorship_id IS NOT NULL`, and `sponsorshipId` is set at checkout for every recurring donation (`DonationApplication.java`), so the rule holds.
- For subscriptions, `resolveSubscriptionPayment` (lines 216–234) works on the current cycle: rows with a null date (the checkout row) or a date in the current month. If the cycle already has a PAID row, it returns null and writes nothing. Otherwise it updates the first cycle row, or inserts a WAITING row if the cycle is empty.
- One-time donations keep `getLast()`. Method, card brand, fee and sponsorship activation code is unchanged.
- No schema change.

**Evidence.**
- *Read:* I read the full service file, the test file, `PaymentRepository`, `PaymentService`, `PaymentQueryBuilder`, `PaymentMapper`, `DonationApplication`, the DTOs (`CreatePaymentDto`, `DonationDto`, `PaymentDto`) and `webhook.json`. The test's constructor calls match the record definitions.
- *Read, diff against `77ed947`:* the only behavioural changes are the subscription branch, an added `donationService.findById` call, and moving the log line earlier. The fee and sponsorship branches are untouched.
- *Read, regression power:* against the pre-fix code, cases 2, 3, 4 and 5 would fail. Case 1 (first charge) and case 6 (one-time) would pass, so they are guards rather than regression detectors. The handoff predicted case 6 would fail before the fix; by reading it does not.
- *Executed:* `mvn test -Dtest=PaymentGatewayServiceUpdatePaymentStatusTest` failed in Maven's resources phase: copying `templates/email/default.html` into `target/classes` returned `Operation not permitted`. No test ran, and the full suite was not run either. I did not work around the sandbox.

**Side effects traced.**
- `cancelPaymentByDonationId` cancels all WAITING rows of the donation. On a PAID notification it runs after the cycle row is set to PAID, so it does not touch the cycle row. It is not a regression.
- `updateCheckoutStatus` still uses `getLast()`. This is the main residual risk (finding 2).
- `notifyPayment` still calls `cancelCheckout` on every subscription PAID webhook. This is pre-existing.

**What I could not verify.**
- Whether the regression test passes, and whether Mockito's inline mock maker self-attaches on this JDK.
- PagBank's actual payload for later charges. The fixture shows `recurring` set to INITIAL on every line, so I could not confirm whether the charge date is available.
