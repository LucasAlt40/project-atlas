## Plan: add priorities to the todo store

**Goal:** Todos gain a `priority` field (`'low' | 'normal' | 'high'`, default `'normal'`). `list()` can filter by priority and, when unfiltered, sorts high → normal → low with insertion order kept within each priority. `formatList` marks high-priority titles with `!`.

**In scope**
- `src/store.js`: validate and store `priority` in `add`; filter and sort in `list`.
- `src/format.js`: add the `!` marker for high priority.
- `test/store.test.js`: new tests for the behaviour. The existing tests stay unchanged.

**Out of scope**
- Changing a todo's priority after creation (there is no setter today, and the task doesn't ask for one).
- Persistence, CLI, or README changes. The README describes the project only generally, so it does not need updating.
- Any new dependency or abstraction.

**Modules and dependencies**
- `store.js` and `format.js` are independent. `format.js` reads only the todo shape (`title`, `done`, and now `priority`) and imports nothing. Keep it that way: the `!` check is a plain string comparison, not an import of the store's constants.
- The only contract change is additive: each todo object returned by `add` and `list` gains a `priority` field. Existing callers that ignore it are unaffected.

**Decisions for the Developer**
1. **Validation in `add(title, options)`.** Keep the existing title check first (it throws `TypeError`). Then:
   - If `options` is missing, or `options.priority === undefined`, use `'normal'`.
   - Otherwise the value must be exactly one of `'low'`, `'normal'`, `'high'`; anything else throws `RangeError`. This includes `null`, `'High'` (case-sensitive) and `'urgent'`. Use `=== undefined`, not `??`, so `null` is rejected rather than silently defaulted.
2. **Sorting in `list(filter)`.** Copy the array, filter by `filter.priority` when given, then apply a stable sort by rank (high=0, normal=1, low=2). `Array.prototype.sort` is stable in Node 12+, so insertion order is preserved within a priority. The same path covers both filtered and unfiltered calls, because a filtered result is a single priority and its order is insertion order. Keep returning copies (`{ ...t }`), as today.
3. **Invalid filter value.** The task doesn't say what happens here. My choice is to throw `RangeError`, matching `add`, rather than returning an empty list silently. The Developer should flag this in the summary as a choice that can be reversed.
4. **Priority ranking constant.** Keep it private to `store.js`, for example a small rank map. Do not export it, because nothing outside the store needs it.
5. **Format.** `t.priority === 'high'` gives `[ ] !Pay rent` (and `[x] !…` when done). Low and normal render exactly as before. A todo without a `priority` field, as in the existing `format` test, must still render with no marker.

**Files to change**
- `src/store.js`: `add` (validation and storage), `list` (filter and stable sort).
- `src/format.js`: `formatList` line template.
- `test/store.test.js`: append tests (see verification).

**Risks**
- Sort stability depends on the Node version. The project uses `node --test` and has no declared engine, so this is low risk, but the Developer should note it.
- `list()` shape changes slightly (additive). This is safe for in-repo code, which has no other consumers.
- Filter-with-invalid-value behaviour is a judgement call (decision 3).

**Verification**
- Run `npm test`. All existing tests must still pass unchanged.
- New tests should cover:
  - Default priority is `'normal'`, both with no options and with `{}`.
  - Each of `'low'`, `'normal'` and `'high'` is stored as given.
  - Invalid values (`'urgent'`, `'High'`, `null`, `1`) throw `RangeError`.
  - `list()` sorts high, normal, low, with insertion order kept within each priority.
  - `list({ priority: 'low' })` returns only low todos, in insertion order.
  - `list({ priority: 'urgent' })` throws `RangeError` (decision 3).
  - `formatList` renders `[ ] !title` for high and `[x] !title` when done, and renders low and normal as before.

I did not implement anything in this step. The design is complete and the Developer can start from it.
