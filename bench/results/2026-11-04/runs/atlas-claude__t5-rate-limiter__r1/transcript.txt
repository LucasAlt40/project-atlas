## Architecture and dependencies

## Decisions the Developer must follow
1. **Closure factory, no class.** `createLimiter` returns an object of four methods over private closure variables: `capacity`, `refillPerMs = refillPerSecond / 1000`, `tokens` (float), `last` (ms reference time).
2. **Validation in `createLimiter`.** Use `const { capacity, refillPerSecond, now = Date.now } = options ?? {}`, so a missing options object yields a RangeError rather than a TypeError.
   - `capacity`: `Number.isInteger(capacity) && capacity > 0`.
   - `refillPerSecond`: `typeof === 'number' && Number.isFinite && > 0`.
   - Both throw `RangeError`. Do not add validation for `now` beyond the default; the spec does not ask for it.
3. **One refill routine, called first by every public method.**
   - `t = now()`. If `t < last`, set `last = t` and add nothing; tokens are not lost.
   - Otherwise `tokens = Math.min(capacity, tokens + (t - last) * refillPerSecond / 1000)` and `last = t`.
   - Multiply before dividing to reduce floating error.
4. **Argument check for counts.** A shared `assertCount(n)` throws RangeError unless `n` is a positive integer, and also when `n > capacity`. `tryRemove` and `msUntil` both call it before refilling.
5. **Method behaviour.**
   - `tryRemove(n = 1)`: refill, then remove and return `true` if `tokens >= n`, otherwise return `false` and remove nothing.
   - `available()`: refill, then return `Math.floor(tokens)`.
   - `msUntil(n = 1)`: refill, return 0 if `tokens >= n`, otherwise `Math.ceil((n - tokens) * 1000 / refillPerSecond)`.
   - `reset()`: `tokens = capacity`. It does not need to read the clock, because the next refill caps at capacity anyway.
6. **Comments and style.** The repo has no style guide yet. Keep the code short, with `'use strict'` only if the Developer wants it, and no comments beyond the non-obvious clock-backwards rule.

## Test plan (`test/limiter.test.js`)
Use an injected fake clock (a mutable `t` variable passed as `now: () => t`). Prefer exact binary fractions such as 0.5 and 0.25 so assertions are not brittle.
- **Exports:** `Object.keys(require('../src/limiter.js'))` equals `['createLimiter']`.
- **Option validation:** RangeError for capacity `0, -1, 1.5, NaN, Infinity, '5', undefined`; for refillPerSecond `0, -1, NaN, Infinity, '1', undefined`; and for `createLimiter()` with no argument.
- **Starts full:** `available() === capacity`.
- **Drain and refuse:** `tryRemove` returns true until empty, then false, and a failed call leaves `available()` unchanged.
- **Continuous refill:** capacity 10, rate 0.5/s, drain to 0. Advance 1000 ms gives 0 tokens, 2000 ms gives 1, and a half-token advance is floored by `available()`.
- **Cap:** after a long idle period `available()` equals capacity exactly.
- **Count validation:** `tryRemove(n)` and `msUntil(n)` throw RangeError for `0, -1, 1.5, NaN, '2'`, and for `n > capacity`.
- **msUntil exact values:** capacity 2, rate 1/s, drained: `msUntil(1) === 1000`, `msUntil(2) === 2000`. Rate 3/s with deficit 1 gives `334` (ceil of 333.33).
- **msUntil consistency:** for rates such as 0.1, 0.3, 3 and 7 per second, advancing exactly `msUntil(n)` makes `tryRemove(n)` succeed. Where `msUntil(n) > 0`, advancing `msUntil(n) - 1` makes it fail. This is the test most likely to expose floating-point problems.
- **reset:** after draining, `reset()` gives `available() === capacity`.
- **Clock backwards:** at t=10000 with 3 tokens, set t=4000, and `available()` is still 3. Drain to 0 at t=4000, move to t=5000, and `available()` is 1. This confirms the earlier time became the reference.
- **Default clock:** `createLimiter({ capacity: 1, refillPerSecond: 1 }).tryRemove()` returns true.

## Risks
- **Floating-point boundaries.** A rate such as 0.1/s can leave a token count a hair under an integer, so `available()` floors one lower than expected, or `msUntil` rounds up by 1 ms. Mitigations: multiply before dividing, and rely on the consistency test above. If it fails, the Developer should report it rather than add an arbitrary epsilon; a scaled-integer representation would be the fallback, and that is a larger change.
- **Clock sources.** `Date.now` can jump backwards. The spec covers this, and the test above pins it down.
- **Node version.** `??` needs Node 14 or later. `node --test` default discovery needs Node 18 or later. I have not verified which Node version runs here.
