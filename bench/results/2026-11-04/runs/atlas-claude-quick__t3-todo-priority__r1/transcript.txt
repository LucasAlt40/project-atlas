## Plan: todo priorities in `src/store.js` and `src/format.js`

**Goal:** Todos carry a `priority` of `low`, `normal` (default) or `high`. `store.list` can filter by priority and sorts high, normal, low when unfiltered. `formatList` marks high-priority titles with `!`. Existing behaviour and tests stay as they are.

**Current code (read, not changed):**
- `src/store.js`: `createStore()` returns `add(title)`, `complete(id)` and `list()`. `add` validates the title with `TypeError`, stores `{ id, title, done }` in a closure array, and `list()` returns shallow copies in insertion order.
- `src/format.js`: `formatList` maps each todo to `[x] title` or `[ ] title`, joined with `\n`.
- `test/store.test.js`: four tests on `node:test`. Run with `npm test` (`node --test`). No dependencies.

**In scope:** `src/store.js`, `src/format.js`, `test/store.test.js`.
**Out of scope:** `complete`, the existing tests, `package.json`, README (no change needed), any new module or file, any setter to change a todo's priority.

### Design decisions

1. **Single source of truth for priorities.** In `src/store.js`, define a module-level `const PRIORITY_RANK = { high: 0, normal: 1, low: 2 };`. Its keys are the valid set and its values give the sort order. No extra abstraction.
2. **`add(title, options)`.** `options` is optional. Use `const { priority = 'normal' } = options ?? {};`. The default applies only to `undefined`, so `null` is rejected with `RangeError`, as the spec requires. Check the title first (existing `TypeError`), then the priority: if `!Object.hasOwn(PRIORITY_RANK, priority)`, throw `RangeError`. `Object.hasOwn` avoids matching inherited keys such as `toString`. Matching is case-sensitive: `'High'` is invalid.
3. **Stored shape.** `{ id, title, done, priority }`. The field is set on every new todo, so it is always present.
4. **`list(filter)`.**
   - Copy the array, then sort with `PRIORITY_RANK[a.priority] - PRIORITY_RANK[b.priority]`. `Array.prototype.sort` is stable in Node 12+ (the tests need Node 18+ anyway), so equal priorities keep insertion order.
   - If `filter?.priority` is given, keep only todos with that priority. Filtered results are therefore in insertion order, which is the one order they can have.
   - Invalid filter priority: **throw `RangeError`**, the same rule as `add`. The spec does not cover this case. The alternative is an empty array. I chose `RangeError` so a typo like `'High'` is not mistaken for "no todos". This is a judgment call, and the Developer should follow it unless the user says otherwise.
   - Keep returning copies (`{ ...t }`).
5. **`formatList`.** Prefix the title with `!` when `t.priority === 'high'`. Output is `[ ] !Pay rent` or `[x] !Pay rent` for done high todos. Other priorities, and todos with no `priority` field, render exactly as before. The existing format test (`{ title, done }` objects) therefore still passes. `formatList` does not sort; it keeps the order it is given.

### Files and contracts to change

- `src/store.js`: add `PRIORITY_RANK`; update `add` and `list`. Contract: `add(title, options?)` returns a todo with `priority`. `list(filter?)` returns sorted copies, filtered when asked. Both throw `RangeError` for invalid priorities.
- `src/format.js`: update `formatList`. Contract: `high` gets a `!` prefix; the output format is otherwise unchanged.
- `test/store.test.js`: append new tests. Do not edit existing ones.

### Tests to add (`test/store.test.js`)

- Default: `add('a').priority === 'normal'`; `add('a', {}).priority === 'normal'`; `add('a', { priority: undefined })` is normal.
- Each valid value (`low`, `normal`, `high`) is stored as given.
- Invalid values throw `RangeError`: `'urgent'`, `'High'`, `''`, `null`, `1`. Also `add('  ', { priority: 'high' })` throws `TypeError`, showing the title check runs first.
- Unfiltered `list()` order: add low, normal, high, normal, high. Expect the high todos first, then normal, then low, each group in insertion order.
- `list({ priority: 'low' })` returns only low todos, in insertion order. Same for `high` and `normal`.
- `list({ priority: 'bogus' })` throws `RangeError`. `list()` and `list({})` return all todos.
- `complete` still works on a high todo, and `done` is kept in the copy.
- `formatList`: `[{ title: 'Pay rent', done: false, priority: 'high' }]` gives `[ ] !Pay rent`. A done high todo gives `[x] !Pay rent`. Low and normal give no `!`. A mixed list keeps its order.

### Risks

- **Silent changes to `list()` order.** Existing callers who relied on insertion order now get high-first sorting. The spec asks for this, but it is a behaviour change. The tests above cover the new order. Nothing else in the repo calls `list()`.
- **Invalid filter.** A typo in a filter fails loudly by design. The Developer should not silently fall back to all todos.
- **Other callers of `formatList`.** Todos without `priority` render as before, so there is no break.

### Verification

- `npm test` must show all existing tests passing and the new ones passing, with zero failures.
- Read the diff: no new files, no changes to `complete`, and the existing tests untouched.
