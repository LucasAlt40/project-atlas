## Plan: priorities for the todo store

**Goal:** add `low` / `normal` / `high` priorities to `createStore` (`src/store.js`) and show `!` for high-priority todos in `formatList` (`src/format.js`). Existing behaviour and the four existing tests must keep passing.

**Current state (read, not changed):**
- `src/store.js`: `add(title)` takes no options; `list()` takes no filter and returns copies in insertion order; `complete(id)` is unchanged by this work.
- `src/format.js`: `formatList` maps each todo to `[x]`/`[ ]` + title. It does not sort.
- `test/store.test.js`: four `node:test` tests. The `format` test passes plain objects with no `priority` field, so a missing priority must render as non-high.
- Baseline: `npm test` gives 4 pass, 0 fail.

**In scope:**
- `add(title, options)` with `options.priority`, defaulting to `'normal'`; anything else throws `RangeError`.
- Each todo stores `priority`.
- `list(filter)`: `filter.priority` narrows the result; with no filter, sort high → normal → low, stable within a priority.
- `formatList`: `!` immediately before the title for high-priority todos only.
- Tests for all of the above in `test/`.

**Out of scope:** `complete`, persistence, changing `README.md`, adding a new module, changing the sort or format of other fields.

**Module and dependency impact:** the change stays inside one module. `format.js` and `store.js` have no dependencies, and the new code adds none. `format.js` must not depend on `store.js`; it reads only the `priority` field on the object it is given. Keeping sort in `store.list()` and not in `formatList` means `formatList` renders the order it is handed.

**Decisions for the Developer to follow:**
1. **Validation order in `add`:** check title first (existing `TypeError`), then priority (`RangeError`). Use `const { priority = 'normal' } = options;` with `options = {}` as the default parameter. Only `undefined` means "use default"; `null` or `'High'` throws.
2. **Valid values are exact, lowercase strings.** Put them in one constant in `store.js`, e.g. `const PRIORITY_RANK = { high: 0, normal: 1, low: 2 };`. Validate with `name in PRIORITY_RANK`, or an equivalent check that does not match prototype keys such as `constructor`. Do not use an `indexOf` on an array of names in a way that could diverge from the sort.
3. **Filter validation (my choice, not in the spec):** `list({ priority })` with an invalid priority throws `RangeError`, matching `add`. A filter of `undefined` or `{}` returns everything, sorted. Mention this to the user as a decision they can change.
4. **Sort:** `Array.prototype.sort` is stable in the Node version this project uses (`node --test`), so sort a copy by `PRIORITY_RANK[t.priority]` and rely on that stability for insertion order. Do not add a counter or sequence field.
5. **Filtered results:** when `filter.priority` is given, return only that priority in insertion order. The rule is the same as the sorted case, so no separate branch is needed.
6. **`list()` still returns copies** (`{ ...t }`), so the new `priority` field is copied too and callers cannot mutate store state.
7. **`formatList`:** `const mark = t.priority === 'high' ? '!' : '';` then `` `[${t.done ? 'x' : ' '}] ${mark}${t.title}` ``. A missing `priority` renders as non-high, so the existing `format` test output is unchanged.
8. **Tests:** add them to `test/store.test.js`, in the same `node:test` style, since the file already covers `format`. Cover: default `normal`; explicit values; `RangeError` on `'urgent'`, `null`, and `'High'`; filter by each priority; no-filter ordering high → normal → low with insertion order kept within a level; invalid filter throws; `formatList` with `!` for high, none for others, and a todo without `priority`.

**Files to change:**
- `src/store.js`: `add` signature and validation, the rank constant, `list(filter)` with filter and sort, stored `priority` field.
- `src/format.js`: `formatList` `!` marker.
- `test/store.test.js`: new tests (existing four stay unchanged).

**Contracts:**
- `add(title, options?)` returns `{ id, title, done, priority }`.
- `list(filter?)` returns copies, sorted unless filtered. A filtered result is in insertion order.
- `formatList(todos)` output is unchanged for todos without `high`.

**Risks:**
- Adding a `RangeError` to `list()` for an invalid filter is a new error path. It is only reachable by bad input, so it does not break existing callers.
- The `in` check on a plain object can match inherited keys. Use `Object.hasOwn(PRIORITY_RANK, p)` or a `Set` to avoid that.
- `formatList` and `list` must agree on what `high` means. Both use the literal `'high'`; a single constant is not worth a new module here.

**Verification:**
- `npm test` must show all old tests and the new ones passing.
- Read the new tests against each decision above; each behaviour in the task maps to at least one assertion.
- I have not implemented anything in this step, so verification of the change happens in the Implement step.

Baseline `npm test` is 4/4 passing, so any failure after the change is from the change.
