## QA verdict: pass

The fix removes all five root causes in `src/cart.js`, and the existing and new tests pass. I found no regression. The remaining issues are edge cases the spec does not clearly cover, so they are low-severity.

**Repository state.** The fix is already committed in `03627b9` ("Atlas: step exec-2"), on top of `1f83dda`. The working tree is clean, so `git diff` is empty. I reviewed the change as `git show` of that commit.

### Root cause

The original `total()` had five independent defects, and the fix covers each one:

1. **Quantity ignored.** `sum += item.price` never used `qty`. Fixed by `cents += Math.round(item.price * 100) * item.qty`. This explains 3 × 19.90 → 19.9.
2. **Percent coupon returned the discount.** `sum * value / 100` gave 20 for 100 with OFF20. Fixed to `(100 - value)%`.
3. **No floor.** `sum - coupon.value` went below zero (5.00 − 10 = −5). Fixed by `Math.max(0, cents)`.
4. **Float drift.** Summing binary floats produced `0.30000000000000004`. Fixed by integer-cent arithmetic, divided by 100 only at return.
5. **Inherited coupon keys.** `COUPONS[couponCode]` resolved `constructor` and similar keys, which gave `NaN`. Fixed by `Object.prototype.hasOwnProperty.call`.

### Fix applied (commit `03627b9`)

- `src/cart.js`: integer-cent totals, correct percent formula, clamp at zero, own-property coupon lookup.
- `test/cart.test.js`: five regression tests (quantity, TENOFF floor, OFF20, cent rounding, unknown and inherited coupons).
- The public API is unchanged: `module.exports = { total }`. `total` has no other callers in the repository (Grep, read).

### Findings

- **Low (validation/precision), not a regression:** Non-integer `qty` or sub-cent prices can produce more than 2 decimals. The fixed-coupon path and the no-coupon path return `cents / 100` without rounding. Example: `total([{price: 0.01, qty: 1.5}])` should give 0.015 → returns `0.015`. The spec says totals must be rounded to cents. Qty is presumably an integer, so this is hardening beyond the reported bug. The decision is yours.
- **Low (precision):** `Math.round(item.price * 100)` is affected by float representation at exact half-cent prices. `1.005 * 100` is `100.49999999999999`, so `total([{price: 1.005, qty: 1}])` gives `1` instead of `1.01`. Sub-cent prices are unusual. Hardening would mean rounding the price with an epsilon, or rejecting sub-cent prices.
- **Low (coverage gaps):** These cases have no test:
  - the `HALF` coupon;
  - percent coupon rounding on odd cent amounts;
  - a multi-line cart with a coupon, and a quantity above 1 with a coupon;
  - a partial fixed coupon (`TENOFF` on 15 should give 5).
