## Plan: priorities for the todo store

**Goals.** Each todo carries a `priority` of `'low' | 'normal' | 'high'`. `store.add` validates it, `store.list` can filter by it and sorts by it when unfiltered, and `formatList` marks high-priority items with `!`. Existing behaviour and the four current tests stay as they are.

**In scope.**
- `src/store.js`: `add(title, options)`, `list(filter)`.
- `src/format.js`: `formatList`.
- `test/store.test.js`: new tests for all of the above. This is the only test file, and it already holds the format test, so the new tests go there too.

**Out of scope.** The `complete` API, ids, the `README.md` (optional one-line note, not required), and any new module. Nothing else in the project depends on these files, so the change is contained.

**Modules and dependencies.** `store.js` owns the data and its rules: validation, ordering and filtering. `format.js` is pure rendering and has no dependency on the store. The two stay decoupled: `format.js` checks `t.priority === 'high'` as a presentation rule and does not import anything from the store. There are no third-party dependencies, so none are added.

**Decisions the Developer must follow.**
1. **Default and validation.** `add(title, options = {})` reads `priority` with a default of `'normal'` for `undefined`. Any other value that is not one of the three strings throws `RangeError`. Matching is case-sensitive, so `'High'` and `null` both throw. The title check runs first and keeps throwing `TypeError`.
2. **Stored shape.** Each todo becomes `{ id, title, done, priority }`. It is stored as a plain field, not in a side map.
3. **Ordering without mutating state.** Sort a copy, never the internal `todos` array. Rank is `high=0, normal=1, low=2`. Array sort is stable in Node 12+, which keeps insertion order within a priority. Keep returning copies (`{ ...t }`) so callers cannot change internal state.
4. **Filtering.** `list()` with no argument behaves as before, except that it now returns sorted output. `list({ priority })` returns only todos of that priority, in insertion order. An invalid `filter.priority` throws `RangeError`, the same rule as `add`. The spec did not cover this case; this plan chooses to throw rather than return an empty list, so a typo is caught early.
5. **Formatting.** `formatList` renders `[${mark}] ${prefix}${title}`, where `prefix` is `'!'` only when `priority === 'high'`. Todos without a `priority` field, such as the existing `format` test's inputs, render exactly as before.
6. **No new abstractions.** No shared priority module, no class, no config. A local `PRIORITIES` constant in `store.js` is enough.

**Files and contracts to change.**
- `src/store.js`: `add` signature gains an optional `options` argument. `list` gains an optional `filter` argument and a sort. The returned todo object gains `priority`.
- `src/format.js`: the line template gains the `!` prefix for high priority.
- `test/store.test.js`: add tests listed below. Existing tests stay as they are.

**Tests to add (in `test/store.test.js`).**
- Default priority is `'normal'`. Explicit `'low'` and `'high'` are stored.
- Invalid priorities (`'urgent'`, `'High'`, `null`) throw `RangeError`. An empty title still throws `TypeError`.
- Unfiltered `list()` sorts high, normal, low. Within a priority, insertion order is kept (use several todos per priority, interleaved on insert).
- `list({ priority: 'low' })` returns only low todos, in insertion order. An invalid filter priority throws `RangeError`.
- `list()` returns copies: mutating a returned item does not change the store.
- `formatList` prints `[ ] !Title` for high and unchanged output for normal and low. Legacy objects with no `priority` field also render unchanged.

**Risks.**
- The unfiltered `list()` order changes. This is required by the spec, but any caller that relied on insertion order will see a difference. Within this project there are no other callers.
- The priority strings are duplicated between `store.js` (validation and ranking) and `format.js` (the `'high'` check). A typo in one would not be caught by the other. The new tests cover both, which limits that risk.
- Sorting on every `list()` call is O(n log n). That is fine for an in-memory store of this size and not worth optimising now.

**Verification.** Run `npm test` (`node --test`). The baseline is 4 passing tests, confirmed above. After the change, the 4 existing tests must still pass alongside the new ones. The new behaviour is covered by the tests listed above.
