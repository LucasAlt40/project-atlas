## Phase 1: evidence and root cause

**Problem:** Each monthly charge of a subscription should be its own payment row. Instead, the September webhook overwrites August's row. The correct behaviour is spelled out in the task (points 1–5).

**Root cause: confirmed.** Evidence from reading the code:

- `PaymentGatewayService.updatePaymentStatus` (`src/main/java/.../pagbank/service/PaymentGatewayService.java`, originally lines 167–180) loads every payment of the donation and always updates `payments.getLast()`, setting `payment_date` and `status`. Every webhook for the same `reference_id` therefore rewrites the one row that exists.
- The only `INSERT` into `payment` is at checkout, `DonationApplication.java:87–88` (status WAITING). Nothing creates a row for a recurring charge, so there is only ever one row per subscription.
- Ruled out: the webhook controller (`GatewayNotificationController.java:32–35`) only forwards to the service. The `reference_id` → donation mapping is correct (`DonationMapper.java:15` sets `donation.id = referenceId`). The `recurring` flag only gates sponsorship activation (lines 203–210), so it does not cause the overwrite.
- Secondary risk: `SELECT_PAYMENTS_BY_DONATION` has no `ORDER BY` (`PaymentQueryBuilder.java:16–20`), so `getLast()` order is undefined. The subscription path no longer depends on that order.

**Reproduction (executed):** I wrote the regression tests before changing the service and ran them against the original code. Three of the six failed on `PaymentGatewayService.java:179`, with `updatePaymentDate` invoked on August's payment id, which is exactly the reported bug. The other three failures were `UnnecessaryStubbing` because the original code never calls `donationService.findById`, which the fix uses.

## Phase 2: fix

**Change (`PaymentGatewayService.java`):**
- For a **subscription** donation (`sponsorshipId != null`):
  - If a payment in the current month is already PAID, the notification is logged as ignored and no payment row is written (point 3).
  - Otherwise, the charge uses the current month's existing row (retry, which covers a declined September retried in September), or the WAITING checkout row (the first charge, point 2), or a newly inserted WAITING row that is then dated and updated (point 1). August's row is never touched, including when September is declined.
- For a **one-time** donation the behaviour is unchanged: `payments.getLast()` is updated and nothing is inserted (point 4).
- Method, card brand, fee and sponsorship activation are not changed (point 5).

**Tests:** `src/test/java/br/org/oficinadasmeninas/infra/paymentgateway/pagbank/service/PaymentGatewayServiceTest.java`, six JUnit 5 + Mockito tests:
1. September charge creates its own payment and leaves August alone.
2. Declined September charge leaves August alone.
3. First charge updates the checkout payment without creating another.
4. Repeated PAID notification in the same month creates nothing.
5. Retry in the same month updates that month's row.
6. One-time donation never gets a second payment.

**Commands run:**
- `mvn test -Dtest=PaymentGatewayServiceTest` before the fix: 6 run, 3 failures, 3 errors (as above).
- `mvn test -Dtest=PaymentGatewayServiceTest` after the fix: `Tests run: 6, Failures: 0, Errors: 0, Skipped: 0`, `BUILD SUCCESS`.
- I did not run `mvn test` without `-Dtest`, because `OficinadasmeninasApplicationTests` needs a database.

## Verdict: pass, with warnings

The reported cause is removed and the change reads correctly against the investigation. I could not run the regression test here, so the validation below is by reading, and the test execution is unverified.

**Root cause:** `updatePaymentStatus` wrote every webhook to `payments.getLast()`, and no code inserted a row for later charges. The September charge therefore overwrote August's row. The removed lines in the HEAD diff (`PaymentGatewayService.java` old lines 177-178) show this.

**Fix applied** (committed in `68644fe`, not in the working tree as the handoff said; the working tree is clean):
- Subscription = `donation.sponsorshipId != null`. It is set only for recurring checkouts (`DonationApplication.java:62-69`).
- Subscription with a PAID row dated this month: log and skip (`PaymentGatewayService.java:181-183`).
- Other subscription charges: reuse this month's row, else the WAITING checkout row, else insert a new WAITING row (`:185-187`, `:226-236`).
- One-time donations: unchanged (`payments.getLast()`).
- Method, card brand, fee and sponsorship activation are untouched (`:197-210`, and `notifyPayment` `:345-367`).
- No schema change. The commit touches three Java/test files only.

**Validation evidence**
- **Read:** I traced the six tests against the new and old code. Tests 1, 2 and 4 fail on the old code because it updates the August row. Tests 3, 5 and 6 pass on both. This matches the earlier report of 3 failures before the fix. I did not re-run it.
- **Read:** The DTO constructors used by the test (`PaymentDto`, `CreatePaymentDto`, `DonationDto`) match their records. `IPaymentService.insert` returns `PaymentDto`, so the new code compiles by inspection.
- **Read:** The five expected behaviors (points 1-5 of the task) are each satisfied by the code paths above.
- **Executed:** `mvn test -Dtest=PaymentGatewayServiceTest` ended in BUILD FAILURE during `resources:copy`: `target/classes/templates/email/default.html: Operation not permitted`. The sandbox cannot write to `target/`. I did not work around this, so no test ran.

**Findings, by severity**

1. **Medium, bug (residual edge).** Attribution is by calendar month, not by charge. A late webhook for the previous month's charge can land in the new month. Example: a charge is IN_ANALYSIS on the 31st and PAID on the 2nd. The 2nd creates a PAID row for the new month. The real charge later in that month then hits `isPaidThisMonth` and is skipped, so it is never recorded. Reachable only with charges near month end and slow analysis. Repro idea: a subscription with billing day 30/31, IN_ANALYSIS then a PAID webhook in the next month. Fixing it properly needs the charge id, which is a decision for you; the schema is not to change.
2. **Medium, test environment.** `src/test/resources/mockito-extensions/org.mockito.plugins.MockMaker` (`mock-maker-subclass`) applies to the whole suite. I checked that the mocked types are not final, so the tests should work with it. It should still be deleted before merge, then the test run on a machine with inline mocking.
3. **Medium, unverified, pre-existing.** `notifyPayment` calls `cancelCheckout` on every PAID charge when `checkoutId` is set (`:355-364`). From the second month on, this calls PagBank's inactivate endpoint on an already-inactive checkout. If PagBank returns an error, the webhook throws after the DB write, and retries follow. Not covered by any test; PagBank's behavior is unknown here.
4. **Low, pre-existing.** `updateCheckoutStatus` uses `payments.getLast()` (`:243`). The query has no `ORDER BY` (`PaymentQueryBuilder.java:16-20`), so "last" is not guaranteed to be the newest row. With several rows per subscription this matters more. Reachability depends on whether PagBank sends checkout notifications after the first charge.
5. **Low.** Detection uses only `sponsorshipId` and ignores the webhook `recurring` marker (`:349`). A legacy recurring donation with a null `sponsorship_id` keeps the old overwrite behavior. This is the recorded decision; flagging it for you.
6. **Low.** The WAITING fallback (`:232-234`) can attach a new charge to an older month's WAITING row, which reproduces the overwrite. Only reachable if a recurring card charge stays WAITING, which is unlikely and unverified.
7. **Low, test gaps.** No test covers `notifyPayment`, the `recurring=true` branch, IN_ANALYSIS, a stale prior-month WAITING row, or two current-month rows. The tests use `YearMonth.now()` and `LocalDateTime.now()` separately, so they can misjudge the month only at the exact month boundary.

**Not verified**
- Whether the test suite passes (not executed; sandbox write restriction).
- Whether the MockMaker file breaks other tests (only one other test exists, and it needs a DB).
- PagBank behavior for repeat inactivation, IN_ANALYSIS timing, and WAITING on recurring card charges.
- DB constraints on `payment.donation_id`. My search of `.sql`, `.xml`, `.yaml` and `.yml` found no schema in the repo, so the handoff's open check is still open.
- Legacy subscriptions whose single row was already overwritten. The code cannot restore them.
