## Plan: `slugify(text, options)`

**Goal:** add `src/slugify.js` exporting `module.exports = { slugify }`, plus `test/slugify.test.js` using `node:test` and `node:assert`.

**Scope.** In: the new module and its tests. Out: any change to `package.json`, `README.md`, or any other file. No dependencies, no shared helpers, no folders beyond `src/` and `test/`.

**Modules and architecture.** One leaf module with no imports. It is a pure function with no I/O, so there are no layers, boundaries or risks beyond the function's own contract. Adding an abstraction (a class, a options schema, a plugin) is not justified by the task.

**Decisions the Developer must follow:**

1. **Normalization order:** `text.normalize('NFD')` → strip combining marks `/[\u0300-\u036f]/g` → `toLowerCase()` → replace `/[^a-z0-9]+/g` with `-` → trim leading and trailing `-`. NFD is used rather than NFKD so compatibility characters are not silently expanded beyond what the spec asks for. Characters with no decomposition (`ø`, `ß`, `æ`) become `-`, which is what rule 3 requires.
2. **Type check:** `if (typeof text !== 'string') throw new TypeError(...)`. Check this before anything else.
3. **Options:** default to `{}` and read `maxLength` as `const { maxLength } = options || {}`, so `null` is tolerated the same as `undefined`.
4. **Invalid `maxLength`:** the spec does not say. Decision: if `maxLength` is provided and is not a positive integer, throw `RangeError`. Silently ignoring it would hide caller bugs. The Developer must follow this choice; if the person wants it ignored instead, change only that branch.
5. **Truncation algorithm** (applies only when `slug.length > maxLength`):
   - `cut = slug.slice(0, maxLength)`
   - if `slug.charAt(maxLength) === '-'`, the cut already ends on a word boundary, so return `cut`
   - otherwise `idx = cut.lastIndexOf('-')`; if `idx > 0`, return `cut.slice(0, idx)`
   - otherwise (the first word does not fit) return `cut` as a hard cut
   - Since the slug never has a leading dash or a double dash, the result never ends with `-`.
6. Empty or symbol-only input returns `''`.

**Files and contracts:**
- `src/slugify.js` (new): `slugify(text, options?) → string`; throws `TypeError` for non-string `text`, `RangeError` for invalid `maxLength`.
- `test/slugify.test.js` (new).

**Test cases to write:**
- The five examples from the spec: `' Olá, Mundo! '`→`ola-mundo`, `'Ação & Reação'`→`acao-reacao`, and the three `maxLength` cases (9→`hello-big`, 8→`hello`, `supercalifragilistic`/5→`super`).
- Lowercasing; `ü`, `ç`, `ã`, `é` removal; runs of punctuation collapse to one `-`; no leading or trailing `-`; `''` and `'!!!'` return `''`.
- `maxLength` exactly equal to the length of the slug returns it unchanged; `maxLength` falling on a `-` boundary returns the full words before it.
- `TypeError` for `123`, `null`, `undefined`, and an object; `RangeError` for `0`, `-1`, `1.5`, `'5'`.

**How it will be verified:** run `npm test` (which runs `node --test`) from the worktree root and confirm all tests pass with no failures. Also confirm that `git status` lists only the two new files.

**Risks:** the main one is the boundary logic in step 5 (off-by-one at `maxLength`), which the boundary tests cover. Another is Unicode normalization differing across Node builds; the chosen NFD approach relies only on the standard combining-mark range, so this risk is low.

**Open choice for the person:** the invalid-`maxLength` behavior (decision 4). I chose `RangeError`; it is a one-branch change if they prefer ignoring it.
