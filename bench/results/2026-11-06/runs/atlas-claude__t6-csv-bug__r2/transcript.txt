## Verification report: parseCsv fix (pass)

**Root cause.** `parseCsv` split the text on `\n` and then on `,` before it looked at any quote. Every reported bug follows from that:
- Commas inside quotes split fields (`"Lisbon, Portugal"`).
- `""` was never unescaped.
- A trailing `\n` produced a final row with one empty field.
- `\r` from CRLF stayed in the last field.
- A newline inside quotes split the record.

Quotes were stripped only when a field started and ended with `"`, so unclosed quotes never threw.

**Fix applied (committed in `5a4dd7e`).** `src/csv.js` is now a single-pass character scanner with an `inQuotes` flag. It handles quoted commas, `""` as one quote, newlines inside quotes, and `\n` or `\r\n` as record ends. A trailing newline doesn't add a row, `''` returns `[]`, and an unclosed quote throws `SyntaxError`. `module.exports = { parseCsv }` is unchanged. The worktree is clean, so the handoff's "M src/csv.js" is stale: the fix is already in HEAD.

**Evidence**
- *Executed:* `npm test` on the worktree: 10 tests, 10 pass, 0 fail.
- *Read:* the pre-fix code (`3a9f620`) against the 8 added tests. The `a,,b` test passes on the old code, and the other 7 fail. This gives 3 pass and 7 fail, not the "2 pass" in the handoff. I could not re-run the old code: the sandbox allows only the project's test commands and git reads.
- *Read:* the scanner against edge inputs. I traced `""`, `""""`, `"""` (throws), `"a""b"`, `a,"`, `a,b\r\n`, `"abc"\r\n`, and `a,` (gives `['a','']`). All give the expected results.
- *Read:* the only consumers are `src/csv.js` and `test/csv.test.js`; no other module calls `parseCsv`. The output shape is unchanged.
- *Read:* the change is minimal and stays in one function, with no new dependencies.

**What I could not verify**
- The pre-fix failure counts are from reading the code, not from running it.
- Behaviour on real CSV files, Excel exports, and very large inputs was not run.
- Whether blank lines and lenient quote handling match what the users expect is a product decision.

**Findings** (in the block below; none block the fix)
- Blank lines still produce a row with one empty field, so a file ending in `\n\n` keeps a phantom row. This is the same symptom as the reported trailing-newline bug, but it is not covered by the reported examples.
- Several edge cases have no regression test.
- Lenient quote handling and the trailing lone `\r` are decided behaviour, but no test pins them.
- A leading UTF-8 BOM stays in the first field. This predates the change and was not reported.
