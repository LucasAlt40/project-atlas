## Plan: priorities for the todo store

**Goal:** Add a `priority` (`'low' | 'normal' | 'high'`, default `'normal'`) to todos in `src/store.js`, with filtering and ordering in `list()`, and a `!` marker for high-priority todos in `src/format.js`. Existing behaviour and the tests in `test/` must keep passing.

**Current state**
- `src/store.js` (`createStore`): one closure holding `todos` and `nextId`. `add(title)` validates the title (TypeError), then pushes `{id, title, done}`. `list()` returns shallow copies in insertion order. `complete(id)` is unaffected.
- `src/format.js` (`formatList`): one line per todo, `[x] title` or `[ ] title`.
- `test/store.test.js`: `node --test` with `require`-style imports. Four tests: add/list, complete, empty title, format. The existing tests only use default-priority todos, so they stay valid.
- `package.json`: `"test": "node --test"`. No dependencies.

**In scope**
- `add(title, options)` accepts `options.priority`, validates it, and stores it on the todo.
- `list(filter)` accepts `filter.priority` and sorts unfiltered results high → normal → low, stable within a priority.
- `formatList` prefixes the title with `!` when `priority === 'high'`.
- Tests in `test/store.test.js` for the new behaviour.

**Out of scope**
- `complete`, id generation, title validation (apart from ordering of checks below).
- Any new module, priority constants exported across files, or persistence. The store is in-memory and nothing else reads priority.

**Decisions the Developer must follow**
1. **Validation in `add`.** Missing `options`, or `options.priority === undefined`, means `'normal'`. Any other value that is not exactly `'low'`, `'normal'` or `'high'` throws `RangeError`. This includes `null`, `''`, and `'High'` (case-sensitive). Use optional chaining (`options?.priority`) so `add('x')` and `add('x', undefined)` work.
2. **Check order in `add`.** Title check first (TypeError, as today), then priority check (RangeError), both before `nextId++`. A rejected add must not consume an id or push a todo.
3. **Storage.** The todo object becomes `{ id, title, done, priority }`. The priority is stored as the validated string.
4. **Ranking.** A small non-exported lookup inside `store.js`, e.g. `const RANK = { high: 0, normal: 1, low: 2 };`. No new module.
5. **Sorting never mutates storage.** In `list()`, build the mapped copies first, then filter and sort that copy. `Array.prototype.sort` is stable in Node, so insertion order is preserved within a priority. Do not sort `todos` in place.
6. **Filter semantics.** `list()` and `list({})` mean no filter. If `filter.priority` is present (not `undefined`), return only todos with that priority, in insertion order. An invalid filter priority throws `RangeError`, the same rule as `add`, rather than silently returning `[]`. This is a choice I am making; the Developer should keep it.
7. **Format.** For `priority === 'high'`, render `[ ] !Pay rent` / `[x] !Pay rent`. Other priorities, and todos with no `priority` field, render exactly as today. The check is `t.priority === 'high'`; `formatList` does not import anything from `store.js`.

**Files and contracts to change**
- `src/store.js`: `add(title, options)` signature and return shape (adds `priority`); `list(filter)` signature and ordering.
- `src/format.js`: `formatList` line rendering.
- `test/store.test.js`: new tests appended; existing tests untouched.
- `README.md`: optional one-line note on the new API. Only if the Developer judges it useful; not required.

**Tests to add** (`node --test`, same style as the existing file)
- `add` defaults to `'normal'` with and without options.
- `add` accepts `'low'`, `'normal'`, `'high'` and stores them.
- `add` throws `RangeError` for `'urgent'`, `'High'`, `null`, and `''`; a rejected add leaves `list()` unchanged, and the next add still gets the expected id.
- `list()` without a filter sorts high, normal, low, with insertion order kept within each group (add a mix of priorities in interleaved order to check stability).
- `list({ priority: 'low' })` returns only low todos, in insertion order.
- `list({ priority: 'bogus' })` throws `RangeError`.
- `list()` does not change internal order: a second `list()` call after a sorted call still returns the same result (guards against in-place sorting).
- `formatList` shows `[ ] !title` and `[x] !title` for high; normal and low lines are unchanged; the existing format test still passes.

**Architectural impact and risks**
- The only observable behaviour change for existing callers is the ordering of `list()` without a filter. This is what the task asks for. Anyone relying on insertion order would see a change, and the risk is limited because the store is in-memory with no consumers in the repo.
- Keeping the priority check in `add` and the rank table in `store.js` means `format.js` depends only on the `priority` field value, not on the store module. This keeps the dependency direction one-way and avoids a new shared module.
- Throwing on an invalid filter (decision 6) is stricter than the spec states. If the person prefers `[]`, it is a one-line change, but the default I recommend is to throw for consistency.

**Verification**
- Run `npm test` (which runs `node --test`) from the worktree root. All old and new tests should pass.
- Spot-check that `list()` on a store with interleaved priorities returns high, normal, low groups in insertion order, and that the internal array is unchanged between calls.
