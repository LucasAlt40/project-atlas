**Root cause: confirmed.** Four defects in `src/cart.js`, all reproduced by the new tests before the fix:

1. **Quantity ignored** (line 16): the loop summed `item.price` and never multiplied by `item.qty`. This gives 19.9 instead of 59.7.
2. **Percent coupon returned the discount, not the price** (line 21): `sum * value / 100` gave 20 for OFF20 on 100. It now uses `sum * (100 - value) / 100`, which gives 80.
3. **No floor or rounding** (line 26): a fixed coupon larger than the cart produced -5, and float sums produced values like 0.30000000000000004. The result is now `Math.max(0, Math.round(sum * 100) / 100)`.
4. **Unknown coupons not fully ignored** (line 18): `COUPONS[couponCode]` also reads inherited properties, so `'toString'` returned a function and the total became NaN. It now uses `Object.hasOwn(COUPONS, couponCode)`.

Git history shows no recent change to `src/cart.js`, so the bugs were in the original code. The export `module.exports = { total }` is unchanged.

**Files changed**
- `src/cart.js`: the four fixes above.
- `test/cart.test.js`: added regression tests for quantity, the fixed coupon floor, the percent coupon, cent rounding, and unknown coupons (including `toString`). The two existing tests are unchanged.

**Residual risks**
- Rounding uses `Math.round(x * 100) / 100`, which works on binary floats. Half-cent cases can round the wrong way (for example, 1.005 may become 1.00 rather than 1.01). The current tests don't cover these.
- Rounding happens only once, on the final total, not per line item. If the customer expects per-line rounding, the totals could differ by a cent.
- A cart item without `qty` gives NaN. The JSDoc type requires `qty`, so I did not add a default.
- `Object.hasOwn` needs Node 16.9 or later. `node --test` already implies Node 18 or later, so this should be fine.

## Final report

**Root cause.** `src/cart.js` had four independent defects:
1. It summed `item.price` and ignored `item.qty`.
2. It computed the percent coupon as `sum * value / 100`, which returns the discount instead of the remaining price.
3. It returned the raw float sum, with no floor and no cent rounding.
4. It looked up `COUPONS[couponCode]`, so inherited keys such as `toString` were treated as coupons.

**Fix applied (commit `2ba98ed`).**
- `sum += item.price * item.qty`
- `Object.hasOwn(COUPONS, couponCode)` guards the lookup.
- `sum * (100 - coupon.value) / 100` for percent coupons.
- `return Math.max(0, Math.round(sum * 100) / 100)`, rounded once on the final total.
- The `module.exports = { total }` API is unchanged.

**Validation evidence.**
- *Executed:* `npm test` (`node --test`) passes 7/7, including the five added tests: qty multiplication (59.7), TENOFF floor (0), OFF20 (80), cent rounding (0.3), and unknown coupons including `toString` (10).
- *Read:* each new test maps to one reported bug. Without the fix, the qty test gives 19.9, the OFF20 test gives 20, the TENOFF test gives -5, the rounding test gives 0.30000000000000004, and `toString` gives NaN. I traced these from the code; I did not execute them against the old code.
- *Read:* `Math.max(0, …)` also handles `-0`, since `Math.max(0, -0)` returns `+0`.

**Side effects and callers.** The only caller in the repo is the test file. The module has no other dependents in the tree.

**Findings (ordered by severity; outcome stays pass):**
- **medium / validation — missing `qty` now yields NaN.** `price * undefined` is NaN, and NaN passes through `Math.round` and `Math.max`. The old code ignored `qty` and returned the price sum, so a caller omitting `qty` now gets NaN instead. The JSDoc marks `qty` as required, so this is arguably correct, but it is a behavior change. Decide whether to validate input or leave it.
- **low / rounding — half-cent values can round down.** Floats make `x.xx5` values land just below the midpoint. For example, 1.005 × 100 is 100.49999999999999 in IEEE doubles, so a total of 1.005 rounds to 1.00, not 1.01. This is from reading the IEEE arithmetic, not from running it. The customer's rounding rule (half-up, half-even, or cents-as-integers) is a business decision. Tell me which one you want, and I'll add a test for it.
- **low / test coverage — gaps in the regression tests.** There is no test combining qty with a percent coupon (for example 19.9 × 3 with OFF20 → 47.76), no half-cent case, and no case for negative or non-numeric input.
- **low / input — negative prices or quantities are not rejected.** They reduce the total and are then floored to 0, which can hide bad data.
- **low / coupon codes — matching is case-sensitive.** `tenoff` is silently ignored. This is consistent with "unknown coupons are ignored" but is worth confirming.

**Could not verify.**
- Running the tests against the pre-fix code, to prove each regression test fails without the fix. I'm read-only and cannot modify files.
- Half-cent behaviour by execution. It is from reading the arithmetic only.
- Node version compatibility. `Object.hasOwn` needs Node 16.9 or later, and `package.json` declares no `engines` field.
