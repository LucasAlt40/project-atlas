## Architect plan: todo priorities

### Goals
- Todos carry a validated `priority`, defaulting to `normal`.
- `store.list(filter)` can filter by priority and, with no filter, returns todos high → normal → low, keeping insertion order within each priority.
- `formatList` prefixes high-priority titles with `!`.
- Existing behaviour and tests are unchanged.

### Out of scope
- Changing `complete`, id generation, or title validation.
- Any priority-based behaviour beyond `list` and `formatList` (no changes to sorting in other places, no persistence).
- New modules, classes, or shared constants files. The project is a single CommonJS file with no dependencies, so a small local constant is enough.

### Modules and dependencies
- `src/store.js` is the only owner of priority rules: the allowed values, validation, and ordering. A module-level `const PRIORITY_RANK = { high: 0, normal: 1, low: 2 }` covers both validation (`in` check) and sort order, so there is one source of truth inside the file.
- `src/format.js` only needs to know that `'high'` gets a marker. It does not import from the store. Coupling is limited to the string `'high'` and the `priority` field name, which is acceptable at this size.
- No changes to `package.json` or `README.md` are needed, though a one-line README note on priorities would be reasonable.

### Decisions the Developer must follow
1. **Validation in `add(title, options = {})`:**
   - If `options.priority === undefined`, use `'normal'`.
   - Otherwise, the value must be exactly one of the keys of `PRIORITY_RANK`. Matching is case-sensitive, so `'High'` is rejected. `null` is also rejected.
   - Anything else throws `RangeError` with a message naming the allowed values.
   - Validate priority before creating the todo, so an invalid call doesn't consume an id. The title check should still run first, as it does now.
2. **Stored shape:** `{ id, title, done, priority }`. `list()` already copies with spread, so `priority` comes through automatically.
3. **Filter validation (my call, not in the spec):** `list({ priority })` with a value not in `PRIORITY_RANK` throws `RangeError`, the same as `add`. This avoids a silent empty result from a typo. A filter object without `priority` (or no argument at all) returns everything. Tell me if you'd rather get an empty array.
4. **Ordering:**
   - Filter and sort on a copy: `todos.filter(...)` / `[...todos]` then `.sort(...)`. Never sort the internal `todos` array, so insertion order is preserved for later calls.
   - Array sort is stable in Node 12+, so comparing `PRIORITY_RANK[a.priority] - PRIORITY_RANK[b.priority]` keeps insertion order within a priority.
   - Sorting applies when there is no filter. With a filter, all results share one priority, so insertion order is already correct; sorting them too is harmless.
   - Todos created before this change would have no `priority`. The codebase has no such data, so do not add fallback handling.
5. **Format:** `formatList` renders `[x] !Title` or `[ ] !Title` when `t.priority === 'high'`, and is otherwise byte-identical to today. The `!` goes immediately before the title, with no extra space. Todos without a `priority` field (as in the existing `format` test) render exactly as before.
6. **No new abstractions:** no priority class, no enum object exported, no changes to the store's public shape beyond `priority` and the `list` filter argument.

### Files and contracts to change
- `src/store.js`:
  - Add `PRIORITY_RANK` constant.
  - `add(title, options = {})` accepts `{ priority }` and returns a todo that includes `priority`.
  - `list(filter = {})` filters by `filter.priority` when given and returns copies sorted high → normal → low when no priority filter is given.
- `src/format.js`: `formatList` adds the `!` marker for high priority.
- `test/store.test.js`: add tests (existing four stay as they are).
- `README.md` (optional): one sentence describing priorities.

### Tests to add in `test/store.test.js`
- `add` without options gives `priority: 'normal'`.
- `add` with `'low'`, `'normal'`, `'high'` stores each value.
- `add` with `'urgent'`, `'High'`, `null` throws `RangeError`, and no todo is added afterwards (check `list()` length).
- `list({ priority: 'high' })` returns only high todos, in insertion order.
- `list({ priority: 'urgent' })` throws `RangeError`.
- `list()` sorts high, normal, low, and within a priority keeps insertion order (use mixed inputs such as low, high, normal, high, low to exercise ties).
- `list()` does not reorder the internal store: a second `list()` call after a filter still gives the same order.
- `formatList` with `{ title: 'Pay rent', done: false, priority: 'high' }` gives `[ ] !Pay rent`. Also cover a done high todo (`[x] !…`) and a non-high todo with a priority field (no `!`).

### Risks
- **Sort stability** relies on the engine's stable `Array.prototype.sort` (guaranteed in Node 12+, and the project uses `node --test`). Acceptable, and the tie-order test catches a regression.
- **Mutating internal state:** sorting `todos` in place would break insertion order for later calls. The test for repeated `list()` calls guards against it.
- **Strict validation** may surprise callers passing `null` for "no priority". That is intentional given the spec, which only defines the three values.
- **String coupling:** `format.js` hard-codes `'high'`. If priorities change later, both files must be updated. Acceptable at this size.

### Verification
- `npm test` must show the four existing tests and all new tests passing.
- Review that `format.js` output for todos without `priority` is unchanged, as the existing `format` test already checks.
