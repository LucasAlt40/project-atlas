**Summary of the fix**

The root cause is in `total()` in `src/cart.js`. It has four bugs that match the four customer reports, plus one related bug:

1. **Quantity ignored.** The loop summed `item.price` and never used `item.qty`. Now it sums `item.price * item.qty`.
2. **Percent coupon returned the discount, not the total.** `sum * value / 100` gave 20 for 100 at 20% off. Now it computes `sum * (100 - value) / 100`, which gives 80.
3. **Fixed coupon could go negative.** `5 - 10` gave -5. The result is now clamped with `Math.max(sum, 0)`.
4. **No rounding.** Totals such as 0.30000000000000004 were returned as-is. The final value is now rounded to cents with `Math.round(x * 100) / 100`.
5. **Unknown coupons could match inherited properties.** `COUPONS['constructor']` is truthy, so it produced `NaN`. The lookup now uses `Object.prototype.hasOwnProperty.call`, so unknown codes are ignored.

The public API is unchanged: `module.exports = { total }`.

**Files changed**
- `src/cart.js`: fixes to `total()` as described above.
- `test/cart.test.js`: new regression tests for quantity, the percent coupon, the fixed coupon floor, cent rounding, and unknown or inherited coupon names. The two existing tests are untouched.

**Verification status**

I could not run anything in this environment, so nothing below has been executed. I checked the arithmetic by reading:
- `19.9 * 3` rounds to `59.7`.
- `0.1 * 3` rounds to `0.3`.
- `100 * 80 / 100` is `80`.
- `5 - 10` clamps to `0`.
- `'constructor'` and `'toString'` fall through to no coupon, so the total stays `10`.
- The existing tests (single item at 10, empty cart at 0) are unaffected.

Command to run:
- `npm test` (runs `node --test`). Expected: all 8 tests pass, with 0 failures.

**Residual risks**
- `Math.round(x * 100) / 100` can round some half-cent values the wrong way because of binary float representation. For example, `1.005` becomes `1` in cents, not `1.01`. This affects only exact half-cent results. A decimal-safe rounding helper would fix it, but I kept the change minimal.
- The code does not validate `qty` or `price`. Negative, non-integer or missing values pass straight through. The reports did not cover this, so I did not add validation.
- The percent discount is applied before rounding. Multi-item carts may differ by a cent from a per-line rounding policy, if the business requires one.

## QA verification report: cart total fix

**Scope:** `src/cart.js` (current state) and `test/cart.test.js`. I did not use the original version, so I could not confirm line by line what changed.

### Root cause vs. fix

The reported symptoms map to these lines in the current `src/cart.js`:

| Symptom | Cause | Current code | Status |
|---|---|---|---|
| 3 × 19.90 shows 19.9 | quantity ignored | `sum += item.price * item.qty` (L16) | Removed |
| TENOFF on 5.00 gives -5 | fixed discount not clamped | `Math.max(sum, 0)` (L29) | Removed |
| OFF20 on 100 gives 20 | percent applied as the discount, not the remainder | `sum * (100 - value) / 100` (L23) | Removed |
| Long decimals like 0.30000000000000004 | no rounding | `Math.round(... * 100) / 100` (L29) | Removed for normal values |
| Unknown or inherited coupon | prototype lookup | `hasOwnProperty.call` (L18) | Removed |

The fix addresses the cause of each reported symptom, not just the displayed value. Clamp and rounding happen once, at the end, so intermediate discount math is not rounded.

### Side effects

### Findings, ordered by severity

1. **Medium, correctness: half-cent values round down.** `Math.round(x * 100)` is affected by binary float representation. `total([{ price: 1.005, qty: 1 }])` yields `1`, not `1.01`, because `1.005 * 100` is `100.49999999999999`. This is a rounding-rule question. The spec says "rounded to cents" but not which rule. Recommendation: use a decimal-safe rounding helper and add a test for `1.005`. Not a reported symptom, so it does not block this fix.

2. **Low, validation: NaN is returned for missing or non-numeric values.** `total([{ price: 10 }])` gives `NaN`, because `Math.max(NaN, 0)` is `NaN`. The spec says totals must be numbers, and `NaN` is typed as one but is not a valid total. Not a reported symptom.

3. **Low, data masking: negative items are silently absorbed by the clamp.** `total([{ price: 10, qty: 1 }, { price: -20, qty: 1 }])` returns `0`. Bad data is hidden, not rejected. This follows from "never negative", but it can hide a data error from upstream.

4. **Low, product question: coupon codes are case-sensitive and whitespace-sensitive.** `'tenoff'` or `' OFF20'` are silently ignored. This matches "unknown coupons are ignored", but it may surprise customers. Needs a product decision, not a code change.

### Test coverage gaps

- No positive fixed-coupon case: `TENOFF` on 25 should give 15. Only the clamp case (5 → 0) is covered.
- No fractional percent case: `OFF20` on `19.9 × 3` should give 47.76.
- No multi-item case with float noise, such as `0.1 + 0.2`.
- No `HALF` coupon test, no percent over 100 test, and no exact-boundary test (`TENOFF` on exactly 10).
- No half-cent test (see finding 1).
- No `NaN` or undefined `qty` test (see finding 2).

### Verdict

The fix removes the cause of all four reported symptoms, based on reading. I found no regression path from the only caller. The open items are a rounding-rule decision and input validation. Neither was reported, and neither blocks this step.

### What I could not verify

- Did `npm test` pass (the prior step's note says all 8 tests should pass)? Not executed.
- Do the new regression tests fail on the original code? Not verifiable without the original file or a runnable `git diff`.
- Exact floating-point results for `59.7` and `0.3` were reasoned, not computed. The rounding wrapper makes them robust, but this should be confirmed by running the test.

**Suggested next step:** run `npm test` and check the four customer examples. Consider adding tests for the gaps above, and decide the half-cent rounding rule before the next change.
