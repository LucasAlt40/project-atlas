# Plan: todo priorities

## Goals

- Every todo carries a `priority` of `low`, `normal` (default) or `high`.
- `store.list({ priority })` returns only todos of that priority.
- `store.list()` without a filter returns high, then normal, then low. Within a priority, insertion order is kept.
- `formatList` shows high-priority todos with `!` before the title, e.g. `[ ] !Pay rent`. Other priorities render as they do today.
- Existing behaviour and the existing tests in `test/` keep working.

## Scope

**In scope**
- `src/store.js`: `add(title, options)` and `list(filter)`, plus a priority rank constant.
- `src/format.js`: the `!` marker for high priority.
- `test/store.test.js`: new tests for the new behaviour.

**Out of scope**
- `complete`, id generation and the title rules (unchanged).
- Persistence, a CLI, or any other module. None exists in the repo.
- `package.json` and dependencies.

## Modules and architectural impact

- `store.js` owns all state in a closure over `todos` and `nextId`. Priority is a field on the stored object, so no new module is needed.
- `format.js` has no dependencies today and should stay that way. It checks `t.priority === 'high'` and does not import from `store.js`. Three values do not justify a shared constants module.
- The public `list()` order changes from insertion order to priority order. The task requires this. Callers that only use normal todos see no change.
- `add` gains an optional second argument. One-argument calls still work.

## Decisions the Developer must follow

1. **`add` defaults and validation.** `options` defaults to `{}`. If `options.priority === undefined`, use `'normal'`. Any other value that is not `low`, `normal` or `high` (including `null`, `'HIGH'`, `'urgent'`) throws `RangeError`. Validation runs before the push, so a failed call leaves the store unchanged. The existing title `TypeError` check stays and runs first.
2. **`list` filter validation.** `filter` defaults to `{}`. `filter.priority === undefined` means no filter. An invalid value throws `RangeError`. The task does not cover this case. I chose to throw so that a typo does not silently return an empty list.
3. **Ordering.** Use `const PRIORITY_RANK = { high: 0, normal: 1, low: 2 }` and sort with `(a, b) => PRIORITY_RANK[a.priority] - PRIORITY_RANK[b.priority] || a.id - b.id`. The `id` tie-breaker keeps insertion order without relying on sort stability.
4. **One code path.** `list` always copies, then filters if a priority is given, then sorts. A filtered result is also sorted, which is harmless because its items share one rank.
5. **Copies stay.** `list` still returns `{ ...t }` copies, so callers cannot mutate store state.
6. **Shape.** New todos are `{ id, title, done, priority }`. No persisted data exists, so there is no migration.
7. **Missing `priority` in `formatList`.** Todos without the field, such as those in the existing `format` test, render as non-high. Their output does not change.
8. **Test style.** New tests go in `test/store.test.js`, in the file's flat `test(...)` and `assert` style. The four existing tests are not changed.

## Files and contracts to change

- **`src/store.js`**
  - `add(title, options = {})` adds `priority` to the stored and returned object. It throws `RangeError` on an invalid value.
  - `list(filter = {})` returns copies, filtered by `filter.priority` when given, sorted by rank then id.
  - Adds a module-level `PRIORITY_RANK`, not exported.
- **`src/format.js`**
  - `formatList` prefixes the title with `!` when `t.priority === 'high'`. The bracket part is unchanged: `[x] !title` or `[ ] !title`.
- **`test/store.test.js`**
  - New tests listed below. Existing tests unchanged.
- **`README.md`**: optional one-line note. Not required.

Resulting contracts:
- `add(title: string, options?: { priority?: 'low'|'normal'|'high' }) → { id, title, done, priority }`
- `list(filter?: { priority?: 'low'|'normal'|'high' }) → Array<{ id, title, done, priority }>`
- `formatList(todos) → string`, with `!` for `priority === 'high'`.

## Tests to add

- `add` defaults to `normal` with no options, and with `{}`.
- `add` stores `low`, `normal` and `high`.
- `add` with `'urgent'`, `'HIGH'` or `null` throws `RangeError`, and `list()` is unchanged afterwards.
- `list()` order: add `n1, h1, l1, h2, n2` and expect `h1, h2, n1, n2, l1`.
- `list({ priority: 'low' })` returns only low todos, in insertion order.
- `list({ priority: 'bogus' })` throws `RangeError`.
- `list()` and `list({})` return the same result.
- `formatList`: high renders `[ ] !title`; done high renders `[x] !title`; normal, low and todos without `priority` render as before.

### Findings, by severity

1. **Medium: `add()` returns the live stored object (`src/store.js:22-24`).** The same object is pushed into `todos` and returned, so a caller that mutates the result changes the store. Reproduction:

2. **Low: `null` options or filter throws `TypeError` (`src/store.js:16`, `src/store.js:36`).** Default parameters apply only to `undefined`. `s.add('a', null)` throws `Cannot read properties of null`, and `s.list(null)` does the same. 3. **Low: non-object options fall back silently.** `s.add('a', 'high')` or `s.add('a', 5)` gives `'normal'` with no error, because `'high'.priority` is `undefined`. This is reasonable under the spec, but it is a silent failure. You may want to reject non-object options.

4. **Low: test gaps.** These are behaviours the code handles but no test checks:

   - `list({ priority: 'normal' })` returns only normal todos.
