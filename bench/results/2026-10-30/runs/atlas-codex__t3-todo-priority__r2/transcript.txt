# Todo Priorities Plan

## Goals

- Add validated `low`, `normal`, and `high` priorities to todos.
- Default omitted priorities to `normal`.
- Support priority filtering and stable `high → normal → low` ordering.
- Prefix high-priority formatted titles with `!`.
- Preserve all existing behavior and tests.

## Scope

In scope:

- `src/store.js`: priority validation, storage, filtering, ordering.
- `src/format.js`: high-priority marker.
- `test/store.test.js`: regression coverage.

Out of scope:

- Persistence, dependencies, CLI changes, title/completion behavior, or new abstractions.

## Architecture and dependencies

The in-memory store in `src/store.js` owns todo creation, IDs, and ordering. `src/format.js` remains a pure presentation module with no store dependency. Tests use Node’s built-in runner; there are no production dependencies.

`add(title, options)` will preserve existing title-only calls, default priority to `normal`, reject invalid priorities with `RangeError` before mutating state, and store `priority` on each todo.

`list(filter)` will return shallow copies. A priority filter will use exact matching. Without a filter, it will sort copied results by `high`, `normal`, then `low`, preserving insertion order within each priority and leaving the internal array unchanged.

`formatList` will add `!` only for `priority === 'high'`; missing or other priorities retain the existing output.

## Developer decisions

1. Keep priority logic local to `src/store.js`.
2. Do not mutate the internal todo array while sorting.
3. Preserve `add(title)` compatibility.
4. Keep formatter compatibility with objects that omit `priority`.
5. Add tests for defaults, accepted/rejected values, persistence, filtering, stable ordering, and formatting.

## Files and contracts

- `src/store.js`: change `add(title)` to `add(title, options)` and `list()` to `list(filter)`.
- `src/format.js`: render high-priority todos as `[ ] !Title` or `[x] !Title`.
- `test/store.test.js`: add coverage for all new behavior.
- `docs/plans/todo-priorities.md`: saved implementation plan.

## Risks

- Mutating state during sorting.
- Losing insertion order among equal priorities.
- Breaking existing `add(title)` callers.
- Making formatting require a priority field.

## Verification

Run `npm test` and review the diff. Tests must cover default and valid priorities, `RangeError` validation, stored priority fields, filtering, stable ordering, and high-only formatting markers.

## Scope

- `src/format.js`: `!` prefix for high-priority todos.
- `test/store.test.js`: regression tests for defaults, validation, filtering, ordering, stability, and formatting.

Out of scope: persistence, new dependencies, CLI changes, title/completion behavior, or new modules.

## Architecture

The project has two production boundaries:

- `src/store.js`: owns in-memory todo state, IDs, mutation, and list ordering.
- `src/format.js`: pure presentation logic consuming todo-shaped objects without importing the store.

The change adds a `priority` field to the store’s todo contract but introduces no new dependency edges. The formatter must remain compatible with objects lacking `priority`.

## Developer decisions

- Preserve `add(title)` compatibility by defaulting priority to `normal`.
- Accept only `low`, `normal`, and `high`; throw `RangeError` before mutating state for invalid values.
- Keep internal insertion order unchanged.
- `list({ priority })` filters by exact priority.
- Unfiltered `list()` returns copies ordered `high`, `normal`, `low`, preserving insertion order within each group.
- Sort a derived array, never the internal `todos` array.
- Format only `high` priority with `!` immediately before the title.
