## Problem and correct behaviour

`total(items, couponCode)` should return a number rounded to cents and never negative. Each line counts `price × qty`. A percent coupon takes that percentage off (100 with OFF20 gives 80). A fixed coupon subtracts its value (5.00 with TENOFF gives 0). Unknown coupons are ignored.

## Root cause: confirmed (by reading `src/cart.js` and `test/cart.test.js`)

| Symptom | Cause | Location (before fix) |
|---|---|---|
| 3 × 19.90 shows 19.9 | `qty` never used | `src/cart.js:16` `sum += item.price;` |
| OFF20 on 100 shows 20 | Percent branch returns the discount, not the net price | `src/cart.js:21` `(sum * coupon.value) / 100` |
| TENOFF on 5.00 shows −5 | No floor at zero | `src/cart.js:23`, and `return sum` at `:26` |
| 0.30000000000000004 | No rounding | `src/cart.js:26` |
| Unknown coupon (latent, not reported) | `COUPONS[couponCode]` also matches inherited names like `toString`. That gives a function, so `sum - undefined` becomes NaN. | `src/cart.js:18` |

No other code is on the path. The git history has only `initial` and `fixture`, so there was no recent change to blame. The test file covers only a single item and an empty cart, which is why none of this was caught.

## What I changed

- **`src/cart.js`**
  - Each line adds `item.price * item.qty`.
  - The coupon is looked up with `Object.prototype.hasOwnProperty.call`, so unknown and inherited names are ignored.
  - A percent coupon now computes `sum * (100 - value) / 100`.
  - The result is `Math.max(0, Math.round(sum * 100) / 100)`, which clamps at zero and rounds to cents.
  - The `module.exports = { total }` API is unchanged.
- **`test/cart.test.js`**: I added regression tests for quantity, percent net price, the fixed-coupon floor at zero, cent rounding, and unknown coupons (`NOPE` and `toString`). The two existing tests are untouched.

I checked each case by hand against the new code. I have not executed them.

## Commands to run and expected results

- `node --test test/` should show 8 passing tests (the 2 original and 6 new), 0 failing.
- The new `quantity multiplies the price` test should give 59.7 for 19.9 × 3.
- The `percent coupon` test should give 80 for 100 with OFF20.
- The `fixed coupon` test should give 0 for 5 with TENOFF.
- The `totals are rounded to cents` test should give 0.3 for 0.1 + 0.2.

## Residual risks

- **Half-cent rounding.** `Math.round(x * 100)` depends on binary floating point, so a value such as 1.005 may round down. A decimal-safe approach (integer cents throughout) would remove this, but it is a bigger change than the bug needed.
- **No input validation.** Negative prices or quantities, non-numeric values, and a percent above 100 are not validated. A percent above 100 is clamped to 0 by the floor, not rejected.
- **Scope.** The report did not say whether totals should be rounded per line or only at the end. I rounded only the final total, which matches "totals must be rounded to cents".

**Verdict:** The fix addresses the four reported symptoms. I found no blocking defect by reading. Tests were not run, so the pass claim rests on tracing, not execution. The handoff's expected test count is wrong.

**Root cause (from the investigation, confirmed against current code):**
1. `total()` added `item.price` and ignored `qty`.
2. Percent coupons returned the discount (`sum * value / 100`) rather than the net price.
3. The total was returned with no zero floor and no rounding, so it could be negative or show float noise.
4. `COUPONS[couponCode]` matched inherited names such as `toString`, which produced `NaN`.

**Fix applied (`src/cart.js:13-30`):**
- Line 16: `sum += item.price * item.qty`.
- Lines 18-20: coupon lookup uses `Object.prototype.hasOwnProperty.call(COUPONS, couponCode)`, so inherited names and `undefined` are ignored.
- Line 23: percent coupons become `sum * (100 - value) / 100`, the net price.
- Line 29: `Math.max(0, Math.round(sum * 100) / 100)` rounds once at the end and clamps at zero.
- Export is still `module.exports = { total }` (line 32), so the API is unchanged.

**Trace of the reported cases (read, by hand):**

**Findings, by severity:**

2. **Low–medium, correctness:** NaN is not guarded. `total([{ price: 5 }])` (missing `qty`) gives `NaN`, since `Math.max(0, NaN)` is `NaN`. This breaks "totals must be numbers." Recommendation: validate `qty`/`price` as finite numbers, or default `qty` to 1, and add a test.

5. **Low, data handling:** Negative prices or quantities are silently clamped to 0 rather than rejected. That hides refunds or bad input. Recommendation: decide whether to reject them or leave the clamp as intended.

6. **Info:** `total(undefined)` throws. Pre-existing and out of scope unless the spec requires it.
