## Plan: todo priorities

### Goals
- Each todo carries a `priority` of `'low'`, `'normal'` or `'high'`, defaulting to `'normal'`.
- `store.list({ priority })` returns only todos of that priority.
- `store.list()` with no filter returns todos sorted high, normal, low. Ties keep insertion order.
- `formatList` prefixes high-priority titles with `!` (`[ ] !Pay rent`). Other priorities render as before.
- Existing behaviour and the four existing tests in `test/store.test.js` stay unchanged.

### Out of scope
- Changing `complete()`, the `done` flag or the id scheme.
- Persistence, CLI, or README changes. The README is one line and needs no update.
- Sorting or filtering by anything other than priority.
- Changing `list()`'s return type. It still returns copies, not internal objects.

### Modules and dependencies
- `src/store.js` owns all todo state through a closure over `todos` and `nextId`. Validation, defaulting, sorting and filtering go here.
- `src/format.js` is pure rendering with no dependency on `store.js`. It must stay that way and only needs the literal `'high'`.
- `test/store.test.js` is the single test file, covering both modules. No new dependencies; `package.json` already runs `node --test`.

Architectural impact is limited to `store.js`'s public surface. `list` gains an optional argument, which is backward compatible. `formatList`'s input shape is unchanged, and `priority` is optional on input.

### Decisions for the Developer
1. **One priority-order constant in `store.js`**, e.g. `const PRIORITIES = ['high', 'normal', 'low'];`. Validation uses `includes`; sort rank uses `indexOf`. Don't export it or add a module, since nothing outside `store.js` needs it.
2. **Defaulting uses an explicit `undefined` check**, not `??` or `||`. `add('a')` and `add('a', { priority: undefined })` both give `'normal'`. `null`, `''`, `'urgent'` and any other value throw `RangeError`.
3. **`add(title, options = {})`**. The existing `TypeError` for an empty title is checked first.
4. **`list(filter = {})`**. If `filter.priority !== undefined`, it must be valid, otherwise `RangeError` (same rule as `add`). The spec doesn't cover an invalid filter; I chose to throw rather than silently return `[]`.
5. **Sort the copied array** that `list()` returns, never the internal `todos`. Use `Array.prototype.sort` with the rank comparator. It is stable, so ties keep insertion order. Don't add an index field.
6. **`formatList` tests `t.priority === 'high'`**, not `!t.priority`. The existing format test passes todos without a `priority` field, and they must still print `[x] a` and `[ ] b`.
7. **Every todo gets `priority`** when created in `add`, so both the returned object and `list()` copies include it.

### Files and contracts to change
- `src/store.js`
  - `add(title, options = {})` returns `{ id, title, done, priority }`.
  - `list(filter = {})` returns sorted copies, filtered by `filter.priority` when given.
- `src/format.js`: `formatList(todos)` renders `[x] !title` or `[ ] !title` for high, and the existing form otherwise.
- `test/store.test.js`: keep the four existing tests and add the tests below.

### New tests (in `test/store.test.js`)
- `add` defaults priority to `'normal'`.
- `add(title, { priority })` stores `'low'`, `'normal'` and `'high'`.
- `add` with `'urgent'`, `null` or `''` throws `RangeError`.
- `list()` orders high, normal, low, and keeps insertion order within each group.
- `list({ priority: 'low' })` returns only low todos, in insertion order.
- `list({ priority: 'urgent' })` throws `RangeError`.
- Repeated `list()` calls return the same order, so the internal store is not reordered.
- `formatList` prints `[ ] !Pay rent` for high and plain `[ ] title` for the others. The existing format test still passes.

### Risks
- **Default order of `list()` changes** whenever priorities are mixed. That is what the spec asks for. The existing "add and list" test uses only default priority, so it still passes.
- **`null` throws in `add`.** A caller passing `null` to mean "default" gets an error. This follows the spec, but it should be mentioned in the final summary.
- **Old-shape todo objects** without `priority` in `formatList` are handled by decision 6.

### Verification
- `npm test` (`node --test`) must pass: the four existing tests plus the new ones.
- Each new test maps to one behaviour in the spec.
- Reviewer check: `src/store.js` never sorts the internal `todos` array, and `src/format.js` does not require `store.js`.
