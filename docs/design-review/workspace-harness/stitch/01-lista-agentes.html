Análise de Idempotência do Módulo Billing

Analisei o fluxo de processamento de faturas (/api/v1/invoices/reconciliation). O endpoint atual processa transações assíncronas via mensageria, porém apresenta duas vulnerabilidades críticas de duplicidade:

  • Payload Duplicado: Não há checagem de Idempotency-Key no cabeçalho HTTP antes da inserção na fila de reconciliação.
  • Lock Distribuído: O banco de dados executa a transação sem trava pessimista ou registro transacional com chave composta (invoice_id + reconciliation_hash).

Proposta de migração para assegurar atomicidade via PostgreSQL com bloqueio distribuído em Redis/Redisson:

BillingReconciliationService.java · PostgreSQL 16 
@Transactional
public ReconciliationResult reconcileInvoice(String idempotencyKey, InvoicePayload payload) {
    // 1. Verificação de chave de idempotência com TTL de 24h
    boolean isNew = redisTemplate.opsForValue()
        .setIfAbsent("idemp:billing:" + idempotencyKey, "PENDING", Duration.ofHours(24));
    
    if (!isNew) {
        return invoiceRepository.findByReconciliationKey(idempotencyKey)
            .map(ReconciliationResult::fromEntity)
            .orElseThrow(() -> new ConcurrentExecutionException("Reconciliação em andamento"));
    }
    
    // 2. Bloqueio no registro financeiro da transportadora
    return executeAtomicReconciliation(payload);
}
